Description

Calling purgeDatastream with a start date-time parameter in a format that Fedora doesn't recognize results in Fedora using a start date-time of null and purging all versions of the datastream.

For example, I have a datastream with versions created at:
2010-05-19T20:41:42.903Z, 2010-05-19T20:41:42.540Z, and 2010-05-19T20:41:42.140Z

If I call purgeDatastream with a startDT parameter of 2010-05-19T20:41:42.000540Z (which should remove the 2 newer versions, but format is not quite right), all versions of the datastream are purged. I get the same behavior if I use a date in another format, e.g. 2010-05-19 20:57:34.739000+00:00 (even for a time that is newer than all the datastream versions).

Here is the output for the purgeDatastream call from the fedora log:

Completed purgeDatastream(pid: eulcoretest:11565, datastreamID: TEXT, startDT: null, endDT: null, logMessage: Purged datastream (ID=TEXT), versions ranging from the beginning of time to the end of time. This resulted in the permanent removal of 3 datastream version(s) (2010-05-19T16:41:42.140Z, 2010-05-19T16:41:42.540Z, 2010-05-19T16:41:42.903Z) and all associated audit records.)

As a side note, it might be helpful to indicate in the documentations that Fedora will accept a date-time that includes 3 digits of microseconds (same format as what it returns in datastream history)

Comments (2)

eddie, 2010-05-24 22:26 UTC

This is pretty bad. Without actually looking at the code, I can guess what's happening: the DateUtility method for parsing a datetime string returns null if it can't parse the date. If the caller isn't checking for that and simply passing the returned value the situation described could result.

So, either, check for null return, or, consider actually making the DateUtility method throw an exception (unchecked, maybe illegalargumentexception) but I'm not sure what else that would affect.

For FCREPO-689 Closed , I already started some work on parsing datetime strings as rest params and returning 400 errors if there's a date parse error. I only needed it to handle lastModifiedDate, but I can apply it to all the REST params that take datetimes.

eddie, 2010-05-25 07:42 UTC

This needs to be verified w/ the SOAP API as well. Glancing at the code, it looks like it suffers from the same problem (see FedoraAPIMBindingSOAPHTTPImpl).

Increasingly thinking that DateUtility should throw at least an unchecked exception if there's a parseexception. However, should a null argument just return null? We have a lot of code that can validly take a null Date (or date string), so either we check for that before calling DateUtility or allow DateUtility to continue to return null for null arguments.
