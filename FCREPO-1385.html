Description

This task is to re-implement blank nodes along the lines of the following plan:

1) The REST API would continue to accept RDF documents with blank nodes (this is not a change from the current behavior).

2) The fedora:Blanknode class in the fedora ontology would be eliminated.

3) Blank nodes will no longer be published at the .well-known/genid location.

That is, when RDF documents with blank nodes are added to Fedora, those blank nodes will be skolemized internally and stored under the node that the RDF document described, but will not be made available at any location.

4) When fedora:Container nodes are requested, any skolem nodes contained in that document will be serialized as blank nodes, according to the concrete RDF syntax that is requested.

5) When a fedora:Container (one that contains blank nodes) is deleted, the corresponding skolem nodes will also be removed from Fedora.

Andrew Woods, 2015-04-27 00:06 UTC

I have poked a bit at this issue and made some small progress. The issue that I am seeing is that deskolemization is happening during RDF updates (PUT and PATCH), and causing two issues:
1) Blank node identifiers are rejected by the JcrPropertyStatementListener as "not being in the domain"
2) In RDF updates, provided blank nodes are not able to match with existing blank nodes which are deskolemized.

The following PR appears to address the PATCH scenario, as detailed below, without any apparent ill effect.
https://github.com/fcrepo4/fcrepo4/pull/786

PATCH scenario:
curl -i -XPUT localhost:8080/rest/foo
curl -i -XPATCH -H"Content-Type: application/sparql-update" --data-binary @bnode.txt localhost:8080/rest/foo
curl -i -XPATCH -H"Content-Type: application/sparql-update" --data-binary @bnode-update.txt localhost:8080/rest/foo

Where "bnode.txt" and "bnode-update.txt" are the same as Unknown's above, and attached to this ticket.

Unfortunately, I have not found a resolution to the PUT scenario outlined below.
PUT scenario:
curl -s -o foo.out localhost:8080/rest/foo

  • update in foo.out – foaf:givenName "Klaus" => "Super"
    • also update the blank node identifiers, as they are apparently not proper RDF

curl -i -XPUT -H"Content-Type: text/turtle" --data-binary @foo.out localhost:8080/rest/foo

  • fails

In general, it seems that if we limited the deskolemization to RdfStreams that are being returned to the client, then all should be well. The issue comes when we deskolemize resources internally while trying to perform update operations.

A. Soroka, 2015-04-30 13:37 UTC

On closer inspection, it's actually removing blank nodes that is the problem. (Which appears as a problem modifying them because SPARQL Update's version of modification is removal-and-then-insertion of triples.)

Because the mapping between RDF resources and Fedora resources (as represented in IdentifierConverter and its subtypes) is one-in-one-out, it's not possible to determine, given a blank node to be removed, which Skolem node should be removed.

This is obviously a solvable problem, and we'd have to look at the various techniques that actual triplestores have used to solve it. I'm in no position to dedicate that time, and I doubt anyone else is. As predicted, attempting to deal with blank nodes is going to slowly turn Fedora into a shoddy triplestore.
