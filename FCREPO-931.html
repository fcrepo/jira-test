FCREPO-931 Modifying a datastream does not always result in modifications being in the latest datastream version

Description

It's a fairly obscure scenario, but it is one that I hit over the weekend that led to hours of debugging to track down...

In general we don't allow setting the datastream last modified timestamp when making changes to content - this is set automatically based on the server date time.

There's one exception - ingest: It is possible to specify a datastream version last modified date to some point in the future.

Then, when the content is modified, a new version is created containing the modified content, but with a last modified date earlier than the version ingested.

So when viewing the "latest" datastream content, you don't see the changes you just made, you see the original.

(This hit me adding some test cases to TestRESTAPI where datastreams are ingested with an explicit date/time which was set to the current date/time, but not as UTC, instead it was formatted as UTC but the actual value was the locale. So here, in summer time, the datastream versions were therefore an hour ahead of the actual time).

Potential solutions:

1) Don't allow ingest of a datastream version with a last modified date in the future - fail the ingest and report an error

2) When creating a new datastream version, verify that it is in fact the latest (check there aren't any versions with a later date/time).

Preference would be for (1) as that's the "invalid" action. (2) is just catching the problem at a later stage, and is harder to rectify (currently the FOXML would have to be edited directly). But maybe we would do both to cater for upgrading to a new version of Fedora where the content is already invalid.
