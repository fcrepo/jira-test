Description

Review all RDF representations available from Fedora's HTTP API to separate them into two categories:

  • Those that are documented in a Fedora API module ontology and to which the Fedora architecture is committed.
  • Those to be added to a kill-list for removal.

All JCR-exposing triples should certainly be removed.

Unknown, 2016-03-01 14:02 UTC

Yes and no. The representations themselves are in a pretty good state now. The main exception to that is:

    <> fedora:exportAs </foo/fcr:export?format=jcr/xml>
    </foo/fcr:export?format=jcr/xml> dc:format <http://fedora.info/definitions/v4/repository#jcr/xml>

The other issue is that FedoraResourceImpl::getTriples(), when requesting server managed triples, will include all sorts of internal JCR properties: jcr:primaryType, jcr:mixinTypes, etc, which the HTTP api then filters out after the fact. It would be much better to simply not produce those triples in the first place. I have a ticket to remove those: FCREPO-1935 Closed , but first, we need to change how the template rendering happens, which depends on the existence of those properties. See FCREPO-1934 Closed .

W/R/T the fcr::export endpoint, that seems tied directly to a JCR representation of the internal node. Is that deprecated now? Especially given the camel-based serialization tool? Andrew Woods can weigh in on that.

Unknown, 2016-03-01 14:15 UTC

As a side note, the current F4 ontology contains a number of JCR-specific properties that should be evaluated: frozenMixinTypes, frozenPrimaryTypes, frozenUuid, hasNodeType, mixinTypes, primaryType, uuid, UnmappedType, hasDefaultWorkspace, hasWorkspace, hasWorkspaces. There may be others in this category, but those jumped out at me.
