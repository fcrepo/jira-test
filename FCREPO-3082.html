FCREPO-3082 Remove PathLockManager and its dependencies if advisable

Description

There are two dependent tasks associated with this ticket.  The first part is to determine whether or not it makes sense for us to remove the PathLockManager and its dependencies.  If it is determined that this is the way to go, the second part is to remove the interfaces, classes, and lines of code that depend on this utility.

Comments (8)

Peter Matthew Eichman, 2019-09-26 19:25 UTC

Is this part of a switch to an "optimistic locking" model? That is, we don't lock resources in advance of changes, we just check ETags/StateTokens at update time?

If so, we can get rid of the PathLockManager and associated code. There will need to be something to replace it, though, to handle actual conflicts.

Peter Matthew Eichman, 2019-09-26 20:04 UTC

On the other hand, if we want to keep the semantics of path-based conflict assessment, even in our optimistic locking scenario, then we would need to traverse a resource's hierarchy, correct? I guess what I'm saying is that knowing whether we can rip out the PathLockManager classes wholesale depends on how we intend to implement optimistic locking.

Peter Matthew Eichman, 2019-09-27 15:07 UTC

Ben Pennell, are we planning on handling conflicts between multiple writes in the persistence layer?

Danny Bernstein, 2019-11-06 16:51 UTC

I think what we're planning is a sort of two phased commit in the OCFLPersistentStorageLayer that would ensure that all OCFLObjects affected by a transaction  are locked before the first write occurs.   

In the case that we are stamping new object versions, rollback is possible in the case of a write failure.   However we don't have a good rollback solution when  writing to the mutable head.

 

Ben Pennell, 2019-11-06 17:43 UTC

Yes rollbacks are trickier with mutable head, they probably aren't really possible without duplication of data if a commit fails partway through. Hopefully by locking all the OCFL objects in a transaction just prior to committing these should be a very rare situation, caused by system error rather than user. But I suspect we will do pessimistic locking at the persistence layer during commits to minimize the chance of a rollback.

It seems like locking by path could still be relevant, and with suitable indexing might not be too costly. I feel like we need to think through and document a more holistic perspective of how we want to handle conflicts now that we are responsible for pretty much everything. The persistence layer can handle locking at the OCFL object level, but I don't know if it'll be the appropriate place to handle conflicts. The kernel level would have a better view of resources as a whole, while the persistence level if looking at things more at the filesystem level.

Danny Bernstein, 2019-12-10 18:08 UTC

In working through https://jira.lyrasis.org/browse/FCREPO-3154,  it is making sense to remove the PathLockManager.  If we want to revive it in the future,  we can always bring it back.
