Description

I am testing an ActiveMQ queue in a "standalone" configuration and I have noticed that there is a difference in the way that fcrepo-triplestore-indexer consumes these messages from a queue instead of a topic. Basically, any triple with a subject skolem/bnode is not consumed/updated with a queue, but is with a topic. Object skolems are indexed in both cases.

Steps to reproduce:
1. Change jms.xml to use JmsQueuePublisher.
2. Insert into container a skolem type graph. (e.g. <> <http://iiif.io/api/presentation/2#hasImageAnnotations> _:c14n18 .
_:c14n18 <http://www.w3.org/1999/02/22-rdf-syntax-ns#first> _:c14n12 .
_:c14n12 <http://www.w3.org/1999/02/22-rdf-syntax-ns#type> <http://www.w3.org/ns/oa#Annotation> .)
3. Check indexing.

I have paused the indexing consumer so that I could see the messages in the ActiveMQ queue. As expected, there is only one message queued for the modification of the parent container. I noticed that the number of Camel exchanges with a topic versus a queue was more (6 vs. 3). With a topic, 2 messages are produced in activemq for the above example, but a queue only produces one.

Since it is not possible to get the second two triples from the parent container using a URI like http://localhost:8080/fcrepo/rest/test2?preferInclude=PreferMinimalContainer&accept=application/rdf+xml, I am guessing that a topic must include more messages, particularly relating to the creation of the bnode/skolems.

According to the http://fedora.info/spec/#message-data, a Skolem, being an LDPR should produce events. But it seems that https://github.com/fcrepo4/fcrepo4/blob/master/fcrepo-kernel-modeshape/src/main/java/org/fcrepo/kernel/modeshape/observer/DefaultFilter.java does not include it as a type.

Unknown, 2017-02-23 16:46 UTC

There is no difference in how messages are produced between queues and topics. The issue you are encountering relates to an assumption made by the fcrepo-triplestore-indexer, such that it expects the "single subject rule" to be in effect. I.e. that all triples will contain the same subject (including hash URIs). BNodes, of course, break that expectation.

The solution is to either 1: don't use BNodes or 2: index your triples into named graphs (this would involve writing your own triplestore indexer or waiting until someone else writes one – I'd like to at some point, but it's not high on my priority list).

Christopher Johnson, 2017-03-03 09:52 UTC

Unknown sure, great idea, but I would have to write new resolver logic for Loris to send variable `Accept` headers to acrepo-exts-image depending on source format foreknowledge criteria specified from the client. The process question is from where does the image server determine what resource format it is requesting and what format it is producing. The obvious answer is from the image viewer client (via a manifest object), but this is not SOP, yet. In the case of JP2, there are also distinct server decompression methods for the same content type, so the image server/client should theoretically also add its supported decompression method (e.g. kakadu or openjpeg) in the request.

In the IIIF manifest, a resource is required to have a source format, and a service definition for the image server request. The right place for the content-type specification for the Accept header would be in a manifest service definition, imo. (Though, this also is a bit complicated, because there are two distinct image server responses, the default IIIF API info.json image server service response (JSON-LD) and the resource binary serialization that is produced from a full IIIF URI.)

The viewer client then processes the service definition and it requests from the image server a resource with an Accept header, and then the image server would handle a viewer client specified format by resolving it against an appropriate Fedora API-X service (and also passing its own Accept header).

Image viewer clients (and consequently the servers) are generally quite liberal about content-type (format) requirements, and AFAIK none of them are implementing conneg. Currently, Loris just reads the content-type from the response and then passes it to a handler rather than asking for it explicitly. It seems that it wants to be able to handle every possibility. I have previously addressed the relevance of conneg to the IIIF here I personally agree with enforcing a more stringent protocol on the client regarding (mandatory) Accept headers, but they seem to view it as more of "unnecessary complication".

The neat thing about API-X is that a particular encoding format can be wired into the service directly, and templated URIs can be made for each format, perhaps. So, for example a TIFF resource at <http://localhost:8080/fcrepo/rest/001.tif> can have multiple service URIs, like <http://localhost/services/001.tif/svc:jp2> or <http://localhost/services/001.tif/svc:png>, and the template resolver would make an image service URI like <http://localhost:5004/jp2:001.tif> or <http://localhost:5004/png:001.tif>. The prefixes jp2: and png: simply identify IRI templates that append the /svc:jp2 or /svc:png contexts on the request URI. While having an image service be able to process multiple output formats is a brilliant implementation, maybe it is easier to make these services a bit less flexible and bound to a SOLID design pattern.
