FCREPO-3257 PUT on existing container should be 409

Fix versionsFedora 6.0.0

Description

When comparing Fedora 5 and Fedora 6 behavior, it is seen that PUTting onto an existing container has the following results:

  • F5 = 409
  • F6 = 204

The following command can be run on two the different versions of Fedora:
curl -s -i -XPUT localhost:8080/rest/a | grep HTTP
curl -s -i -XPUT localhost:8080/rest/a | grep HTTP

Using the 5.1.0 jetty-console https://github.com/fcrepo4/fcrepo4/releases/download/fcrepo-5.1.0/fcrepo-webapp-5.1.0-jetty-console.jar (note that you must be using a Java8 runtime)
..and using the 6.0.0-SNAPSHOT jetty-console

This ticket should also either resolve the following Fedora API Test Suite failures, or create follow-on tickets for their resolution:

  • https://fedora.info/2018/11/22/spec/#http-put-ldprs
    Any LDP-RS must support PUT to update statements that are not server-managed triples (as defined in [LDP] 2). [LDP] 4.2.4.1 and 4.2.4.3 remain in effect.
  • https://fedora.info/2018/11/22/spec/#http-put-ldprs
    The server must provide a corresponding response body containing information about which statements could not be persisted. ([LDP] 4.2.4.4 should becomes must).
  • https://fedora.info/2018/11/22/spec/#http-put-ldprs
    In that response, the restrictions causing such a request to fail must be described in a resource indicated by a Link: rel="http://www.w3.org/ns/ldp#constrainedBy" response header per [LDP] 4.2.1.6.

Technically you can PUT on an existing container, this is more a question of what you are PUTting and whether it should conflict.

Andrew Woods, 2020-05-21 16:13 UTC

In this test, we are PUTting an empty container twice. In any case, the semantics of PUT should be: whatever was there before, replace it with this.

Jared Whiklo, 2020-05-21 16:58 UTC

I agree with your interpretation of the PUT semantics.

I think the current 204 response is a false positive (ie. its not actually replacing the contents, but I'm not sure).

But we need to add in our handling of server managed triples because in theory the correct response would be 204 unless you try to add a rdf:type with ldp: namespace or change the interaction model.

Fedora 5 threw a lot of 409s on PUT related to people GETting and PUTting server managed triples. Once we start to silently ignore those triples we can reduce the 409s by a large extent.

That said I don't know (and I can't find) a Jira ticket related to this new ignoring SMTs behaviour. Though I think this old ticket might be valid
https://jira.lyrasis.org/browse/FCREPO-1416

Jared Whiklo, 2020-10-14 19:21 UTC

Fedora API Test Suite does not test this properly (does not currently allow for a failure) and being a generalized test suite I am not clear how it can tell what is a server managed triple. Even the URI for include/omit is implementation specific (http://fedora.info/definitions/v4/repository#ServerManaged)
