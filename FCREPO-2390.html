Description

This bug can be seen when executing a sparql-update request that attempts to delete a property that does not exist.
The response returns with a 204, but no properties are deleted.
The solution to this issue should be to return a 400 Bad Request.

To demonstrate the error:

  1. Create a resource, "test".
    > curl -i -XPUT localhost:8080/rest/test
  2. Add properties to the new resource
    > curl -i -XPATCH -H"Content-Type: application/sparql-update" --data-binary @rdf_insert.txt localhost:8080/rest/test
  3. Attempt to delete resources
    > curl -i -XPATCH -H"Content-Type: application/sparql-update" --data-binary @rdf_delete_one_multiple_one_non_existing.txt localhost:8080/rest/test
    • Notice 204 response but no change in the "test" resource

See attached "rdf_insert.txt" and "rdf_delete_one_multiple_one_non_existing.txt"

Unknown, 2017-01-24 14:02 UTC

This is expected behavior (it is not an error). A SPARQL Update with a WHERE clause will attempt to match a graph. If the match pattern contains a triple that does not exist in the resource, there is no match. If there is no match, nothing will be removed. Therefore, there would be no change in the resource, and a 204 would be an appropriate response.

If you want 10 separate delete statements, you need to execute them as 10 delete statements, not a single delete statement. It seems that you would rather have a Sparql Update like this:

Unknown, 2017-01-24 15:12 UTC

My point is this: it is not a failure. Just as a SPARQL Query that doesn't match a graph, a SPARQL Update that doesn't match a graph results in no change. This is from the spec:

The DELETE WHERE operation is a shortcut form for the DELETE/INSERT operation where bindings matched by the WHERE clause are used to define the triples in a graph that will be deleted. Analogous to DELETE/INSERT, deleting triples that are not present, or from a graph that is not present will have no effect and will result in success.

Unknown, 2017-01-24 15:18 UTC

More from the spec:

The pattern in WHERE is matched against the Graph Store. The resulting sequence of
solutions to the WHERE clause is used to instantiate the triple patterns in the
DELETE template similar to CONSTRUCT in SPARQL 1.1 Query. The resulting
triples are then removed from the Graph Store.

Thus, if there is no match from the WHERE clause, nothing will be removed because there are no triples in the resulting graph.

Benjamin Armintor, 2017-01-24 15:30 UTC

You have to read across the entire DELETE/INSERT spec to resolve the ambiguity that results from read the DELETE WHERE shortcut spec in isolation. It expands to DELETE

{...} WHERE {...}

, with the same pattern:
"The QuadPattern is used both as a pattern for matching against triples and graphs, and as the template for deletion."

And from DELETE:
"The WHERE clause identifies data in existing graphs, and creates bindings to be used by the template. The graphs to apply the GroupGraphPattern follow the same rules as for DELETE/INSERT."

And from DELETE/INSERT:
"The GroupGraphPattern in the WHERE clause is evaluated as in a SPARQL query "SELECT * WHERE GroupGraphPattern" and all the solution bindings are applied to the preceding DELETE and INSERT templates for defining the triples to be deleted from or inserted into the Graph Store."

If the WHERE doesn't match the resource, there is no solution set to pass to DELETE.
