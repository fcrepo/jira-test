Kevin Bowrin, 2015-04-14 17:51 UTC

Hello, original big reporter here.

Question 2: As far as I remember, the result of this bug causes an error in fcrepo-message-consumer, causing resources to not be indexed by the RDF indexer and likely the full text indexer, but I didn't get that far. This might be a bug in fcrepo-message-consumer or fcrepo.

Question 1: Yes, the baseUrl for the resource is set incorrectly when you create a resource using the WebUI... through a proxy. This might happen in a port-forwarding scenario, or when one is using a proxy server.

More details: I was creating a virtual machine in Virtualbox. That virtual machine's fcrepo was available to the host at http://localhost:38080. Virtualbox would take any requests to that port on the host machine and forward them to port 8080 on the guest machine.

To reproduce:

  • Create a virtual machine in Virtualbox with port forwarding from a host port (like 38080) to the Fcrepo port (default is 8080, I think).
  • Install Fcrepo on the guest.
  • Install the RDF indexer and fcrepo-message-consumer.
  • Access the WebUI through the forwarded port.
  • Add a resource in the WebUI.

If the bug is reproducible in the latest version of Fcrepo: The indexer will not have statements for the newly created resource.

I think creating a resource in the WebUI set the baseURL of the resource to localhost:38080 (what's in the address bar) and not the baseURL of the server (localhost:8080). This causes the error in fcrepo-message-consumer.
It also means, depending on how you 'got to' the REST API, different resources would have different baseURLs. (localhost:8080/fcrepo/rest vs mydomain.net/fcrepo/rest) That's just speculation, though.

Let me know if you need any help. Thanks for looking at this.

Jared Whiklo, 2015-04-14 20:59 UTC

The HttpResourceConverter uses a translator initialized in FedoraBaseResource, that is initialized using the FedoraLdp.class.

That uses a javax.ws.rs.core.UriInfo in AbstractResource, which from documentation allows you to rebuild the Uri for a request without having it hard-coded. So the URI is based on the URI the request was sent to.

Probably because the VM doesn't touch the traffic it just re-directs it, hence the baseUri is built using the external facing port instead of the correct internal one.

Former user, 2015-04-16 16:19 UTC

Jared Whiklo: the initial approach was setting the baseURL only once, to avoid problems with ObservationManager opening too many threads. That bug was fixed, and a new requirement was added (tracking the userAgent which would vary between requests). So we switched to setting the baseURL and userAgent with each request, and that seems to solve the other problem too.

Kevin Bowrin, 2015-04-16 19:09 UTC

If you're going to make the assumption that all clients (users, applications, indexers) will access the repository using the same address, that should be indicated in the setup documentation.

IMHO, an Indexer shouldn't ignore messages produced by a client that happens to use port forwarding or a proxy or an altered hosts file. The repository doesn't ignore those clients, so you'll get inconsistent data.

Jared Whiklo, 2015-04-16 19:45 UTC

I agree with Kevin that an assumption has been made when dealing with Fedora instances behind a NAT firewall. So I'd say no, it's not resolved by that commit.

It makes sense that the UriBuilder uses the request to generate the URLs it sends back, but for JMS messages it becomes more complicated.

I think I mentioned this before, but I feel we can either:

a) leave it as is and document this behaviour.

b) determine the web-app container server name and port and add those to the JMS Message as alternate baseUrls. This requires a change to the fcrepo-message-consumer, possibly fcrepo-camel?

c) some hybrid version, where you configure your Fedora instance if you are behind a NAT firewall and your JMS message consumer are as well.
