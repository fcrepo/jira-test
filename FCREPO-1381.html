Description

This task is to determine where in the application stack sparql-update requests, like the one below, are having their namespace declaration mis-interpreted.
The following example should successfully create a "esc" namespace prefix.

  1. Request
    curl -i -XPATCH -H"Content-Type: application/sparql-update" --data-binary @props.sparql localhost:8080/rest/testcontainer
  1. Where, props.sparql is:
    ---------------
    PREFIX esc: <http://myurl.org>
    INSERT { <> esc:package "ppp"; }

    WHERE { }
    ---------------

See: https://groups.google.com/d/msg/fedora-tech/rk8U4KCKWbc/2J6bZkP3AxwJ

Osman Din, 2015-02-26 20:59 UTC

The misinterpretation is happening in Jena Prologue .-

The result is that the update statement returned by the parser is :

INSERT <http://localhost:8080/rest/object1> <http://myurl.orgpackage> "ppp" WHERE {}

versus:

INSERT <http://localhost:8080/rest/object1> <http://myurl.org/package> "ppp" WHERE {}

I think one way around this grammar issue would be updating the FedoraLdp code (in this case the patch method) to do a regex check/substitution for urls without a terminating slash.

Osman Din, 2015-03-17 23:27 UTC

The issue is in this specific utility method we're indirectly relying on in PropertyConverter (and likely not with other namespace population logic, in whatever package or method or classes that resides in Jena).

The specific lines are 70-72. It looks for a terminating character (working backwards), and the first slash it can find backwards in “http://myurl.org” is “http://“. When PropertyConverter asks for a namespace to lookup/register in JCR, it gets "http://", and registers “http://“ (as opposed to getting "http://myurl.org").

Looking at the method’s Javadoc, it seems that the method is correct technically, but its usage is broken as far as PropetryConverter is concerned. Currently, I'm not familiar with their API or the source code to guess what a patch would look like if necessary. This method is called by other Jena methods as well.
