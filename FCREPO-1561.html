Description

Large literals (4096 characters or greater) can be created, but cannot be deleted.

  • In addition to not deleting the large literal, no error is raised.
    See https://github.com/fcrepo4/fcrepo4/issues/787

If there is a bug that prevents deleting large literals, it would be great to fix it. However, it is quite likely that there is a hard limit, in which case determining and documenting that limit would be adequate for this ticket.

Finding the limit of both the size of literals that can be created, and the size of literals that can be deleted would be helpful.
A note added here could be useful:
https://wiki.duraspace.org/display/FEDORA4x/RESTful+HTTP+API+-+Containers#RESTfulHTTPAPI-Containers-GreenPATCHModifythetriplesassociatedwitharesourcewithSPARQL-Update

Bethany Seeger, 2015-09-18 18:48 UTC

Andrew Woods,

I wasn't seeing an exception, so I dug deeper.

ModeShape is storing the string in the binaryStore and now calling it a binary and the fedora code is not prepared for that switch. This is expected ModeShape behavior, from what I've read - strings larger then the minimumBinarySizeInBytes will be stored that way. The (one?) flaw in the fedora code is around line 207 in NodePropertiesTools.java - in the removeNodeProperty. 

                final Value[] newValues = stream(node.getProperty(propertyName).getValues()).filter(v -> {
                    LOGGER.debug("v is {}", v);
                    if (v.equals(valueToRemove)) {
                        LOGGER.debug("Found value, removing!");
                        remove.set(true);
                        return false;
                    }
                    LOGGER.debug("Didn't find value, not removing");
                    return true;
                }).toArray(Value[]::new);

It's not prepared to receive a binary reference back, so it fails to match the string (v, in this scenario, is a binary type and valueToRemove is a string). It's a silent fail - though I can see it clearly with my debug statements added in.

ModeShape has another config var we can put in repository.json (under "binaryStorage") called:


"minimumStringSize" : {
                                    "type" : "integer",
                                    "description" : "The size threshold that dictates whether string values should be stored in the binary store. String values shorter than this length are stored with the node, whereas strings with a length equal to or greater than this limit will be stored separately from the node and in the binary store, keyed by the SHA-1 hash of the value. This is a space and performance optimization that stores each unique large value only once. The default value is to match the 'minimumBinarySizeInBytes' value."
                                },

If we want to allow for larger string literals that do not automatically get put in binaryStorage, we can. But that really doesn't solve the problem.

So, long winded answer, but it's around that code in NodePropertiesTools.java that the flawed assumption is.

Fix or document is the question...? Guess it's always been the question.

-Bethany

Andrew Woods, 2015-10-19 12:40 UTC

The reason that your test is not demonstrating the issue is almost certainly due to the fact that the test repository.json is creating a "transient" binary store... vs. type "file". A transient store is in-memory and therefore does not exhibit the same characteristics as a filestore, that your PR addresses. The reason the tests use a transient store is because it is faster... and the tests run faster. Once you have verified that your test demonstrates the issue (by changing the repository.json config), it would be helpful if you could time the difference between a test transient and file store. If the file store takes significantly longer to run:
mvn clean install -pl fcrepo-kernel-modeshape/

...then you should probably create a new repository.json that is referenced just by the FedoraResourceImplIT.java test. see:
https://github.com/fcrepo4/fcrepo4/blob/master/fcrepo-kernel-modeshape/src/test/java/org/fcrepo/integration/kernel/modeshape/FedoraResourceImplIT.java#L116
