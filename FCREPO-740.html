Description

Currently the request context resources are built from (a) the PID (and dsID) of the object and (b) the same with all parents.

According to the XACML 2.0 spec, multiple parent lineages should be included, ie if a resource test:res is a member of test:col1 and test:col2, then we should be generating

  • test:res
  • test:col1/test:res
  • test:col2/test:res

Currently only a single parent lineage is calculated (using the first parent relationship discovered in the relationships).

This would allow resources to be members of multiple collections, and to use policies from all parent collections.

Stephen Bayliss, 2010-12-03 23:43 UTC

Correction: FeSL is using XACML 2 (schema at least, but an "interim" build of the Sun engine post 1.0).

The issues are likely to be how the policy combining algorithms work.

FeSL currently uses the hierarchical resource profile specified in XACML 2.0, and has hierarchical policy combining algorithms, but it's not known how (if) these will work with multiple hierarchies.

The other "standard" combining algorithms should be fine. However the hierarchical ones are probably the most useful (if we can figure out how they should work in this scenario, and then make them work).

Currently we have (eg for hierarchical-deny-overrides
/coll1/coll2/res1:

Policy at coll1 level is overriden by policy at coll2 level etc, with multiple policies on the same level treated as "deny overrides".

What should happen if we have
/coll1/coll2/res1:
/collA/res1:

with policies applied for all collections. Does the "level" at which the policy applies even make any sense over two hierarchies? It would seem that if we could combine policies independently down the two hierarchies, and then apply a simple "deny overrides" (eg) to combine the two resulting policies that would make sense?
