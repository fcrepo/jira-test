Description

It would be helpful to have a standard way to use the Camel Toolbox to facilitate messaging between Fedora and arbitrary third-party microservices/APIs.

For example: my use case is that whenever an object is added or modified in Fedora, I would like to POST the object's identifier to a web service that handles indexing. (My indexing process is quite complex and depends on other parts of my non-Java-based codebase, and so it makes more sense to handle it as an external microservice rather than trying to directly incorporate the whole indexing process into the Camel Toolbox).

It seems that it may be possible to create a configurable service in the toolbox which could meet my use case while also being flexible enough to support a significant number of other possible use cases. For example, if we could configure which types of actions trigger a message, the target URL, the HTTP method to use, and the payload (which could potentially be GET and/or POST parameters, or a message body).

I have full control over the nature of my own web service, so I can tailor the code I build to suit whatever implementation is easiest on the Camel Toolbox side – thus, I do not demand all this flexibility... but it might be helpful to others if easy to implement. I would be perfectly happy to start with a minimum viable product that is designed to be extensible in case of future need.

If others feel this is a good idea and would like to discuss a path forward, I am willing to lead an initial implementation, on the understanding that I'm unfamiliar with the platform and might need a little hand-holding to get things underway.

This topic was discussed on the August 12, 2021 Fedora Tech call.

This was discussed during the August 26 Fedora Tech Meeting (see https://wiki.lyrasis.org/display/FF/2021-08-26-+Fedora+Tech+Meeting for full notes).

We agreed upon a minimum viable product that creates a thin route that uses the existing http service to POST messages to a configured API endpoint, with the option of basic authentication.

Some additional “nice to haves” include the ability to include configured arbitrary HTTP headers in the POST, the ability to filter which messages are passed along (perhaps using a simple substring match rule), and perhaps a JSON configuration file for managing these details (which in the future could be expanded to support messaging to multiple endpoints, etc., etc.).
