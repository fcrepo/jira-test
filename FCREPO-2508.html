Bethany Seeger, 2017-06-20 15:01 UTC

Andrew Woods - I was thinking of using the strings in POSSIBLE_RDF_RESPONSE_VARIANTS_STRING list to determine what is a valid RDF format, and therefore a container versus binary. 

However, it doesn't include 'application/n3' (contentTypeN3Alt1) , which is (or was?) an accepted mime type.  So, when I've made my changes, tests that use 'application/n3' as the mime type now fail.  I can either change the tests, or add that content type to the POSSIBLE_RDF_RESPONSE_VARIANTS_STRING.  I'm wondering why contentTypeN3Alt1 wasn't in there in the first place and the history of POSSIBLE_RDF_RESPONSE_VARIANTS_STRING? I was trying to use that to prevent having the code have to be explicit about what it cannot accept, however, maybe being explicit is the way to go.  

I realize that POSSIBLE_RDF_RESPONSE_VARIANTS_STRING list might not be the best thing to use, since it's probably for the 'Accept' header.  My goal is to make sure we don't have to have these exceptions listed everywhere ('text/plain', 'text/csv') in the code, but rather in one spot. 

Andrew Woods, 2017-06-20 15:20 UTC

It looks like POSSIBLE_RDF_RESPONSE_VARIANTS_STRING is currently only used in integration-test code.

Using a constant for defining the allowable mime-types would be good... but I do not believe the Jersey machinery allows for an array of constants in the "@Produces" annotation.

As for the history of removing 'contentTypeN3Alt1'... that goes back a long way: https://www.pivotaltracker.com/n/projects/684825/stories/64775424

My guess is that the underlying RDF generation machinery did not allow for "application/n3"... that may have since changed.

Bethany Seeger, 2017-06-20 18:15 UTC

In looking at this more...

Jena now allows 'application/n3' for a valid RDF type, though it's not technically a mime type (yet). So, some of the tests use that mime type when creating resources (versus accessing them, which would fail since the 'application/n3' is not in the @Produces list). When I limited the type checking to just that POSSIBLE_RDF_RESPONSE_VARIANTS_STRING list, the tests started failing, because Jena (used in former logic) was far more lenient. 

I will change the logic I created to not use the POSSIBLE_RDF_RESPONSE_VARIANTS_STRING. 

I would like to change the test code to use the IANA accepted mime type of 'text/n3'.  Do you have any objection to me changing that?

Esmé Cowles, 2017-06-20 18:18 UTC
