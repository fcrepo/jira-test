Description

The JMS events emitted by Fedora should not contain the list of changed properties. These are not used by any of the camel machinery and they are particularly troublesome in the context of ldp membership and containment (which are not currently included in JMS events anyway). Removing them will save a lot of work.

Unknown, 2016-03-11 13:57 UTC

The difference is that in the indexing context, a DELETE event simply removes all trace of that resource in the external index, which doesn't require any interaction with the repository. For audit, however, the camel route is recording that a DELETE event happened, and if the fedora:hasContent property exists in the properties header (as it does for any fedora:Binary resource – whether the binary itself changes or the metadata describing that binary). If the fedora:hasContent property is present, then the premis:hasEventType is set as http://fedora.info/definitions/v4/audit#contentRemoval; otherwise, the premis:hasEventType is http://id.loc.gov/vocabulary/preservation/eventType/del.

In some ways, though, this is orthogonal to the discussion of properties, since the only value in question is fedora:hasContent, which is specially added to any fedora:Binary, regardless of the properties that may or may not be changed. In fact, I would assert that fedora:hasContent is not a property like any of the other values packed into that header. It is certainly not one that has been changed.

If we need to retain this sort of functionality for the audit stream, I think a better solution would be to not publish properties at all but rather publish whether the object is a Container or a Binary, along the lines of the HTTP Link headers that are currently published for every resource.

Unknown, 2016-03-18 01:00 UTC

OK, I have a much better approach: take a look at this function: https://git.io/vaocq

By casting to a org.modeshape.jcr.api.observation.Event, you can call getMixinTypes() on the Event, which will include any RDF type added to the resource (I have confirmed this via logging statements). This will not include the LDP types, but those are dynamically added based on the Fedora types anyway and aren't part of the FedoraResource::getTypes response (a bug?). See: https://git.io/vaocw

Specifically, with this addition to the DefaultFilter:

         try {
             final org.modeshape.jcr.api.observation.Event modeEvent =
                     (org.modeshape.jcr.api.observation.Event) event;
+            // ----------------------------------------------
+            LOGGER.info("Event Type: {}", modeEvent.getType());
+            LOGGER.info("Event Path: {}", modeEvent.getPath());
+            LOGGER.info("Primary Type: {}", modeEvent.getPrimaryNodeType().toString());
+            stream(modeEvent.getMixinNodeTypes()).map(NodeType::toString).forEach(type ->
+                    LOGGER.info("Mixin Type: {}", type));
+            // ----------------------------------------------
+
             return concat(of(modeEvent.getPrimaryNodeType()), stream(modeEvent.getMixinNodeTypes()))
                 .map(NodeType::toString);
         } catch (final ClassCastException e) {
