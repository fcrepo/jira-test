FCREPO-3150 Create datastream index only for datastreams in migrated objects

ReporterScott Prater

Updated2020-01-06 04:11 UTC

Componentsf4-migration

Description

The migration-utils process currently creates a datastream index for all the datastreams in a Fedora 3 repository, regardless of the number of objects that will actually be migrated (as specified in the PID list).

This can result in unnecessary processing time, especially for large repositories where only a small subset of objects will be migrated.

Proposed solution:  if a list of PIDs to be migrated is specified, only create a datastream index for the datastreams in the objects identified by those PIDs.

Comments (2)

Scott Prater, 2019-12-20 21:17 UTC

I looked more into this, and I realized that creating an index for a single datastream in a way that does not index all datastreams is not a trivial task, given that the filesystem layout for any particular Fedora instance can vary:  it can be legacy or Akubra, and within Akubra, it can be split into any combination of n-tuples, with varying depths.  In short, in order to calculate the filesystem path for a datastream object in Fedora, we need to know what storage provider Fedora is using, and how it is configured – which means reading and interpreting the Fedora configuration itself.  To do this, we would need to introduce a dependency on the Fedora configurations, as well as duplicate path calculation algorithms implemented in the Fedora and Akubra codebase.

This strikes me as an unacceptable approach.  I recommend closing this ticket as "Won't fix", and recommending that organizations with large repositories create the datastream index once, then re-use it. 

Unfortunately, every time there is a change to their repository, their datastream index will need to be wiped and recreated; perhaps there might be a less onerous approach to updating an existing datastream index (but that's another ticket).

Andrew Woods, 2019-12-22 01:02 UTC

I will need to investigate the implications... but it also may be possible to skip the creation of the index in the case that a PID-list is provided by the user. It would be slower without the index, but with a small PID-list, not as slow as re-creating the index.
