Osman Din, 2015-09-22 15:38 UTC

It’s a bug only if Fedora is making a guarantee that even when there are long running ingests, it will work within a specific heap range.

The OOM stacktrace is really a warning by the JVM that the code is inefficient for three things: (a) a memory setting; (b) a data set (I used the ticket’s 6K RDF file, I’m assuming that’s a representative sample); (c) a particular system (I tested it on a desktop Windows machine with Tomcat 8 on a standard electro-mechanical disk).

After successfully running various tests for 160 hours and ingesting, without restart, about 350K items (using Andrew’s command and data) and finding out that the heap usage actually decreases with time, I’m not sure if the ticket (and the experience) should be classified as a bug.

I ran the ingest on a Windows desktop machine (the defaults on my machine are: Java 8 Hotspot Server VM, 4-8GB memory (it used around 3 GB), parallel garbage collector) and did not run into any relevant issues. Initially, the heap usage was a bit high but it settled down to about 1.7 GB. The ratio of GC activity was pretty reasonable throughout my tests, hence there was little possibility of a GC Out of Memory error. I can share a screenshot, if somebody is interested.

The JVM documentation says the following:

Both parallel and collector will “ will throw an OutOfMemoryError if too much time is being spent in garbage collection: if more than 98% of the total time is spent in garbage collection and less than 2% of the heap is recovered, an OutOfMemoryError will be thrown”.

Of course, we could look at the source code to make Fedora use less heap and thus make it spend less time garbage collecting, but I think a different ticket regarding performance-tuning should be created as there is no guarantee that users would not see this stack trace even when the modifications have been made (let’s suppose they want to run a long, heavy ingest on a 128 MB machine).

I do recognize that there’s possibly an issue here. But I think this issue is only a symptom, and specific effort should be planned to get rid of the underlying problem.

In parallel to any performance-tuning efforts, it might be a good idea for the customer (or the Fedora developers) to profile the application before selecting (or recommending) a particular hardware, JVM, memory heap setting. It’s not a consumer application, after all.

Andrew Woods, 2015-09-29 16:43 UTC

I believe your analysis is correct, Osman Din. I would add that if anyone runs into this issue in the future, debugging and tuning can be facilitated by adding the following JAVA_OPTS, then reproducing the error.

JAVA_OPTS="${JAVA_OPTS} -Xloggc:/tmp/java-gc.log -XX:+PrintGCDetails -XX:+PrintGCDateStamps"

The "java-gc.log" (or whatever you wish to name it) will contain memory management details that can be easily visualized with:
https://github.com/chewiebug/GCViewer

Osman Din, 2015-11-18 19:03 UTC

The reason is that although the memory you are passing it exceeds the physical memory on the machine, it's going to write the memory pages to disk, causing performance issues and ultimately OOM warnings. From the output, it's not clear to me if the other process is consuming 10.5 or 6.5 GB of virtual memory. It seems like this process could be preventing F4 from the 3-4 GB it needs (for a certain duration of time at least).
