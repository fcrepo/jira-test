Description

Sparql Delete requests which do not specify an exact object/literal to delete are having inconsistent results depending on if the subject having its properties deleted was created inside of the current transaction or not.

The query in question is:

DELETE

{ <> <http://purl.org/dc/elements/1.1/relation> ?obj . }

WHERE

{ <> <http://purl.org/dc/elements/1.1/relation> ?obj }

This query should delete every property dc:relation from the object the request is made against. However, I've run into it working differently in the following cases:
1) No TX involved -> dc:relations deleted
2) Subject and Object created out of TX, delete query in TX -> dc:relations deleted
3) Subject created in TX, object out of TX -> nothing deleted, no error
4) Subject created out of TX, object created in TX -> dc:relations deleted
5) Subject and object created in TX -> nothing deleted, no error

Attached is a script (run against the one click installer) which illustrates the bug.

I know this seems very edge case-y, but we really are running into it. The approach that seems to work consistently in transactions is to retrieve all the existing values and then generate a delete query from that, but it can produce some rather large queries and takes 2 requests.
