Description

From Asger Blekinge-Rasmussen:

(In a discussion at OR'09) we came up with a total redesign of the fedora install procedure. Here goes, from memory:

1. Fedora is just a .war file. There is no installer. (Distribution includes the Fedora WAR and Fedora.fcfg file.)
2. You install said war file in a tomcat. (Renaming the WAR file as necessary to indicate the preferred context name)
3. Upon init of the war file, fedora reads /fedora/fedora.fcfg, or another location specified in the war file's web.xml (or specified by command line or environment variable)
4. This config file specifies, among all the things it already does, the Fedora Home dir.
5. If this dir does not exist, it is created and populated with the nessesary stuff from the war file.

The purpose of the current installer is primarily to set up the web.xml. That settings have to be set up in the web.xml is unfortunate, but unavoidable. (The installer also creates and moves files to fedora home, but this can be done during WAR startup.)

The features that are set up, again from memory:
1. SSL endpoints
2. Other endpoints
3. Servlet filters for Authentication

As far as we could establish, the SSL endpoints are somewhat odd, since people would probably use the tomcat in SSL, rather that the specific web application.

The other endpoints, we envisage, are default enabled. The fedora.fcfg specify which class should handle requests for each endpoint, and thus certain endpoints could have stub implementations per default.

Preferences which were used to set up the servlet filters in the installer could be added to fedora.fcfg then read by a single filter which is always available.

Chris Wilper, 2009-06-16 17:10 UTC

Description from FCREPO-501 Closed (dupe of this issue):

Based on a discussion BillB, ChrisW, TimD, Asger, and others had at OR09:

Move toward having a war file for Fedora that doesn' t need to be modified.

1) Make AuthN stuff plug in via an always-configured servlet filter that delegates to what's configured
2) Don't use Tomcat for SSL (recommend Apache for this)
3) Make "fedora home" conventionally at /fedora (and don't include it in the war by default)

There was also some discussion that needs to be further rationalized re: running multiple Fedoras in one Tomcat. A couple ways to go:

a) require that people edit the war file in these cases (to point to a different fedora.fcfg)
b) have a convention where it's stored in /fedora/config/fedora-context.fcfg

Looking at this again, I like a) because it seems to be needed anyway if people need to install in a dir that isn't /fedora (e.g. /usr/local, or whatever convention their sysadmin uses)

Chris Wilper, 2010-03-01 09:36 UTC

I was just doing a test installation of Nexus (the maven repository), and realized the pattern they've used could be followed for doing this with Fedora. Since Nexus is a repository of sorts, it clearly needs to have local storage, but allows simple installation as a standalone WAR.

Here is how Nexus does it, in a nutshell:

You can install it simply by deploying it as a war in your favorite webapp container. By default, it will store persistent data in $

{user.home}

/sonatype-work/nexus. But if you've defined a system property or environment variable, it will use that instead. Lastly, it allows you to edit a properties file in WEB-INF directory to specify it. If the directory doesn't exist in any case, it is automatically created.

Anytime you want to change the directory, you can stop the webapp, move the directory, change where the configuration points, then restart.

Aaron Birkland, 2011-07-26 18:49 UTC

Final scope of this issue: remove all customization/configuration from fedora war, and place in FEDORA_HOME. This allows the use of a single generic war file for a given fedora distribution. The installer now merely copies this war file into the webapp container of choice and builds a custom FEDORA_HOME based on installer input. Minor bugfixes can be deployed by merely dropping in a new war file.
