FCREPO-1361 Triples about non-repository subject URIs are silently ignored

Description

If a SPARQL update tries to insert triples about non-repository URIs, those triples are silently ignored. E.g.:

PID=$RANDOM
curl -X PUT http://localhost:8080/fcrepo4/rest/$PID && echo
echo "insert data

{ <http://example.org/foo> <http://example.org/bar> \"baz\" . }

" | \
curl D -s -X PATCH --upload-file - http://localhost:8080/fcrepo4/rest/$PID

Does not add the triple to the repository, and returns 204 No Content response indicating successful completion of the PATCH operation. Should it return an error instead?

Former user, 2015-03-10 11:33 UTC

Aaron Birkland, all of the properties in the repo are attached to repository paths, which are mapped to repository-managed URIs when they are transformed to/from RDF. So if we are going to store triples about subjects that don't map to repository paths, it may make sense to make blank nodes for them (with owl:sameAs properties to map them back to their original subjects). There may be other options for how to handle these. For example, we could serialize the triples and store them in the value of a property. That would require creating new machinery to work with, but might be closer to how we think they should be treated than the blank node approach.

For me, the key question is: if I post triples about the same external URI to two separate repository paths, do I expect those to map to the same internal structure (updating one updates the other, etc.), or do I expect them to be kept separate? Merging them seems more convenient if the purpose is to cache external triples (e.g., labels for external URIs that are referenced). But keeping them separate might be better if the purpose is maintaining provenance of third-party data that is being merged.

Andrew Woods, 2015-03-10 15:16 UTC

Aaron Birkland, currently F4 is built to take the resource on which properties are associated as the subject of those properties (or of those triples, rather). In your case, where you wish to ingest an RDF document that has a subject other than the current repository resource, and then to use F4's machinery to manage/update those RDF statements would involve a deep shift in how F4 works. If these RDF documents were ingested as F4 named graph resources, that may be better aligned with the existing F4 model. However, named graphs are not currently supported in F4, and doing so would benefit from some on-list discussion.
