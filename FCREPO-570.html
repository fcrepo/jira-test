Description

The SOAP API contains methods for manipulating relationships in RELS EXT.

These could either be extended, or new methods created, for relationships in RELS-INT.

Chris Wilper, 2009-11-11 10:14 UTC

Looking at the signatures for the relationship methods today, they take PIDs as the first parameter, but the datatype is String. For example:

https://fedora-commons.org/confluence/display/FCR30/API-M#API-M-addRelationship

So it strikes me that it would be possible to extend the existing methods to do this, and still have it be backward compatible. The first parameter could be defined to accept a PID or subjectURI (object or datastream info: URI).

Stephen Bayliss, 2009-11-11 11:17 UTC

Good spot Chris.

We should (1) maintain consistency with other API method parameters and (2) be mindful of a future where these methods may possibly be used to operate on arbitrary relationships.

So for subject parameter, currently the PID, we could have the following syntax options
(1) pid (eg changeme:1234) - keep for backwards compatibility
(2) pid/dsID (eg change:1234/DC) - however I note that all other API calls have separate parameters for pid and dsID, so this seems inconsistent, my preference would be not to allow this
(3) Subject URI, eg info:fedora/changeme:1234 , a PID URI for RELS-EXT operations and info:fedora/changeme:1234/DC, a datastream URI for RELS-INT operations

Option (3) is then flexible-enough for an arbitrary URI subject in case operations on arbitrary relationships are introduced in the future. So for asserting RELS-EXT relationships we would allow both the forms changeme:1234 and info:fedora/changeme:1234; and for RELS-INT only the URI form info:fedora/changeme:1234/DC would be acceptable.

On the face of it, it seems distinguishing between a pid (1) and a URI (3) should be fairly simple, however looking at the specification for URI syntax, a Fedora PID of eg changeme:1234 does in fact conform to generic URI syntax.

This means that in a future "arbitrary relationships" scenario, subject URIs which conform to PID syntax would be incorrectly interpreted as PIDs rather than URIs, and result in incorrect triples being created. (Although it seems to me that in practice this form of URI occurring is unlikely).

I'd be happy to take on implementing (1) + (3) for the moment if there is consensus.

This could mean that at some point in the future we might need to first deprecate the (1) syntax, and then remove it altogether. Which begs the question as to whether we should deprecate syntax (1) now.

Chris Wilper, 2009-11-12 14:22 UTC

Good point on distinguishing between PID and URI. I think it would be best to mark as deprecated the ability to accept a PID as the first arg (that is, allow it to still work for at least one release, then fully get rid of it in a future release).

Since for now, the first arg is either going to be a PID for an object URI, there shouldn't be trouble syntactically distinguishing:

  • if it doesn't start with "info:/fedora/", it's a PID
  • if it does, and has 2 slashes total, it's an objectURI
  • if it does, and has 3 slashes total, it's a datastreamURI
