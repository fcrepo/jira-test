Comments (6)

Bethany Seeger, 2016-09-09 14:49 UTC

As far as what gets included in the log, I would find it valuable to know the total number of objects exported. A list of overall objects exported would be nice as well, but when the numbers are large, having the total number of exported objects will be a nice, quick sanity check.

Also, any data on resources that failed to export and why.

Having a full list of resources could be handy to compare to the log that gets generated on import. That would imply keeping the format somewhat similar for the export/import logs. (I realize order is unpredictable, perhaps, so it would need to be sorted by the user before comparison)

Nick Ruest, 2016-10-28 18:41 UTC

See @awoods' comment here for a proposed format of the log.

Jared Whiklo, 2016-12-05 17:54 UTC

So just digging into this now and I have a couple questions/confirmations (these also relate/apply to FCREPO-2169 Closed ).

  1. I am assuming this would be a separate log from the application logging.
  2. That this would be some plain text file saved to the filesystem.
    1. Is this file name configurable (as a config option) or is a date/time stamped filename acceptable (ie importexport_20161205T114400.log).
    2. Is the location configurable, or should it be saved to the temporary directory like the configuration file is saved to.
  3. That this would output a line for every item exported (or imported in FCREPO-2169 Closed ) as well as a summary at the end of total resources export/imported and total failures.
Jared Whiklo, 2016-12-05 18:06 UTC

Or would it be acceptable to create use the existing log files and add a DEBUG level notice for each item imported/exported as well as an INFO level summary at the end?

Andrew Woods, 2016-12-06 05:00 UTC

Jared Whiklo,
1. Yes, a separate log file probably makes the most sense.
2(1). Date/time file name sounds good.
2(2). A configurable location, defaulting to either the temp-dir or the current-working-dir, would be good.
3. Yes, a line for each item. Summary of total resources may not be necessary since the output file lines can be counted, but if it is simple to include a count, that is fine. As for failures, maybe indicating on a given item line that it failed, with a reason if possible, may do the trick.
