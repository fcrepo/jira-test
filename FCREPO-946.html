Chris Wilper, 2011-07-01 07:28 UTC

So far, using strategically placed thread dumps, I've narrowed down the creation of pool-1-thread-1 to somewhere in the execution of FOXMLDODeserializer.deserialize. It exists after the first time that method is called from within Rebuild.addObject, and doesn't go away on its own. Hmm.

Chris Wilper, 2011-07-01 08:44 UTC

I've now narrowed it (the creation of pool-1-thread-1) down to somewhere in org.fcrepo.server.storage.RDFRelationshipReader#readRelationships. This is basically a thin wrapper around some calls to Trippi, which ultimately uses RIOTripleIterator to parse the stream of triples. RIOTripleIterator has historically used a separate thread to parse the triples. Looking at recent changes to Trippi, I see https://github.com/fcrepo/trippi/commit/62b0725f7abc1d7517566d8dfdbf763516d2f81c ...which switched to using a java.util.concurrent.ExecutorService (thread pool) instead of spinning up a thread itself. However, the EXECUTOR field is final static, and only typed as an Executor, which doesn't have a shutdown() method like ExecutorService does. Therefore, ExecutorService.shutdown() can never possibly be called.

Now I'm pretty sure this is the cause, because the javadoc for Executors.newCachedThreadPool()[1] says:

"Threads that have not been used for sixty seconds are terminated and removed from the cache."

[1] http://download.oracle.com/javase/6/docs/api/java/util/concurrent/Executors.html#newCachedThreadPool%28%29

Chris Wilper, 2011-07-01 10:48 UTC

Attached demo maven project to reproduce the hang by calling Trippi's TripleIterator.fromStream method, when RIOTripleIterator is used. See README in zip file for instructions.

Chris Wilper, 2011-07-01 16:57 UTC

Fixed in Trippi 1.5.2 by moving back to a thread-per-parse model. See https://github.com/fcrepo/trippi/commit/4ef40ea22b4a6b359de73c4b4d8b5a9fe432a594

If you change the trippi version to 1.5.2 in the attached project's pom, you'll see that it exits immediately now.
