Description

David Novák reported on Slack:

We experience some strange and inconsistent behaviour while evaluating effective authorization for specific container. In our set up, the default ACL is set for the info:fedora/AMCR/record (see image in first reply), which should handle all child containers. It seems to be properly propagated in the index tables (containment, ocfl_id_map, reference; see images in first reply).However, when we I tried to update info:fedora/AMCR/record/P-1223-000360/metadata record using AMCR account, Fedora rejected to authorise the PUT operation (code 403), despite the user should have inherited write permissions. It is well visible in the attached log file.The strangest thing is that at the same time, authorization worked for other containers well. What helped was restarting Fedora (without reindexing).It was not the first time this happened. It is extremely difficult to reproduce, as it is unpredictable. But when it happens, it is full blocker.Did some of you ever experienced something similar? Is there any known solution or the way how to avoid this?So far, we experienced this just in the test environment, but I am afraid it can happened even in production, which would be big issue for us.

Dan Field, 2026-01-28 17:01 UTC

This may be due to WebACRolesProvider using Optional on ACLHandle allowing for cache poisening. This would allow for an empty ACL to be stored if getEffectiveAcl() ever encountered a transient issue during processing. On restart, the cache would be purged and requests would use a new working ACL fetch which would fix the issue for the user going forward.

David Novák, 2026-01-28 18:35 UTC

We may have find out a way to reproduce it, as it break for records where we previously call info:fedora/AMCR/record/P-1223-000360/metadata/fcr:versions with the same account. This leads to fail of the next PUT operation on the info:fedora/AMCR/record/P-1223-000360/metadata (just to note: info:fedora/AMCR/record/P-1223-000360 is an archival group). After some time it somehow unlocks itself and the operation passes.

David Novák, 2026-01-28 19:55 UTC

I can confirm that it is cache-related issue. Setting:

fcrepo.cache.webac.acl.size.entries=0
fcrepo.cache.webac.acl.timeout.minutes=0

as previously suggested is a confirmed workaround which prevents it from happening.

EDIT:

Our programmer’s guess what is happening:

  • When reading the container versions without a transaction (i.e., read-only), the rights are cached.
  • When writing, the rights are taken from the cache, regardless of whether there are different rights for the transaction.
David Novák, 2026-02-01 13:13 UTC

Further info form Jan Havrlant, our programmer:

I analyzed the error and I see two problems.

In the getRoles( https://github.com/fcrepo/fcrepo/blob/80b52f906b695784e92e9b3c6a7b54bea2567082/fcrepo-auth-webac/src/main/java/org/fcrepo/auth/webac/WebACRolesProvider.java#L154 ) function, caching occurs using a key that does not contain fcr:versions, see the getResourceId(https://github.com/fcrepo/fcrepo/blob/b05ed9400b0d4dc7943beb5f05a36500a820adb8/fcrepo-kernel-api/src/main/java/org/fcrepo/kernel/api/identifiers/FedoraId.java#L215 ) function.

Furthermore, the getEffectiveAcl (https://github.com/fcrepo/fcrepo/blob/80b52f906b695784e92e9b3c6a7b54bea2567082/fcrepo-auth-webac/src/main/java/org/fcrepo/auth/webac/WebACRolesProvider.java#L451 ) function cannot find the ACL correctly, it is probably necessary to define a getDescribedResource method for the TimeMapImpl class similar to here( https://github.com/fcrepo/fcrepo/blob/e06850a38a9e3a2cfd2527b2eb7ef6b2019f17d6/fcrepo-kernel-impl/src/main/java/org/fcrepo/kernel/impl/models/NonRdfSourceDescriptionImpl.java#L61 ), now it returns itself and not the parent object.
