FCREPO-176 Lockup after frequent dissemination requests

TypeBug
StatusClosed

AssigneeChris Wilper

Description

When making many back-to-back requests for the same dissemination, the Fedora server becomes unresponsive to similar dissemination requests. When this state is reached, the server does not recover until it is restarted.

This problem has been reproduced consistently with the following instructions (and ZIP attachment) provided by Anoop Kumar:

In order to replicate the behavior, you need to ingest all three objects
in the zip file and change the hosts file/ or add the spoofs in hosts
file that are provided in zip package. Once the object is in repository
you need to find the object by searching for its id
tufts:UA069.001.DO.MS008. and call the disseminator getChunckList by
setting parameter to true. Here is the url to access the object in
repository from fedoras root path
/fedora/get/tufts:UA069.001.DO.MS008/bdef:TuftsText/getChunkList?withBody=true
You can also access it on our test machine at
(http://vue-dl.tccs.tufts.edu:8080/fedora/get/tufts:UA069.001.DO.MS008/fedora-system:3/viewMethodIndex)

Once you see the dissemination click on the reload button of the browse
several times rapidly. It may take about 15-20 clicks or a little more
and then you will notice that the page doesn't reload anymore and the
browser keeps trying to load the page. This essentially crashes the
dissemination process and the disseminator cannot be loaded anymore. I
have included fedora server log at the bottom of this email. Once the
server freezes disseminating the only way out is to re-start the server.
We have been doing that for a month now.

Ross has found that upping WebClient's default "max connections per host" seems to alleviate the problem, but we haven't found why these connections aren't being released. It appears that threads are waiting in line for a connection to the host, but older connections aren't being released for some reason, so they wait indefinitely.
