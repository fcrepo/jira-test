FCREPO-1064 Include attributes for relationships API methods in FeSL - allow policies based on the relationship being manipulated

Affects versionsFedora 3.5
Depends onFCREPO-1063 FeSL does not support granular policies at the level of individual API methods

Description

the Relationships API methods (see purge relationship for an example) do not specify any attributes that identify the actual relationship being manipulated.

It would be useful to add these.

Then one could write policies to specifically control certain types of relationships (eg control who can add members to collections)

Chris Wilper, 2012-03-08 20:52 UTC

Are FeSL policy "actions" are currently 1-to-1 with REST or SOAP API operations? I can't recall. At any rate, it would be good to enforce relationship restrictions consistently or be very clear about people's ability to get around relationship API-oriented restrictions by just modifying the RELS-EXT datastream via modifyDatastream.

Stephen Bayliss, 2012-03-09 14:42 UTC

FeSL policy "actions" are not 1:1 with API methods currently, see FCREPO-1063 Closed - this is a limitation currently; actions are only at the basic "read/update/delete" level.

Yes consistency is important, as implementing policies around the relationships API methods could be circumvented by modifying RELS-* datastreams directly.

Options for this could be:

  • allow policies on relationships methods, but clearly document potential circumvention by direct modification of RELS-* datastreams and that modification of these should be restricted so that relationships can only be modified by relationships API methods
  • somehow (not sure how!) make modification of RELS-* datastreams a "special case"; I guess the filters for datastream operations would have to test for the datastream ID and in these cases apply extra rules. Could be complex as it would entail doing some kind of triple diff based on the update, and testing the diff to determine if the add/purge of the relationship should be allowed.

Possibly a two-phase implementation - do the first option, raise a JIRA for the 2nd for the future?

Stephen Bayliss, 2012-03-09 14:44 UTC

Depends on this issue as policies will need to be able to test for the individual relationships API methods (as XACML actions); currently they can't as the individual methods are not exposed as actions in the PEP.
