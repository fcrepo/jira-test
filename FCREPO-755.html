Description

From Steve's recent message to the user list[1]: "Alternatives could include N3 and N-Triples, both of which tend to be more readable (and therefore potentially easier to author) than RDF/XML - possibly useful to those less experienced in creating RDF/XML.

This would not be possible with the current 3.3 release, as the RELS-* datastreams must be XML as they are "X" datastreams (N3 and N-Triples are not XML), but could be an option for 3.4 onwards now that we support M datastreams for RELS-*.

(Additionally, RDF/XML has limitations as to to what RDF can be serialized as RDF/XML.)"

Chris Wilper, 2010-08-06 19:53 UTC

I think it is a good move for us to keep the RDF parsing well contained so that most internal access to the relationships is via Java objects. Doing so would be a prerequisite for this change, but would have other benefits as well (more maintainable code being one).

A cleaner object model would certainly make this kind of feature easier to implement and maintain, but keep in mind that we already have the relations accessible as pure Java in the existing code. See DOReader.getRelationships(..), which returns a Set of objects representing the relationships. Could this be improved? Yes...in fact I think we should use the Sesame RIO interfaces rather than our own. For example, the relations returned by this method are currently org.fcrepo.server.storage.types.RelationshipTuple objects, but I'd much prefer if they were RIO Statement objects: http://www.openrdf.org/doc/rio/api/org/openrdf/model/Statement.html

If we used the RIO abstractions, serializing and deserializing to/from the various RDF formats would be easy. See RIO's Parser interface: http://www.openrdf.org/doc/rio/api/org/openrdf/rio/Parser.html (note how you can set a StatementHandler, which listens for Statement objects encountered while processing the stream).

Daniel Davis, 2010-10-06 22:20 UTC

Even though the requirements described in this issue are needed to support known use cases. I suggest this issue be closed and reformulated to meet the goals described using other features, extensions or tools. A major aspect of the RELS-EXT/INT implementation is to provide a standards-based implementation of a datastream containing RDF. It is purposely limited in its expressiveness to provide a specified level of interoperatibility already recognizing that RDF/XML still gives it a powerful degree of extensibility. RDF/XML was selected because it is the only W3C standard for expressing RDF. There is also a general desire to limit the expansion of the Fedora API where built-in extension points can be used or added, which is likely in this case. There is always going to be this tension between interoperability and extensibility that must be considered for this issue.

The RELS-EXT datastream is part of the default content model in Fedora 3.x (which uses an extension point of the core Fedora information model for its implementation). This avoids over specifying or over-generalizing the features of Fedora's current release. Implementations are free to add datastreams which can contain the RDF format of their choice and which is needed to express statements that the constraints of RELS-EXT or RDF/XML cannot. The contents of these added datastreams can be produced by tooling external to the Fedora core and disseminated by applications or custom services. In general, it is a goal of Fedora and Fedora Create to produce and share tooling for creating and using Fedora Digital Objects and content.

However, Fedora does not provide some easy-to-use generic, extensible functionality that is implied by this issue. For example, it is high desirable to be able to create graphs by merging two or more datastreams containing RDF, possibly in different formats. Fedora's datastream orientation is consistent with the W3C specification of the semantic web in that datastreams contain serializations of RDF messages (representations). In many cases, an RDF representation must be retrieved to be used by suitable code for interpretation. Tooling, applications, services, and the use of JMS notification can be employed in the current version of Fedora for help retrieve/update the representation, but this can likely be done much better through the additional features, some of which are already described in JIRA.

In particular, it would be useful to combine RDF into the Fedora-supplied RDF database (triplestore). I suggest considering adding features to facilitate this in the High Level Storage initiative. We have also suggested that implementing "writable" services (formerly known as disseminators) could simplify update of individual objects. Improved shared, open-source libraries to simplify creating and modifying digital objects is clearly missing from Fedora-related offerings even though many of our users have created just such libraries. Also, validation and policy features need to be considered. Please do not take this comment to pre-suppose exactly how this functionality should be designed and implemented but instead as a few thought exercises.

I suggest we take this up as one or more projects leading to a series of well-scoped JIRA features that can be added to Fedora or its associated framework over time. This issue illuminates additions to Fedora that can enormously increase its functionality, decrease its complexity, and enable architectures that are more than the sum of their parts.
