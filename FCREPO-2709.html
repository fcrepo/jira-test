Description

Allow for creation of historical mementos of binary descriptions using the body and datetime in the request. Server must honor most server managed triples provided in the request body.

If the body of the request does not contain necessary server managed triples, request should return with 4xx status.

I’m still trying to work through the implications and options for how a binary description memento should behave given the design of versioning binaries and descriptions separately. I had some questions/observations that I was hoping to get thoughts on regarding how description binary memento should differ from the original:

  • binary is versioned separately, implying that the description does not need to contain a binary

        1) store an empty binary,

        3) create memento of binary at same time as description
  • should not return etag or last modified header, as these values refer to the binary for descriptions
  • should it include a "describes" link?  Would it reference the original?

Danny Bernstein, 2018-03-20 17:41 UTC

Ben Pennell:  Regarding the describes link,  I think that it can't reference the original,  because once the original changes, the description would no longer would describe the original resource, but a historical version of that resource.  Therefore it seems a memento of the binary should be created at the same time and linked via the describes header.  If this is the case then the etag of the newly versioned binary comes from the associated versioned description.  I think the subject of the triples in the description memento should be the newly created binary memento. 

However doesn't creating the memento of the binary at the same time as the description pose a problem for the import use case?

Ben Pennell, 2018-03-20 18:35 UTC

Danny Bernstein Mainly creating the description and binary mementos at the same time runs into problems with only being able to provide the content for one at a time. Updating the RDF of the LDP-RS describing the binary requires the body of the request, as does updating the binary itself.  Then after updating the description, you can no longer update the binary for the same memento since memento's are considered immutable by the specification.  We could create a multi-part request that updated both at once, but its not in the specification currently.

The tickets I created were based on creating binary and description in two requests, but that results in two disassociated LDPR's. Fedora could attempt to guess which description describes a binary memento (check for a memento with a matching memento-datetime), but there's always the possibility that it won't find anything. Judging by 5.2.3.12 from the LDP specification, it sounds like it is okay to have an LDP-NR without a LDP-RS, but we should attempt to link the two if they both exist.

So I agree it would be best to have the describes link go to a memento, but it gets messy in either direction.  Ahh, such fun.
