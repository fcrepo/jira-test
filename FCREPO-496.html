Description

Reported by Graham Triggs:

When repeatedly deploying/undeploying the Fedora webapp (without restarting Tomcat), the JVM permgen size continues to grow. This can lead to an eventual out-of-memory condition.

This is caused by a failure of classes to be unloaded.

Graham has seen this before, and has dealt with it by using a "cleanup context listener" that gets invoked at shutdown time. Part of this is due to JDBC drivers not being automatically unregistered when the webapp is stopped (this is what the attached java file deals with). Part also appears to be caused by a JAXP DocumentBuilderImpl reference that is being held by a ThreadLocal. This reference hasn't been tracked down fully yet.

While investigating this issue, Graham came across a flaw in the shutdown code that can prevent clean shutdown if ManagementModule doesn't shut down properly:

"...during the shutdown code, the ManagementModule hadn't been fully initialised, so it was then throwing an exception during shutdown (not an MSE), so all the remaining modules never had their shutdown code called (and so the Thread wasn't stopped, and Tomcat couldn't stop).

The local fix is to add a null check to ManagementModule's shutdown procedure:

public void shutdownModule() throws ModuleShutdownException {
if (invocationHandlers != null) {
for (AbstractInvocationHandler h : invocationHandlers)

{ h.close(); }

}
}

Thus preventing an NPE that can occur. Although the shutdown method in Server should probably be more defensive and catch Throwables (not just MSEs) to ensure that all remaining modules are at least attempted to be cleaned up."

Former user, 2009-07-13 14:45 UTC

After writing a ServletContextListener dedicated to cleaning up all the usual suspects (using the suggested fix above, jdbc driver deregistration, explicit shutdown of Log4j and commons logging) there are still classes left that prevent Fedora from being fully garbage collected while undeploying the application. The responsible libraries can be narrowed down to Xerces, Axis and Derby:

Xerces-J
Tomcat uses a sax parser for parsing the configuration files. As Xerces is included in Fedora's WEB-INF/lib directory, Tomcat apparently
uses parts of Xerces from Fedora rather than the one bundled with the JRE. This in turn creates a dependence of Tomcat on the Fedora classloader which can't be collected any more. The Tomcat documentation on class loading suggests otherwise[1] but following the tip at [2] and removing xerces.jar from Fedora solves the problem. A heap dump taken after the removal of Xerces from Fedora shows no signs of uncollected DocumentBuilderImpl instances or classes.

Axis
Most remaining shortest paths to the gc rootset appeared to be linked to Axis.
All Axis framework versions 1.3 and 1.4 suffer from a known class loader leak[3]. This leak
stems from a Cache that uses a ThreadLocal and fails to clean it up properly during shutdown. The issue hasn't been fixed. A cusom retrofitted fix
for 1.3 (the version used) along with some more tweaking of the ThreadLocal used for caching showed the successful removal of all Axis related classes.

Derby
Derby also seems to have some classloader leaks. After fixing Xerces and Axis related problems only classes from Derby appeard in the root set preventing the classloader from being collected. The Derby issues are significantly harder to trace down, but appear to be linked to Derby's ConcurrentCache.

Solution:
It appears that in order to fix all classloader leaks Xerces has to be removed, Axis patched or upgraded to 2.x and Derby probably has to be patched as well.
After fixing the Xerces and Axis related problems and substituting Derby with PostgreSQL the OOM does no longer occur. Heap dumps don't reveal any more classes that are not supposed to be loaded and JConsole shows the successful collection of PermGen after some time.

Method used:
In order to reproduce the issue the following steps were taken:
1. deploy fedora
2. check permgen
3. undeploy fedora
4. check permgen
5. trigger heap dump
6. analyze heap dump with Yourkit Profiler or Eclipse Memory Analyzer, search for classes that are not supposed to be loaded, identify the respective leaking classloader and find the shortest paths from gc root

Environment: Java 1.6.0_13, OSX, Fedora 3.2.1 default installation, Tomcat 5.5.26

Patched Axis and found another leak. After undeploy there are two remaining Instances of org.apache.commons.logging.impl.Log4jLogger being held on by Tomcat. It seems that this kind of issue has been known for some time, see [1]. After having unsuccessfully tried a number of options (upgrading commons logging, searching for possible leak scenarios in the code base, removing commons logging and replacing tomcat/bin/commons-logging-api.jar), only removing both log4j and commons logging from the webapp and placing them in tomcat/common/lib fixed this remaining classloader leak.
Given the many problems that the dynamic binding approach of commons logging brings along, it should be considered abandoning commons logging in favor of slf4j. The slf4j approach avoids classloader issues altogether by using a static binding approach, see [1] and [2].

There is one other thing that influences memory during undeploy: the finalizer. As there are some classes in the Fedora codebase that override the finalize() method, memory usage can build up when the webapp is deployed/undeployed in rapid succession. It takes at least two GCs until a finalizable object can be collected, and the finalizer queue may not keep up with finalizing its objects because the finalizer is a low priority thread and therefore eventually cause an OOM. For "normal" deploy/undeploy cycles this should however not be an issue.
