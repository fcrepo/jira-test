FCREPO-748 Ability to Authenticate to http-based storage when getting "E" datastreams

TypeStory
StatusClosed
ResolutionWon't Fix
PriorityMinor
ReporterChris Wilper
AssigneeChris Wilper
Created2010-07-27 23:40 UTC
Updated2015-01-16 21:01 UTC
Resolved2015-01-16 21:01 UTC
Affects versionsFedora 3.x trunk

Description

Fedora currently allows one to point to files hosted on external services via http, using the "E" control group. This is a read-only connection. If such content is protected via HTTP-Basic, it'd be nice if Fedora could be configured to authenticate to the service it's hosted on, so it can provide the content to the caller.

Chris Wilper, 2010-08-03 21:55 UTC

Options:

  • Put in FOXML with each datastream
  • Directly code a http prefix + credentials map into Fedora

Options for doing outside Fedora:

  • Don't have E datastream go to the real content location, reference service that has credentials
  • Use a disseminator service that keeps necessary credentials/mapping for various authN-protected paths

In any case, credentials+mappings could be saved in various Fedora objects.

Dan noted: If we want Fedora to authenticate "on behalf of" a given requester (the user of Fedora), the userId is available, so could be passed to a service/proxy that has access to the credentials necessary to make the real request.

Stephen Bayliss, 2010-10-16 15:06 UTC

Another implementation thought:

External content is in general (on ingest, "E" datastreams, etc) grabbed by ExternalContentManager -> DefaultExternalContentManager

This is configured a a module in fedora.fcfg.

We could therefore provide additional configuration information (either directly in fedora.fcfg, or as a separate module config file) providing for example

  • per domain or per url-path auth credentials
  • any additional auth information required (eg whether to pre-emptively provide credentials)

However this would mean that plain-text auth credentials would be present in the file system - is there any alternative trust mechanism that could be used?

Stephen Bayliss, 2010-12-17 13:11 UTC

This would also be useful in the context of SDep methods; the external service called in these cases may also require authentication. Arguably that could be a different JIRA issue, however both go through the ExternalContentManager so it would seem logical to extend the scope of this issue.

Within this it would also be useful to:
1) Pass through selected request context information. See http://permalink.gmane.org/gmane.comp.cms.fedora-commons.user/6178 and http://permalink.gmane.org/gmane.comp.cms.fedora-commons.user/6180 - in this case the logged-in user. Potentially this could include the auth credentials from the request thus allowing the external service to call-back to Fedora using the user's original auth details (with appropriate health-warnings as this could compromise security if the service is not trusted).
2) Perform cross-context requests within the same servlet container - if the service is within the same container then using the RequestDispatcher may be more efficient than a request going through the IP stack. For instance defining something like a context:// protocol.
