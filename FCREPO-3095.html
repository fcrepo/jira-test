Description

The PersistentStorageSession manages 1 to n OCFLObjectSession objects under hood.  The OCFLObjectSession manages the staging and persistence of content for a single OCFL object within a single transaction.   The OCFLObjectSession must be able to span multiple requests and must be persistent across reboots (though it would not be included in any notion of rebuildability).   The caller must be able to indicate whether changes should be committed to the OCFL object's mutable head or as a new version.   

The basic flow is as follows: 

  1. OCFLObjectSession is created based on a new or existing OCFL object.
  2. 0 to n  changes are written to a staging space.
  3. On commit,  the changes are then written to the OCFL client and commit either to the MUTABLE HEAD or to a new OCFL Version, and the staging content is removed.

Regarding ocfl object sessions surviving reboots, that seems to also imply that fedora transactions would need to as well, since the hierarchy goes fedora tx -> persistence session -> object session. Is that something new we are committing to?

 

I'm also trying to work out where the decision about whether to commit to the mutable head or a new version would happen. If autoversioning is repo wide, then it could probably happen almost anywhere. If it were to be an option per object, then it seems like a decision to make at the object level, which might imply that the OCFLObjectSession would figure this out rather than being told how to commit.
