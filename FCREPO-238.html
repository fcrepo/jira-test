Stephen Bayliss, 2011-08-02 21:32 UTC

See DefaultDOManager:

  • line 780 picks up the date/time from the request
  • lines 814-823 set this on the object
  • lines 827-841 set this on datastreams that don't have a date/time set

This implies that somewhere in the prececeding code, ie when the object is deserialized, a datestamp is being added to datastreams where there is none in the FOXML, which is a bug, as it means that the line 827-841 above don't get to do their job.

This could be in the deserializer, or possibly the Datastream classes themselves are somehow setting defaults on construction etc.

Stephen Bayliss, 2011-08-02 22:02 UTC

And for a potential candidate for this bug, FOXMLDODeserializer.instantiateDatastream does m_obj.addDatastreamVersion... which calls BasicDigitalObject.add (under the hood), which has:

if (d.DSCreateDT == null)

{ d.DSCreateDT = new Date(); }

Which is just plain wrong; it should probably be leaving this as null. But doing this could throw up issues elsewhere in the code potentially (expect some NPEs will need tracking down). Theoretically Datastream.DSCreateDT should be final?

Former user, 2011-08-03 18:06 UTC

after investigating stephen's comments i think the problem might be in FOXMLDODeserializer.startElement() at line 378 which sets the class variable m_dsCreateDate from the FOXML. When the datastream date in the FOXML is empty DateUtility returns null (DateUtility.parseDateLoose(String dateString):184). So in FOXMLDODeserializer.instantiateXMLDatastream(): 854 the datastream's DSCreateDT is assigned null.
I'm not quite sure how to fix this, since it seems to me with the current approach FOXMLDODeserializer needs knowledge of the current create date from the context.

Stephen Bayliss, 2011-08-03 18:56 UTC

I think it is ok since the deserialization is kicked off at line 805 in DefaultDOManager.getIngestWriter; then DefaultDOManager.getIngestWriter subsequently sets the DSCreateDT to the one from the context around lines 826-841 if the existing DSCreateDT is null or "".

So if we can stop any "default" date (ie one not provided in the FOXML) being assigned in the deserialisation process and leave it at null, then the existing code should add the correct value.

Probably should also verify that add/modify datastreams still work as intended and pick up the date from the context also.

(And I've not actually traced this through with a debugger... so still might be missing something - but in principle we should make sure that null/empty dates only get set at one consistent point in the codepath.)
