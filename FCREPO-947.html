Apppears to always occur when there is an asOfDateTime specified: http://localhost:8080/fedora/objects/demo:REST/validate?asOfDateTime=2011-05-21T15:54:50.215Z. Need to find out why the choice of database makes a difference, though.

Stephen Bayliss, 2011-05-23 15:57 UTC

I've reproduced this.

The failure is on demo:REST - and this object has its date/time settings set to the current date/time - and the asOfDateTime is set to exactly the same value.

So I wonder if this is something to do with date comparison/precision that is specific to postgresql

The validation is failing because of a missing DC datastream, which is of course impossible - so I'd suggest that it is not actually picking the datastream up because of something awry in the date/time querying/comparison.

Stephen Bayliss, 2011-05-25 11:21 UTC

Further observations

String datetime is set to current date (new Date()) as a static at class level

test object demo:REST has CREATED set for datastreams RELS-EXT and RELS-INT, but not for DC to this value

Ingest will take place (theoretically?) after datetime - so DC will have a created date later than datetime (as will the object creation date/time)

So the validate is failing correctly - it is validating the object at an earlier datetime than the created date for DC - so DC won't have any versions present.

The behaviour now seems correct to me - but I have no idea why this should have not been failing on other databases - perhaps with Derby the whole thing is running faster and the ingest date/time is in fact (to the date/time precision) the same as datetime set at class level? I would have expected the odd spurious test failure from time-to-time.

Stephen Bayliss, 2011-05-25 11:50 UTC

Testing the validate method with alternative date/time values:

validate at now + 10 mins - success
validate at now - 10 mins - fail - expected

So this would fix the test case.

I note that in the REST API tests at least, there is very little explicit testing of asOfDateTime parameter to check it gets the right version (especially at a degree of precision; we should be testing 1ms before, now, 1ms after on a few methods to check this behaviour).

So in conclusion, no idea why this was specifically failing on Postgresql, I can only suggest that the alternative database caused some variation in execution time of various methods in the test class, and that triggered the error. But I don't think that this failure was revealing an underlying bug.
