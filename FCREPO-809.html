Scott Prater, 2010-11-10 00:29 UTC

Sure. First, some background about how this issue came to be. My main concern is with FCREPO-807: we ran into an issue where we were ingesting large amounts of FOXML that contained inline XML which we wanted stored as managed datastreams (and were indicated as such in the FOXML), but were silently being stored as inline datastreams. Researching the topic, I came across that issue, which as originally proposed by Steve Bayliss, included the feature described here. After talking with Steve, we decided to split 807 into two separate issues: FCREPO-807 Closed , which was reclassified as a bug (since Fedora does not behave as users expect it would, and as intuition would suggest it should behave), and this issue, which is really a feature.

That said, I can come up with two use cases for including managed datastream XML in exported FOXML. The first would be for archiving/backup/migration purposes: I can imagine a situation in which someone would want to backup their data and/or move it elsewhere without having to chase down many links, especially if many of those links are to localhost or resources on a private network. Of course, this wouldn't make binary datastreams, redirects, and external datastreams any more accessible, but it could reduce the number of links that would need to be followed to assemble an object outside Fedora.

The second use case is one that's actually much closer to my needs: I use the export API to get XML representations of our objects and process them to create complex METS packages. Having managed datastream XML available in the exported object XML would save me quite a few HTTP fetches.

Stephen Bayliss, 2010-11-10 15:23 UTC

I'd also support this. Including "M" datastreams as inline XML rather than base64 makes it easier to export objects, edit them offline and ingest them again. Something I do when for instance developing CMA objects, once I'm happy with them I often export them, "tidy them up", and re-ingest.

Plus when authoring objects it makes life a lot easier to include XML inline for "M" datastreams rather than having to base64-encode.

(Furthermore the FOXML schema does support it)

Chris Wilper, 2010-11-16 23:58 UTC

Hi Scott, we talked about this again at today's committer meeting. There's generally some reluctance (from me, and at least a couple of the other committers) to encourage the use of inline xml datastreams, because of all the problems they have caused for us in the past. Providing XML datastreams inside the FOXML requires more memory of the server and places requirements on the XML that it can't contain any document type declarations, processing instructions, custom entity references, or xml comments. It also requires that the XML is encoded is transcoded to UTF-8 on the way out.

Indeed, there is a movement afoot to reconsider having inline xml datastreams at all in future versions of Fedora and/or FOXML. Of course, that will require more discussion, but it feels like we'd be jumping the gun to provide this capability only to take it away later.

We were wondering if the AtomZIP format would fit the bill for your use cases. If you specify that AtomZIP as the desired format, Fedora will give you a zip file with an Atom.xml manifest and content included as separate entries within the ZIP file. This would only require you to make one request of Fedora, and you'd get all the content you need to generate a custom METS file, for example.

Scott Prater, 2010-11-17 00:20 UTC

That sounds reasonable to me. The AtomZIP export would be even faster than an export with inline XML, if I were dealing with many and/or very large xml datastreams: fewer bytes being transferred across the network.

Perhaps we should shelve this issue, then?
