FCREPO-3905 Upgrade util should support destination host that does not match source

ResolutionFixed

ReporterBen Pennell
AssigneeBen Pennell

Componentsfcrepo-upgrade-utils

Description

When migrating data from a fedora 4 to 6 repository using the following steps:

https://wiki.lyrasis.org/display/FEDORA6x/Migrate+to+Fedora+6#MigratetoFedora6-TheFedora4%E2%86%926MigrationPath

If the fedora 4 instance being exported does not have the same hostname as the fedora 6 instance being migrated to, it will result in triples being created in Fedora 6 with the original Fedora 4 URL as the subject. The result is that the triples are not directly describing the Fedora 6 resource, and will display in the “Other resources” section.

The issue is that fcrepo-import-export tool exports RDF with the original subjects, but the fcrepo-upgrade-util does not have a way to remap those URLs for the new fcrepo 6 instance. Since the subjects are from another base url, fcrepo 6 does not interpret them as referring to the resource being created.

We could address this by adding a base url remapping option to fcrepo-upgrade-utils, similar to the fcrepo-import-export tools --map option.

Comments (2)

Ben Pennell, 2024-01-03 16:44 UTC

After some testing, I was able to reproduce the issue, but also was able to avoid the problem without any code changes.

I had a fedora 5 instance running at localhost:8043, did the export as follows:

java -jar fcrepo-import-export-1.1.0.jar \
  --dir fcrepo-5-export \
  --user fedora_admin:fedora_admin \
  --mode export \
  --repositoryRoot http://localhost:8043/fcrepo/rest \
  --resource http://localhost:8043/fcrepo/rest \
  --binaries \
  --versions

Then ran the upgrade util as follows:

java -jar fcrepo-upgrade-utils-6.2.0.jar \
  --input-dir fcrepo-5-export \
  --output-dir fcrepo-6-home \
  --source-version 5+ \
  --target-version 6+ \
  --base-uri http://localhost:8043/fcrepo/rest

and then inspected the generated OCFL. The binary descriptions with extra triples had the correct “info:fedora/” prefix in subject URIs. I then brought fedora 6 up on port 8880 so that the port would not match the original server with:

java -Dfcrepo.home=fcrepo-6-home -jar fcrepo-webapp-6.4.1-jetty-console.jar

Inspecting the binary descriptions in the UI, the properties belong to the binary rather than to a separate resource like originally observed.

If I do the same steps, but when running the upgrade util provide a different base-uri that doesn’t match the fedora 5 server (for example, “http://localhost:8880/fcrepo/rest"), then I get the issue observed in this ticket: triples in the binary description rdf in the OCFL will have subjects with the old “http://localhost:8043/” prefix, and when viewed in the web interface the properties will appear in the Other Resources section.

This behavior makes sense however, since there is not actually an import step. The upgrade util transforms the fedora 5 export into OCFL format, and while doing so it also transforms the URIs in the RDF, replacing all subject and object URIs that contain the base-uri with the host agnostic “info:fedora/”. And then fedora 6 is started with the generated OCFL as its data directory, with the transformed URIs in the RDF if the correct fedora 5 base-uri was provided.

So as long as the base-uri matches the URI in the fedora 5 export, the upgrade util appears to work as expected when migrating to a new host since the generated OCFL contains URIs that use the generic “info:fedora/” prefix.
