Description

When two simultaneous transactions update the same object(s), the second transaction should fail at commit time, preferably before any of its changes are persisted. This failure should produce a 409 status on the commit.

A few notes on how this may work:

  • The OCFL java client includes mechanisms for optimistic locking based on the expected Head version number at the time of committing
  • OCFLObjectSession includes the unimplemented prepare() method.
    • This method could perform a precheck and lock on objects it is updating
    • We would most likely need to capture the current head version per ocfl object when they are first modified, for checking later against the head version in OCFL.
