FCREPO-2104 Fedora breaks when commiting extra large transactions

Description

When using Fedora 4 transactions and making many thousand changes in single transaction, if commiting this transaction takes more than 2 minutes, Fedora returns internal error and is unusable after.

We catalogize books, where every page has several objects, including high-res scan and such, so when saving a book, we have a transaction that can include thousands of objects and quite a few gigabytes. This prolongs the commit time of Fedora transaction. However, once it takes more than 2 minutes, everything breaks.

There seems to be internal transaction reaper in infinispan that execs after 2-3 minutes and destroys this long running (internal, not fedora) transaction. Immediately after this Fedora can not continue commiting its own transaction so fails.

However, this thread remains broken - I understand that Fedora uses pool of about 8 threads when serving requests and accessing its internal Infinispan. When this happens, approximately every 8th request on Fedora fails because it's assigned to thread whose Infinispan transaction has been destroyed and it never opens a new one. This persists until Fedora is restarted, rendering it unusable.

There should be a way to control and prevent this timeout, or at least Fedora should not break when this timeout happens.

A. Soroka, 2016-08-12 15:51 UTC

I'm not actually sure that Fedora can do anything about this, because it's not Fedora that maintains that threadpool, it's ModeShape. Fedora's code doesn't have any access to those threads, so far as I can tell.

Would it be possible for you to set up this problematic situation with a profiler running so that we can see who owns the dead thread? If you do not have a profiler, we could be able to get you access to YourKit for this specific purpose (ping Andrew Woods).

A. Soroka, 2016-08-12 15:52 UTC

Lukáš Jáně, 2016-08-12 18:01 UTC

Well, we were thinking about it, but one book is probably as atomic as we can go, during loading data from external system. It was all fine until we hit books with > 1300 pages. We store every page with hi res scans, thumbnails we generate, user copies with watermark, ocr text in several formats, lots of book metadata. It makes little sense to parse half of a book, because in our process we'd hardly put it all together after, without manual interventions. It's all complicated enough as-is.

A. Soroka, 2016-08-12 18:43 UTC

I can see that a book is a pretty natural unit. Let me suggest one workaround, which may or may not be any use to you: you could use multiple transactions to assemble the book in a temporary location in the repository, then use a single MOVE request to shift your completed resource into its proper position. That way, a fouled assembly can be deleted without any ill effects. It's not a simple transaction and you would have to hand around the temporary location as a "handle", but it might get you further down the road.
