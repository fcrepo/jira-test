Description

ocfl-java-client v2.2.1 supports range requests at the ocfl level. Once fcrepo us updated to this version, we should see if we can make use of this in fedora in order to only retrieve the parts of the file that a user is requesting, then they make a request with an HTTP Range header.

I’ve tried the PR with local filesystem binaries, and with fedora using s3 as its storage. There was a very significant performance improvement with s3 when dealing with a 100mb TIFF file and requesting the last 10 bytes of the file. There was no noticeable difference when requesting the first part of the file, or downloading the whole file of course:

# Against aws 100mb file, download whole thing
time curl http://localhost:8080/rest/large_tiff -v -o /dev/null  -ufedoraAdmin:fedoraAdmin 

100 96.2M  100 96.2M    0     0  12.4M      0  0:00:07  0:00:07 --:--:-- 14.2M
curl http://localhost:8080/rest/large_tiff -v -o /dev/null   0.06s user 0.14s system 2% cpu 7.738 total

# Without range updates, get last 10bytes
time curl http://localhost:8080/rest/large_tiff -H"Range: bytes=100924970-100924980" -v -o /dev/null  -ufedoraAdmin:fedoraAdmin

100    10  100    10    0     0      1      0  0:00:10  0:00:08  0:00:02     2
curl http://localhost:8080/rest/large_tiff  -v -o /dev/null   0.01s user 0.01s system 0% cpu 8.058 total

# WITH range updates, get last 10bytes
time curl http://localhost:8080/rest/large_tiff -H"Range: bytes=100924970-100924980" -v -o /dev/null  -ufedoraAdmin:fedoraAdmin

100    10  100    10    0     0     31      0 --:--:-- --:--:-- --:--:--    31
curl http://localhost:8080/rest/large_tiff  -v -o /dev/null   0.01s user 0.01s system 4% cpu 0.333 total

With local storage, the retrieval times are already very short on my personal laptop, but there is some difference when getting the last 10 bytes. Without these changes it took 0.108s, and with these changes it took 0.030s. Getting the first 10 bytes took around 0.030 either way.
