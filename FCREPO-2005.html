Description

In the default activemq configuration a ConstantPendingMessageLimitStrategy is used to limit messages on the topic to 1000.

http://activemq.apache.org/slow-consumer-handling.html

In the camel toolbox the fcrepo-camel-indexing-triplestore connects to that topic and in my case at least, is slower to process those messages than fedora is generating them and for large batch ingests a bunch get dropped leaving the triplestore in a worthless state.

A. Soroka, 2016-04-21 19:49 UTC

I'm not sure why a topic is being used here. I think we want a feeder network of queues. We really need to guarantee delivery for this stuff.

Unknown, 2016-04-27 09:58 UTC

The default ActiveMQ configuration is terrible for production. The first thing I did for our production setup is change the topic to a queue that gets pushed to a remote broker network. Perhaps more documentation about how to do this would be good.

A. Soroka, 2016-04-27 13:34 UTC

If you have a better scheme already designed, why not just put it into the default? Is there some reason we have this janky setup configured?

Unknown, 2016-04-27 13:39 UTC

I think I big reason for using a topic is that not everyone consumes the JMS messages, and for those folks, you wouldn't want to needlessly fill up an unused queue in the local broker.

A counter argument to this is that if someone isn't using the messaging infrastructure, they should disable this via spring.

Either way, there is currently documentation for how to convert the topic into a queue in the activemq.xml file here: https://wiki.duraspace.org/display/FEDORA4x/Setup+Camel+Message+Integrations

including how to push those messages to a remote broker, which I'd highly recommend.

A. Soroka, 2016-04-27 13:42 UTC

Yeah, I don't buy that argument. The number of people who will want no messaging is a fraction of the number of people who will want no indexing: pretty small. We should use a guaranteed-delivery setup as the default and offer instructions on how to turn it off for those who so desire. The evidence? Someone as bright and experienced as Michael Durbin, a committer, got fouled up by this unexpected behavior.

Unknown, 2016-04-27 13:48 UTC

I completely agree that these messages need some notion of "guaranteed delivery". A JMS topic is anything but guaranteed (topics are more like: we guarantee that at some point we'll drop messages).

I'd be in favor of changing the topic to a queue and providing documentation for disabling messaging (for those who don't use it).
