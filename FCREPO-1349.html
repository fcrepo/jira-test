FCREPO-1349 fcrepo-camel should include explicit support for transactions

Description

Fcrepo-camel does not provide explicit support for transactions, but it should. Furthermore, it should do so in such a way that it does not get in the way of a user – this would probably involve using appropriate header values inside a transaction (which are then cleared after committing the transaction). This way, a user program would not need to do any extra (unnecessary) url processing.

Unknown, 2015-02-04 12:18 UTC

What would you think of this sort of interface:

First, there would be a new header: CamelFcrepoTransaction (or FcrepoHeaders.FCREPO_TRANSACTION in java)

onException(Exception.class)
.to("fcrepo://localhost:8080/rest?transaction=rollback")
.log("error ...")
.handled(true);

from("direct:foo")
.to("fcrepo://localhost:8080/rest?transaction=start")
...
.to("fcrepo://localhost:8080/rest?transaction=commit");

Under the covers, what would happen is this: if the transaction=commit or transaction=rollback option is given, the appropriate POST is sent to fedora (no need to explicitly set the HTTP_METHOD). For any other non-empty transaction value (you can use start or create or refresh or whatever), one of two things will happen – if there is an existing value in the CamelFcrepoTransaction header, then that transaction is "refreshed"; if there is an empty or null value in that header, a new transaction is created, the value of which is stored in the CamelFcrepoTransaction header. A commit or rollback operation will clear that header.

When the CamelFcrepoTransaction header is present, all calls to the fcrepo endpoint will be run in the context of that transaction, meaning the path will have the "/tx:<transaction value>/" string inserted between /rest and the node identifier.

This also means that you wouldn't need to do any special processing of the Location header that the initial /fcr:tx POST operation returns (though it would be good for the Location header to be returned to the client in any case).

At least this interface makes sense to me. Any thoughts?

There is a suggestion to use the camel transaction manager to handle transactions – this would involve a different implementation, and I am currently looking into this. So for now, do not merge the PR mentioned in this ticket.

The difference from the perspective of a camel user is that the route would look more like this:

from("direct:foo")
.transacted()
.to("fcrepo:localhost:8080/rest")
.process(...)
.to("fcrepo:localhost:8080/rest")
.process(...)
.to("fcrepo:localhost:8080/rest");

Here, all of the fcrepo-based endpoints would run in the context of a single transaction. This implementation looks promising, but it involves a certain degree of complexity (and lack of documentation).
