Description

Section 5.3 of the Fedora spec states:
"A conforming server MUST advertise the individual resource ACL for every controlled resource in HTTP responses with a rel="acl" link in the Link header, whether or not the ACL exists."

So Fedora needs to always advertise an ACL location the client can PUT to to create an ACL, even if it doesn't exist already.

https://fcrepo.github.io/fcrepo-specification/#link-rel-acl

 

Peter Matthew Eichman's proposed the path:  /resource/fcr:acl

 

As documented in a related, overlapping, and now closed ticket ( https://jira.duraspace.org/browse/FCREPO-2744 )  this ticket will entail removing the use of acl:accessControl in order to create the rel=acl header link.

To complete the issue, 

  1. Every resource with the exception of all resource's ending in /fcr:acl should return a link header as follows:  Link: <resource-uri/fcr:acl>; rel="acl"
  2. The old way of doing things (populating the rel="acl" using the <> acl:accessControl <aclpath>  statement),  acl validation , and support for specifying an ACL on resource creation, should be removed.

Danny Bernstein, 2018-04-04 16:22 UTC

Aaron Birkland:  Is that the intent of Section 5.3? Or is it just saying that the link should point to the  resolved ACL if no ACL is explicitly defined directly on the resource? 

Aaron Birkland, 2018-04-04 16:33 UTC

The link MUST be present and point to the resource's individual ACL.  If the resource doesn't have an ACL (and therefore relies on the algorithm to traverse the tree to find an ACL), then the link points to a resource that returns a 404, explicitly indicating that the resource does not have an ACL directly applied to it.  Clients can PUT to that ACL link URI to create an ACL for the resource.

See background conversation:

https://github.com/fcrepo/fcrepo-specification/pull/198#issuecomment-326126675

Danny Bernstein, 2018-04-04 16:50 UTC

Aaron Birkland:  thanks for the reference to the background discussion.  That all makes sense though it seems to create some confusion with respect to Section 5.4 which allows the user to define the location of the ACL.  So am I correct in saying that if the user does not use a rel=acl request link header on creation, then a default location is presented whether or not the acl exists? If the user wishes to define the acl on the resource  he/she must perform a PUT to the default location returned in the rel=acl response link header?

Aaron Birkland, 2018-04-04 16:55 UTC

Danny Bernstein Yes, precisely - a default location is provided that the user can PUT to.  

Peter Matthew Eichman, 2018-04-12 17:09 UTC

Danny Bernstein, Aaron Birkland In light of the discussion of ACL locations on today's tech call, I am in favor of removing section 5.4, which would have the effect of removing the ability to link a resource to an arbitrary location for an ACL. That would make this issue simpler, since the location of a resource's (nominal) ACL is always known, even without additional information.

I'll also put in a pitch for naming that default location "fcr:acl", in parallel to things like "fcr:versions" and "fcr:metadata". So if you have a resource http://example.com/fcrepo/rest/foo, it's ACL location would be http://example.com/fcrepo/rest/foo/fcr:acl.

I'll also raise the question of whether a GET to a non-existent ACL should return a 404, or if it should return a 303 See Other, with the effective (inherited) ACL in the response?
