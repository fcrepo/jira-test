Description

The XPath generated for policy queries in the xml database are restrictive and in certain cases will not return matching policies.

Example:
If a policy specifies an attribute id not usually supplied in the request it will not be matched when it should be (the policy query is built on attributes supplied by the PEP; ie before additional attribute-finding has taken place). An attribute in the policy which is not specified in the request should always result in a match (since the finder is unable to determine if the policy matches due to lack of information in the request).

The attribute conditions part of the query needs to include an additional clause specifying "if a policy attribute is not present in the request".

Comments (2)

Stephen Bayliss, 2011-04-10 13:13 UTC

The above is still imperfect - there is a distinction between:

  • a datastream ID attribute missing in the request; which means the resource is not a datastream, and there should be no policy matching on the datastream attribute
  • a custom resouce attribute missing in the request; which means the request does not know about the attribute (it will be retrieved later when evaluating); and a policy specifying this attribute should always be matched by the finder.

But it is probably the best we can do unless a mechanism for specifying attribute lookups to take place before policy finding takes place can be implemented.

Stephen Bayliss, 2011-04-10 21:56 UTC

Opened, fixed, closed; as issue was causing some new integration tests for fcrepo-840 to fail (policies that include custom RI-based attributes as resource attributes were not picked up by eXist/DBXML policy index)
