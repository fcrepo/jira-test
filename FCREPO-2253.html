Description

This task is to investigate the feasible options for creating and verifying fixity information related to RDF Sources, i.e. Fedora objects.

This functionality already exists for Non-RDF Sources (Binaries), but the metadata in the repository does not have fixity information associated with it.

The final outcome of this (or a follow-on) task is to have a fixity service, like the one for Binaries, that can be performed on RDF Sources on-ingest or on-demand.

The challenges of this task are well-known, but ones that must be addressed.

A. Soroka, 2016-10-09 11:51 UTC

Youn Noh has picked up on an important point; every fixity use case with which we are presented is actually a demand for equivalence comparison across time. Fixity records are "continuations" for equivalence-checking algorithms. But we don't have to introduce OWL and semantic equivalence quite yet. RDF defines a perfectly good notion of isomorphism:

https://www.w3.org/TR/rdf11-concepts/#graph-isomorphism

http://www.hpl.hp.com/techreports/2001/HPL-2001-293.pdf

and it is already available in Jena, the framework we are using for RDF. If we want to offer actual fixity numbers on RDF, we should begin with a good algorithm for isomorphism and work from there, for the same reason that sensible programming expects that hash-codes and type-specific equivalence functions should normally agree.

A. Soroka, 2016-10-10 20:17 UTC

isomorphic graphs need not be identical, which I believe is what we need to demonstrate

No, this is the whole point. We're not even agreed on what we mean by "identical" (what kind of "identity" do you think an RDF graph has? If that graph is translated into a different format and has exactly the same meaning, has that "identity" been preserved? If I write down that graph in Turtle and add an extra blank line, have I changed the "identity" of that graph? What if there are blank nodes in the graph and I change their labels?).

If you want to say that "identity" is what we need to demonstrate, you have to define identity. I think the W3C has already done a perfectly good job of that for us. We gain nothing by producing our own special flavor of RDF equivalence.

As for the computational complexity question, please forward your friend the HP tech paper I linked above. The tractability concerns don't arise in the restricted context in which we are working.
