Description

Attempting to fixity check a binary memento is failing when run against fcrepo 6 running in jetty

% curl -ufedoraAdmin:fedoraAdmin http://localhost:8080/rest/5bf5ee06-a74e-4a34-80a4-6c2fad2bfa95/fcr:versions/20250519144423/fcr:fixity
Invalid request for memento at /5bf5ee06-a74e-4a34-80a4-6c2fad2bfa95/fcr:versions/20250519144423/fcr:fixity

This is despite the fact there is a passing IT that verifies the behavior:
https://github.com/fcrepo/fcrepo/blob/main/fcrepo-http-api/src/test/java/org/fcrepo/integration/http/api/FedoraFixityIT.java#L168

No error is logged normally, but if I add a stacktrace to where the response message is originating, I get the following (line ref is slightly off due to added debugging statements):

	at org.fcrepo.kernel.api.identifiers.FedoraId.processIdentifier(FedoraId.java:542)
	at org.fcrepo.kernel.api.identifiers.FedoraId.<init>(FedoraId.java:117)
	at org.fcrepo.kernel.api.identifiers.FedoraId.create(FedoraId.java:130)
	at org.fcrepo.auth.webac.WebACFilter.doFilterInternal(WebACFilter.java:218)
	at org.springframework.web.filter.OncePerRequestFilter.doFilter(OncePerRequestFilter.java:117)

So it appears that during WebACFilter parsing the fedora id is failing because the afterVersion portion of the id is /20250519144423/fcr:fixity and it can’t handle the fcr:fixity. The integration test may be passing due to webac not being active in that context. In the FedoraFixity controller, the ID it parses has the fcr:fixity suffix removed already by the controller.
