Description

I'm requesting creation of a configurable camel service (similar to fcrepo-indexing-solr or http endpoint service) enabling fedora CRUD records to be sent to Solr (or any configurable endpoint) in xml/rdf format.

This would enable users to adopt a sustainable solution and bypass dependency on Marmotta (now retired) for Solr indexing transformation. It would be easier and more natural to configure this way for anyone with xslt experience (and GSearch in particular). This might make migrating from GSearch less challenging.

For most use cases Solr has sufficient functionality to execute xslt transformations itself when presented with a single record in xml format: the Solr UpdateRequestHandler can automatically perform xslt transformations on xml to generate index records using the tr=<myArbitraryXlstHere.xslt> parameter (see https://solr.apache.org/guide/8_2/uploading-data-with-index-handlers.html).

More complex use cases can already use the camel toolbox http endpoint service to configure their own service exactly as they want - but it would be nice for everyone without additional requirements if they didn’t have to build their own service this way!

Use case summary

Send fedora content as xml  to solr for indexing through xslt transformation.

Actor: systems architect/developer

Scope: Useful to a wide rang of fedora installations currently utilising solr (most?), including those using or contemplating using ldpath. Facilitates migration from fedora 3.x to fedora 6.

Level: High level impact with focus on technical inter-operability. Extend current camel-toolbox functionality by enabling it to send xml-formatted records to solr This would leverage fedora API’s ability to send records as xml and solr’s ability to perform arbitrary xslt transformations on ingest.

Story: I want to customise transformation of fedora content into a solr index using xslt. This service would align with fedora 3.x praxis, where GSearch plugin is/was widely used to perform xslt transformation on index. It would be more sustainable than using (deprecated) ldpath and offers more flexibility. It would facilitate migration where integration with solr is a requirement.

Dan Field, 2023-02-07 17:12 UTC

I have a first draft of this functionality available. It currently:

  • Removes ldpath entirely from the camel toolbox
  • Replaces the ldpath indexing routes with XSLT processing routes
  • XSLT processing is currently processed within the Camel route, utilising XSLT component https://camel.apache.org/components/3.20.x/xslt-component.html
  • XSLT Processing could be handed to Solr if there is a good use-case but I see no advantage as yet, in doing so.
  • XSLT to be used is configured via the solr.fcrepo.defaultTransform when no transform is provided in the object metadata.

Is this suitable for your needs James Alexander ?

Dan Field, 2023-04-20 13:32 UTC

James, the 3 properties used by the solr indexer are:

solr.indexing.enabled=true
solr.baseUrl=http://localhost:8983/solr/fcrepo
solr.fcrepo.defaultTransform=org/fcrepo/camel/indexing/solr/default_transform.xsl

Where in this case, the default transofrm is the one which should have been packaged with the camel toolbox. It might be missing in your environment? THat might be a bug we need to address. Its a fairly simple transform

 <?xml version="1.0" ?>
<xsl:stylesheet version="1.0"
    xmlns:xsl="http://www.w3.org/1999/XSL/Transform"
    xmlns:rdf="http://www.w3.org/1999/02/22-rdf-syntax-ns#"
    xmlns:fedora="http://fedora.info/definitions/v4/repository#"
    xmlns:ldp="http://www.w3.org/ns/ldp#">

    <xsl:template match="/">
    <add>
        <doc>
            <field name="id"><xsl:value-of select="rdf:RDF/rdf:Description/@rdf:about" /></field>
        </doc>
    </add>
    </xsl:template>

</xsl:stylesheet>
