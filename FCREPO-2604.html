Description

The spec states that there MUST be a corresponding notification when the state of a resource changes as a result of an HTTP operation.

First, seek clarification: What is the definition of 'state' of a resource?

Secondly, check/audit the current impl behaviour. At the very least, it seems to emit too many message under some circumstances. For example, if you modify A with a PATCH so that it links to B, there will be two "resource modification" messages: one for A, and one for B. It is unclear if B is warranted.

Situ, Longshou, 2017-10-03 20:05 UTC

Andrew Woods Here are the events I got from the client operations above. I've added one more case for # 8 Link between resources with PATCH and POST that emits an extra event for the linked-to resource, which seems hard to explain. Please reference the attachment messaging.txt for details of the messages emitted from Modeshape.

Here are the conclusions:
1. Create container emits two messages:

  • A message with an Update event and a Create event for the new container created.
  • A message with an Update event for the parent container.

2. Create binary emits is two messages:

  • A message with an Update event and a Create event for the new binary created.
  • A message with an Update event for the parent container.

3. Update container (and binary) both emits a message with a Update event.

4. Delete container (and binary) both emits two messages:

  • A message with an Delete event for the resource deleted.
  • A message with an Update event for the parent resource.

5. Add resource to basic container emits two messages:

  • A message with an Update event and a Create event for the new basic container created.
  • A message with an Update event for the parent container.

6. Add resource to direct container emits three messages:

  • A message with an Update event and a Create event for the new resource created.
  • A message with an Update event for the direct container.
  • A message with an Update event for the membership resource.

7. Add resource to indirect container emits four messages:

  • A message with an Update event and a Create event for the new resource created.
  • A message with an Update event for the indirect container.
  • A message with an Update event for the membership resource.
  • A message with an Update event for the member resource that is linked-to.

8. Link between resources with PATCH emits two messages:

  • A message with an Update event for the linking resource.
  • A message with an Update event for the resource linked-to.

9. Link between resources with POST emits three messages:

  • A message with an Update event and a Create event for the new inbound resource created.
  • A message with an Update event for the linking resource.
  • A message with an Update event for the resource linked-to.

kefo, 2018-05-24 14:28 UTC

I do not think a message should be emitted when a 'linked-to' resource receives a new inbound reference, which is the case in examples 7, 8, and 9.  In short, I do not believe the state of the linked-to resource has changed.  If I perform a GET on the linked-to resource after the original requests in 8 and 9 (and whether I ask for inbound references is beside the point) the triples of the linked-to resource are the same (except, perhaps, the last-modified value because that might be set by modeshape?).  This gets to Aaron Birkland's second question (and, by example, the first).  There also seems to be consensus on this interpretation of 'state' in FCREPO-1742 Closed .

To bring in a working example of this, we've been hit pretty hard by the activity described in items 8 and 9.  We sync resources from one system to another.  We process thousands a day (sometimes tens of thousands) and sometimes we need to perform a full sync which frequently means hundreds of thousands of resources.  The resources we sync often have many references to other repository resources in part because those are rich relationships between other 'first-class' repository resources and in part because we make heavy use of vocabularies and lists.  Our "Active" Status resource (meaning a resource is "Active") is probably referenced by hundreds of thousands of resources.  We do not know what properties specifically were updated in the source system for a given repository resource (so we cannot perform a targeted PATCH).  We must, by and large, replace nearly all the content that might have been modified in the source system with the PATCH.  (A PATCH, versus a PUT, is necessary because we have repository-created and repository-only relationships we must persist and we do not want those wiped out.)  I can watch our reindexing logs and observe these vocabulary and list resources, and other linked-to resources, being fetched and reindexed again and again and again and again.  We do not request and index the inbound references, so the linked-to resource is basically unchanged each time it is reindexed.  This has resulted in a deluge of traffic and not infrequent indexing lags.
