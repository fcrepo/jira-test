Description

Develop a plan for exporting of versions against the current versioning implementation:
https://wiki.duraspace.org/display/FEDORA4x/RESTful+HTTP+API#RESTfulHTTPAPI-Versioning

Consider persistence representations of the export, ensuring that it would retain sufficient information for round tripping. Also, consider the implications of the changes to the versioning specification in the upcoming memento based API, with an eye towards allowing for import into future versions of Fedora:

https://fcrepo.github.io/fcrepo-specification/#resource-versioning

Ben Pennell, 2017-05-18 14:09 UTC

Versions would be stored in a new subdirectory, which would be a sibling to the exported object, "<objid>.versions".  Within this directory would be folders for each version, named "<version-created-timestamp>(-<version label>)", which would contain the entire subtree of the object and its children, in the same format as a regular export.

Ben Pennell, 2017-05-19 14:06 UTC

After an initial look at implementation, a number of concerns came up about our ability to make assumptions about future versioning implementations.  For one, metadata exports of objects from f4 contain references to resources with f4 versioning internals scattered throughout (namely fcr:versions/<version label> in resource paths).  Changing paths did not interact well with the implementation of the tool, and would require translation in import tools since resource uris wouldn't match export structure.

The approach outlined below is a more straightforward dump of the f4 versioning structure.  It accepts existing assumptions of the export tool about directory structure and URIs, while containing all the information needed to import versions into other Fedora implementations, whether or not they support versioning in the same way (fcr:versions and versions would simply become resources). 

 

Export of a binary

  • file.binary # original binary
  • file # subdir for resources of the binary
    • fcr%3Ametadata.ttl # metadata for the binary
    • fcr%3Aversions.ttl # retained to hold onto fedora:created
    • fcr%3Aversions
      • version1.binary
      • version1
        • fcr%3Ametadata.ttl
      • version2.binary
      • version2
        • fcr%3Ametadata.ttl

 

Export of a container

  • 1831cj92z # subdir containing child resources
    •  children...
    • fcr%3Aversions.ttl
    •  fcr%3Aversions
      • version1
        • children...
      • version1.ttl
      • version2
        • children...
      • version2.ttl
  • 1831cj92z.ttl # metadata of the object
Andrew Woods, 2017-05-19 17:52 UTC

This second approach does seem more straightforward.

One question, are you anticipating using the literal terms "version1", "version2", etc? or are these placeholder terms for some other value?

Ben Pennell, 2017-05-19 18:46 UTC

"version1" is the version label.  This is a direct translation of the uri of the versioned resource.  So using an example with an autogenerated version label from in the admin ui:

http://localhost/rest/container/fcr:versions/version.201751610172

the export would be:

rest > container > fcr%3Aversions > version.201751610172

A child of this container would be at:

rest > container > fcr%3Aversions > version.201751610172 > child
