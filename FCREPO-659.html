Description

Currently, DOManager is responsible for creating database tables for field search, pid generator, etc. In order to reduce this unnecessarily coupling, these maintenance tasks should be the responsibility of their native modules.

Benjamin Armintor, 2015-03-06 06:24 UTC

I'm interested in this because I think there's a problem with DBPIDGenerator related to it: If it is initialized before DefaultDOManager on startup, its ability to track the highest PID assigned for a namespace is compromised.

I've got a fork for it that splits the dbspecs up into 4 batches (DefaultDOManager, DBPIDGenerator, DBPathRegistry and FieldSearchSQLImpl). This is generally sound, except that the DOManager actually uses the lastMod data column from the FieldSearch table to build one of its caches. If it were not the end of the line, I'd want to refactor that. In any case, the rest of the split looks okay:
