FCREPO-1884 WebAC acl:accessTo property requires a trailing slash when the protected resource is the repsitory root

Description

When creating a WebAC ACL to protect the repository root, you must include a trailing slash in the Authorizations's acl:accessTo predicate, otherwise the Authorization will not match the resource's path in Fedora, and won't get applied.

The desired behavior is to allow the URI to the repository root to omit the trailing slash (e.g., <http://localhost:8080/fcrepo/rest>) but still have the Authorization apply. In other words, this should be valid:

<> a acl:Authorization ; acl:accessTo <http://localhost:8080/fcrepo/rest> .

It appears that the fix for this would involve a change to Fedora's core IdentifierTranslator classes, which I am somewhat hesitant to do. A much simpler resolution would be to make the documentation clear that a trailing slash is necessary.

Technically, the URI without the trailing slash is considered an out-of-domain URI, not managed by Fedora. So, strictly speaking, in a repository-wide sense, no one should ever refer to the repository root without a trailing slash.

Unknown, 2016-03-11 01:10 UTC

I don't actually think the change to IDentifierTranslater would require too much work, though it may also be an opportunity to reevaluate our use of Guava's Converter class. If that is replaced with a simple class with two (bidirectional) {{Function}}s, the kernel-api would no longer depend on Guava (I think). I see a lot of advantages to keeping kernel-api very light weight in terms of dependencies.

And the more I think about it, it seems that repository users who inadvertently omit a trailing slash when referring to the Root resource may encounter quite a few unexpected situations. Furthermore, there is an inconsistency here – HTTP requests for the root without the trailing slash return triples whose subject contain a trailing slash. For any child container, however, the subject never contains the trailing slash, whether the HTTP request contained the trailing slash or not.

That is, I think it makes sense that references to the root resource should be considered "in domain" whether they contain a trailing slash or not.

Are all trailing-slash URIs out-of-domain? That doesn't seem right.

Unknown, 2016-03-11 16:52 UTC

No, no. All trailing-slash URIs that point to a location in the repository are in-domain. For example, these are both valid in-domain URIs:

INSERT

{ <> ex:related </fcrepo/rest/foo>, </fcrepo/rest/bar/> . }

WHERE {}

But only the first one here is in-domain:

INSERT

{ <> ex:hasRoot </fcrepo/rest/>, </fcrepo/rest> . }

WHERE {}

(The second one will be translated to an http:// URI, depending on the host and port of the request, and that HTTP address will persist across changes in the repository's domain name).

That is:
<http://localhost:8080/fcrepo/rest/some/resource> ex:hasRoot <http://localhost:8080/fcrepo/rest/> .
<http://localhost:8080/fcrepo/rest/some/resource> ex:hasRoot <http://localhost:8080/fcrepo/rest> .

But if you change the domain name, this is what you get:
<http://fedora.myhost.edu/fcrepo/rest/some/resource> ex:hasRoot <http://fedora.myhost.edu/fcrepo/rest/> .
<http://fedora.myhost.edu/fcrepo/rest/some/resource> ex:hasRoot <http://localhost:8080/fcrepo/rest> .
