FCREPO-1741 Transactions using Headers rather than URI segments

Description

A URI is the primary identifier for an object. I posit that a URI for an object should not change when you are dealing with it from within a transaction. It would be great if we could do something like this:

POST /fedora/rest/transaction
// returns a transaction token, e.g. 1001-1001-1001

POST -H "X-fcrepo-tx:1001-1001-1001" /fedora/rest/my_object

POST /fedora/rest/transaction/1001-1001-1001/commit

cb, 2015-09-18 14:37 UTC

The approach described here is not RESTful. In fact, we discussed this approach early in the development on transactions and landed on the current implementation because objects in the scope of a transaction are different than the resources outside that scope (they certainly have different caching notions, among other behaviors).

While adding a header may not be at odds with LDP, it is a capability that some LDP clients may be support or properly expose to consumers. In general, I think we were trying to cut down on magic HTTP headers, which can't be HATEOS'ed easily and usually exclude the browser from participating with it natively.

I also think exposing the transaction in the URI is a simple way to expose to the client (or user) that there is something different about this request and could cut down on some classes of error (e.g. I thought I was sending it in a transaction, but actually deleted some really important object, because i forgot a header).

I've run into what @jcoyne is describing when working through constructing PCDM objects. It is a bit surprising to have the uri change on you. Or maybe it's just the fact that the optional part isn't at the end of the uri.

I wound up with a string processing function to make sure I can construct the uris properly whether or not I'm in a transaction. I'm not particularity proud or fond of it, but it works.

I'll agree that it's a quirky part of the interface, but I also agree with the desire to keep the transaction transparent. I'm also not sure if it's worth breaking interface over.

FWIW, a query string is a simple and obvious way to express the transaction id as an optional parameter when performing CRUD operations, though I doubt that would be a popular amendment to the API.
