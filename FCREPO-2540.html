FCREPO-2540 Possible memory leak in org.fcrepo.event.serializer.JsonLDSerializer

Description

Analysis of the heap dumps during a load process that created 7000+ objects in the repository demonstrated a possible memory leak in the org.fcrepo.event.serializer.JsonLDSerializer class.

The ObjectMapper used by that class is accumulating what looks like a Jackson JSON Deserializer and Serializer object for each event created by fcrepo. These objects are each about 1MB in size, but are never cleared out of the ObjectMapper. This lead to the ObjectMapper retaining approximately 456MB of heap space during the load process. See jsonldserializer-memory.csv for the tracking of that growth across the 4 heap dumps. Heap dump 1 occurred about 7 minutes after the start of the load, and heap dump 4 is just after then conclusion of the load.

See [^memory-analysis-20170721T105651.png] for a screenshot of the top dominator objects from the fourth heap dump.

Original fedora-tech thread: https://groups.google.com/d/topic/fedora-tech/oAwFFHaRu8Q/discussion

Aaron Birkland, 2017-07-21 21:38 UTC

It looks like 4.7.0 has some sort of Jackson-related memory leak, but 4.7.4-SHAPSHOT doesn't.

What I did:

  • Write a script that endlessly issues PATCH requests against a resource
  • Attach a listener which receives messages, and dumps to /dev/null
  • Monitor the memory with jvisualvm

What I found:

  • Using 4.7.0, memory slowly crept up.  In 10 minutes, the heap (i.e. the things that don't go away after GC) increased from 141MB to 203MB.  The top culprits were HashMap$Node and com.fasterxml.jackson.databind.type.ClassKey
  • Using 4.7.4-SNAPSHOT, memory basically stayed constant.  in 15 minutes, the heap went from 69.2MB to 69.6MB. None of the above noticed classes remained in heap in any significant amounts.

Things of note:

  • I used a STOMP to consume messages, for what it's worth
  • I used the standalone jetty console jar on Windows 10, with no arguments, jvm flags, or system properties.  Just the defaults.

Peter Matthew Eichman, 2017-07-24 22:28 UTC

It's possible that I was misreading the information on the ring buffer in the heap dump. I took the subscript to be the number of objects it contains, when it was in fact the total number of slots allocated (even if they are not filled).
