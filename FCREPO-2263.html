FCREPO-2263 Reserved Characters in fragments are encoded by UriBuilder

Description

If I have an RDF body triple that looks like this:
<_:e0c3ccbf985465c1f29a63ae9532ea3e> <http://www.w3.org/ns/oa#hasTarget> <http://localhost:8080/fcrepo/rest/collection/test/009/canvas/001#xywh=0,0,2137,3293>

When the object value is created in Fedora, it looks like this:
http://localhost:8080/fcrepo/rest/collection/test/009/canvas/001#xywh=0%2C0%2C2137%2C3293

I should also point out that <http://localhost:8080/fcrepo/rest/collection/test/009/canvas/001> exists as an LDP Container prior to the update, and the hash is a schema specific identifier that is used by the client .

This happens both with FcrepoClient and directly with curl. It does not occur if an update is made directly through the UI, however.

Christopher Johnson, 2016-10-18 17:01 UTC

The percent encoding of reserved characters in a fragment problem I believe is a bug in UriBuilder.fragment().
The docs say that it supports query parameters per RFC 3986, but apparently they have not considered the possibility of reserved characters in the value of a fragment. Perhaps I raise the question to them directly?

This method is indeed used in HttpResourceConverter

The variety of hash URI creation/manipulation in core is very confusing. In the webapp, it seems that this is just using URI.create(uri) and not UriBuilder, which is why it works. Also, the "internal" (/#/..) versus "external" (/#...) representation adds a lot of complexity.
