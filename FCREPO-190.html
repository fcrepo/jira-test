Description

The current pseudo-canonicalization of inline XML (for checksum computation) is non-standard. The w3c has published c14n which defines a canonicalization, and Fedora should use this for:

1) Computation of the checksum
2) Computation of the SIZE attribute

This behavior should also be documented in the system docs.

Note that this also applies to METS.

While we're fixing FCREPO-696 Closed , it'd be nice to finally wrap this one up too. Checksums for inline XML datastreams are pretty well useless in the current state since you need to deduce Fedora's internal, undocumented, non-standard (any more adjectives?) canonicalization.

There are a few choices for c14n: inclusive and exclusive, both with or without comments. For out purposes, I believe we'd want inclusive w/ comments. If someone can lend a hand identifying various places in the code c14n needs to happen (tests would be bonus), I can provide the implementation.

Chris Wilper, 2011-01-05 19:10 UTC

I've recently had some experience with Axiom, which looks like it'd be a good library to use for this (it's been recently active, is on central, and provides the 4 standard types of canonicalization: http://svn.apache.org/viewvc/webservices/commons/tags/axiom/1.2.10/modules/axiom-c14n/src/main/java/org/apache/axiom/c14n/impl/ )

I would favor exclusive + omitting comments. People are already over-using inline XML (straining memory), so I think if people want comments in the XML they keep in Fedora, steering them toward managed content is a better approach. Also, retaining comments would require additional code in the FOXML and METS deserializers – currently, they drop comments as a side effect of parsing.

Chris Wilper, 2011-01-07 12:13 UTC

Eddie, I noticed you were using Apache Santuario (xmlsec) in fedora-client, and looked into it a bit. I actually think Santuario is a better choice because it's smaller (doesn't bring in a bunch of unneeded dependencies like axiom-c14n does) and provides a c14n11 impl (something I had previously not known about). I found this comparison of the different c14n specs at w3c helpful in thinking about it http://www.w3.org/standards/techs/xmlc14n

I now think c14n11 with comments omitted is the best option for Fedora's Inline XML.

Chris Wilper, 2011-01-07 13:26 UTC

Fyi, it turns out that some inline XML that Fedora currently accepts cannot be canonicalized. The case I've noticed so far is when an XML namespace is declared and the "URI" is given as relative. For example:

<myns:doc xmlns:myns="a-relative-uri"/>

I've tried this both with Axiom and Santuario, with c14n and c14n11. Both fail with: Element myns:doc has a relative namespace: myns="a-relative-uri"

Note that this is a well-formed XML document when parsing doesn't care about namespace, but c14n needs namespace declarations to be absolute.

There may be other kinds of inline XML that Fedora accepts today which cannot be canonicalized. I just noticed this one because the case occurs with a lot of the demo Service Deployment objects' WSDL datastreams. (<wsdl:definitions xmlns:this="bmech" ..>..) This should of course be addressed in these demo objects for future releases, but also need to decide what to do about other such objects that people no doubt have lying around in their repositories.

A couple options I can think of include:

1) Start rejecting non-canonicalizable inlineXML as soon as this feature is implemented. This would require we come up with a way for people to repair old sdeps and any other non-c14n-able FOXML in their repository.

2) Add a new attribute to stored FOXML, indicating that the inline XML is canonicalized (and will be provided as such on every request to get it). (e.g. <xmlContent C14N="c14n11">...</xmlContent>. This would require a new release of the FOXML schema.
