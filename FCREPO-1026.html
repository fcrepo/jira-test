Description

Currently validation is somewhat configurable: A custom validation module could be written and configured in fedora.fcfg.

This isn't that flexible as it means that if the existing validation was also to be carried out, then that would need to be called by the custom validator. A better design pattern might be something like the management Decorator pattern we already used.

We also might consider allowing validators to operate on the digital object, rather than a file or inputstream - it may be more convenient for the validator to access the object itself rather than FOXML.

We perhaps also might distinguish between different types of validation, eg validation of the FOXML vs validation of the object - the FOXML is a serialisation of the object, it is not the object itself.

Existing validation on doCommit() (DefaultDOManager) only happens in debug - but the validator is invoked on ingest separately.

The existing validation could be refactored so that the XML validation and schematron validation become decorator implementations.

We should also consider relationships validation (which is carried out by the ValidationUtility, and not included in the DOValidatorImpl).

Perhaps the REST validate endpoint could also be extended (and configurable) to validate using the above as well as the current ECM validation.

Stephen Bayliss, 2012-01-25 21:52 UTC

My thoughts on implementing this are:

  • Existing FOXML validation on ingest (and when committing object if in DEBUG):
    • improve configuration options to select which validation (XSD and/or Schematron) get run at each point (ingest, commit to object store)
  • New DigitalObject-based validation - new module (configure via spring) to hook into new interface DOObjectValidator in current doCommit() - this for instance (with some fairly minor code changes) will allow the ECM validator to be plugged in to validate on ingest (as configuration option, of course!).

As part of this tackle the current Schematron validation lack of caching the prepared stylesheet - for which there probably should be a different issue. Tests showing this can range from 20% to 50% of DefaultManagement.ingest time

Stephen Bayliss, 2012-02-02 13:42 UTC

Current implementation in fcrepo-1026 branch, and proposed documentation at https://wiki.duraspace.org/display/FEDORA36/Validation

Outstanding issue: HTTP status codes - current foxml validation error results in a 500. A 400 code (perhaps 422, but this is a webdav extension so could be regarded as non-standard from a purist REST standpoint, though people do use it) would be more appropriate.

Would this constitute a breaking change for the REST API? One could argue the case that the current 500 codes for validation errors are in fact a bug, as it's not a server error.
