Osman Din, 2015-02-16 19:35 UTC

I think we should update the Sonar checkstyle/puppycrawl rule value to a higher number (15?) or disable the rule altogether because:

1) The instantiation operations in question seem to be mostly for exceptions and JDK data structures. Do things really need to be more flexible, e.g. by using DI and making different bindings (via XML) possible? Probably not.
2) Really 'complex' classes would most likely be caught in a code review, and I'm not sure sure how much value an automated analysis on this specific design case brings to the table.

It does seem, however, that the rule does indirectly catch instances where the new operator is being used excessively. So, if we want to disable this rule we should probably check if some other 'new'-catching mechanism exists (assuming if it's an issue at all).

Andrew Woods, 2015-02-17 15:13 UTC

I agree that the "exceptions" that are included in this metric should be excluded. However, the classes that are flagged are some of the most complex classes in the codebase and should be refactored... although probably not as an immediate-term priority.
If you would be interested in investigating how to exclude "exceptions" from the com.puppycrawl.tools.checkstyle.checks.metrics.ClassDataAbstractionCouplingCheck, that would be helpful.
Otherwise, I will keep this ticket alive, but move it out of the current sprint.
