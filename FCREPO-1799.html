Description

When doing some testing, I came across an error condition when trying to add a triple with a predicate that starts with an integer to an existing Fedora container. This can be replicated from Fedora's default UI. This SPARQL INSERT statement works fine:
==================
PREFIX bf: <http://bibframe.org/vocab/>
PREFIX cc: <http://catalog.coloradocollege.edu/>

INSERT

{ <> bf:relatedTo cc:1234 }

==================

This very similar SPARQL INSERT statement fails (but succeeds with Blazegraph):
==================
PREFIX bf: <http://bibframe.org/vocab/>
PREFIX cc: <http://catalog.coloradocollege.edu/>

INSERT

{ <> cc:1234 "anything" }

WHERE {}
==================
See: https://github.com/fcrepo4/fcrepo4/issues/924

Esmé Cowles, 2015-11-04 21:25 UTC

I think the main issue here is that the current specs allow the local part of QNames to start with digits, but Jena's URL parsing assumes that they do not. Jena's implementation is following the XML namespace spec, which is somewhat more strict about QName:

https://github.com/apache/jena/blob/master/jena-core/src/main/java/org/apache/jena/graph/Node_URI.java#L73

Even if the Turtle spec allows it, accepting URIs where the local part started with a digit would mean that the RDF couldn't be serialized in valid RDF/XML.

So I'm torn about which would be the better approach:

1. Adding a check for empty local parts and throwing an exception. This would be very easy.
2. Stop using Jena's namespace parsing and use our own instead. This would be more involved, and would allow creating properties that we could not serialize as RDF/XML (so we'd need to catch that error too).
