Fedora behind SSL/TLS termination proxy

Description

Links to UI assets (css, js, etc) are always http, even if the repository is behind an SSL termination proxy, and the X-Forwarded-Proto header indicates https.

Suggestions on on the table include allowing the protocol in hyperlinks to be relative, configurable, or reactive to X-Forwarded-Proto.

Andrew Woods, 2017-07-13 22:00 UTC

Actually, I do not believe that UI assets are always http, but rather the base URL used to serve those assets are the same as the requesting URL.

In the case of https://github.com/fcrepo4/fcrepo4/pull/1208 , the proxy_pass directive is requesting http resources:

> proxy_pass http://c1mckay-sgki99-fedoraerror-8080;

Aaron Birkland, 2017-07-13 22:25 UTC

The proxy_pass is correct for a termination proxy;  It's accepting TLS requests from the outside world, decrypting (TLS/SSL termination), and proxying the requests to Fedora unencrypted. 

The user/browser in the outside world is using https, but gets back html that says:

<script type="text/javascript" src="[http://sgki99-fedoraerror.workbench.nationaldataservice.org/fcrepo/rest/fcr:assets/common.js]"></script>

That's an unencrypted http link.  The baseuri is good except for protocol, which does not match the original request (which was https).  The browser is refusing to load it because it is violating the mixed content rule.  In order for it to work, one or more of the following needs to be true:

  • HSTS and/or CSP directives instruct the client to ignore stated protocol and always uses https
  • The link in the html is https instead of http
  • The link is relative, so the browser uses the same protocol as the initlial request (http)

Esmé Cowles, 2017-07-13 22:52 UTC

Aaron Birkland, 2017-07-13 23:22 UTC

In general, all a reverse proxy does in terms of rewriting occurs in http headers.  The entity bodies are considered opaque and are unmodified (except for stuff like decrypting, transfer encoding, and other transport-related stuff).  This is very lightweight.

The problem is that links within the documents fedora produces (in this case, the html for the UI) contain plain links.  Inspecting those documents and modifying them (e.g to re-write URIs) is a specialized task, requiring knowledge of the media types, etc.  Essentially you're piping the response through a specialized grep   I know nginx and apache also have modules that can do that too.  The problem is that this is more heavyweight and resource-intensive than simple proxying.

For something as simple and straightforward as TLS/SSL termination, usually the expense of re-writing entity bodies is not justified.  That's why headers like X-Forwarded-Proto exist:  So that they can give the web apps the information they need in order to create a document that doesn't have to be rewritten.  So it would be a win if Fedora supports that.
