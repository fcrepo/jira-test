FCREPO-497 Content disposition header for filename.extension downloads of datastreams

Description

Suggested by Matt Zumwalt at OR09:

To allow people to use a preferred filename and extension when downloading datastreams from Fedora, the REST API should provide a Content-Disposition HTTP header that includes the preferred filename and extension. The filename can come from the datastream label, if provided. The extension can either come from the datastream label (if provided), or a mime-type-to-extension map that's configurable on the server.

Stephen Bayliss, 2009-11-20 11:35 UTC

I think there are three potential scenarios here, which could depend on the context in which the resource is served:

1) disposition is to be determined by the browser, based on the content-type header, which is what will happen at the moment
2) disposition is to be determined by the browser; however if the user instead explicitly wants to save the content (ie "save link as"/"save target as") then a filename should be provided
3) disposition is explicitly to download, providing a filename.

To force a download with a filename, content-disposition should be set to 'attachment; filename="name.ext"' [1][2] which covers (3). Theoretically (2) is covered with 'inline; filename="name.ext"' however in practice some browsers tend to ignore the filename in this case [3].

I think setting this header should be under the control of the application - ie a parameter on this URL (eg "setContentDisposition=true" or "download=true") so that both "open" and "download" links can be provided by the application as required.

For the filename, I'm not comfortable with using the datastream label alone, as this has different semantics - however it could default to the datastream label if no filename is defined.

The filename+extension could be defined as a new datastream property - or we could make use of RELS-INT for this, eg specifying info:fedora/demo:123/DSID ns:downloadFilename "myfile.ext". (It would be nice to use an existing vocabulary for the relationship, such as [4], but as this specifies the header as a class rather than a property we couldn't use this within the existing RELS-INT validation rules).

Where no filename is explicitly specified, I'd suggest
1) if there is a datastream label, use that as the filename, determine extension as below
2) if there is no datastream label, use the datastream ID as the filename. If the datastream contains "." then the filename + extension should be the datastream ID. If the datastream ID doesn't contain "." then determine the extension as below.

(I believe people are currently using dsIDs such as "filename.ext" as most browsers will generate a download filename based on what's after the final "/" in the URL - so this is for consistency with existing behaviour)

For the extension, rather than defining a mime-type-to-extension map, I'd suggest using web.xml - although this does give a one-many mapping between mime-types and extensions it could default to the first extension specified for the mime-type.

(as an aside - browser treatment of content-disposition has not always been entirely consistent - and I believe there are cases where it's also necessary to specify a content-type of eg application/octet-stream to force the download [5])

[1] http://www.ietf.org/rfc/rfc2183.txt - 2. The Content-Disposition Header Field
[2] http://www.rfc-editor.org/rfc/rfc2616.txt - 19.5.1 Content-Disposition
[3] http://stackoverflow.com/questions/381890/securly-download-file-inside-browser-with-correct-filename
[4] http://www.w3.org/TR/HTTP-in-RDF/ and http://www.w3.org/2006/http.rdfs
[5] http://n4.nabble.com/File-Download-XForms-IE7-tt42785.html#a42787

Chris Wilper, 2009-11-21 06:59 UTC

I like the idea of the download=true param to give the linking website/page an opportunity to force a Save As... prompt right in the request url.

I see your point about datastream label not really being intended as a filename, but absent an additional field that specifies a particular filename to use, I think it would act as a good fallback. Certainly a better fallback than DSID. So I think we're in agreement on the preference-order for where the filename comes from.

RE: web.xml for mapping. Thinking about this vs an external file (say, in $FEDORA_HOME/server/config), I guess I don't feel too strongly either way. I see the benefit of the way it's defined in web.xml being somewhat standard. However, changing what's in web.xml seems somewhat more of a hassle than changing a simple text file for that purpose. Ultimately, I guess such a mapping could come from some sort of management object in the repository. But figuring out the "best place" to store this mapping is something that could be done after making something simple work.

RE: a "preferred filename" property. I think you nailed it, that it's a choice between versioning the FOXML (and METS, and AtomExport) schema to add that, or doing it via RELS-INT. Whenever it comes to adding a new property, I tend to lean the RDF way myself, because versioning XML schemas is always such a clunky proposition. As you mentioned, this means either choosing an existing predicate in the wild or minting our own. I could go either way on that. Two other things to consider on the RELS-INT front: 1) since it would be a fedora-recognized property, do we attempt any validation on the value?, and 2) the asOfDateTime of the original request is probably significant here: I think we'd probably want to use the RELS-INT as it existed at that time.

Meta-statement about this feature in general: How about breaking it into three phases?

Phase I:
For all GETs on datastream content:
+ Add 'inline; filename="foo"`content-disposition
+ Determine filename using DSID, with extension-guessing as described above
+ If ?download=true, use 'attachment; filename="foo"'

Phase II:
For all GETs on datastream content:
+ Prefer to use the datastream label as the filename. If undefined, fallback to DSID as described above.

Phase III:
+ Figure out how a new filename property will be defined and resolved for a given ?asOfDateTime GET request on a datastream.
+ Determine whether + how this should also be provided when people GET the datastream profile
+ Consider storing it in the RI (automatic if the choice is to express it in RELS-INT)
For all GETs on datastream content:
+ Prefer to use the filename property as the filename. If undefined, fallback to label as described above.

I'd suggest we go ahead and implement it, but not document any commitment to it working; avoid setting expectations and then getting lots of reports of problems that we can't actually solve.

I think I can see what you're getting at with the version of RELS-INT now - if version 1 of a pdf were uploaded, and a filename of "report v1.0.pdf" specified, and then this is replaced by version 2 with a filename name "report v2.0.pdf" then it could be useful to ensure that the user gets the appropriate filename for the version they download.

One fairly significant issue here is that the API-M methods for relationships do not include asOfDateTime as a parameter; so the API doesn't currently support this. So to implement this properly it would also mean (breaking?) changes to the API which we probably don't want to do at this time.

So do we go forward with with the current RELS-INT view; raising a JIRA issue for this; and clearly documenting this?

An alternative could be to add additional methods to the API - these would be the generic "arbitrary RDF datastream manipulation" methods that have been discussed with regards to the REST API. (something like [get|add|purge]DatastreamRelationships). Though theoretically the existing relationships methods should still be modified in a future (major?) release to add asOfDateTime.

On "inline", I'd propose adding it to the header so that those browsers that do support picking up the filename for inline content when a user chooses to download it can use this; but setting expectations - stating that it's not generally supported by all browsers (it is only specified in rfc2183 for internet messages, and not rfc2616 for HTTP).

Stephen Bayliss, 2009-11-25 13:56 UTC

Implemented as follows:

Configuration:

Originally we discussed deriving the filename from (in order) RELS-INT, the label and the datastream ID. However I believe there are people who, recognising that currently the datastream id will be used as a filename by the browser on download, have included extensions in some of their datastream IDs. So I've made it all fully-configurable; it might be a bit over-the-top, suggestions welcomed on simplifying this if you feel necessary.

Potential sources for filenames for the content-disposition header are:
RELS-INT
Datastream Label
Datastream ID

These (or a subset) can be specified in any order in fedora.fcfg - the initial setting is per the order we originally came up with.

Additionally, for each source, you can configure whether or not to determine a file extension from the mimetype-to-extensions mapping file - for instance in the case of a label which would normally be a textual description, you would want to do this. But where you're asserting the filename in RELS-INT you may prefer to include the extension in that name. And for datastreams that may have already been set up to include an extension in the name you might want to only determine the extension if there's not already one present in the ID.

Potentially the configuration in fedora.fcfg could be simplified by combining the source order configuration and extension configuration into a single value, eg "rels|never label|always id|ifmissing". Feedback welcomed.

Mapping file:

This is in the server config directory. This is based on a trimmed-down Tomcat web.xml; potentially we may want to supply something much smaller with just a few of the most well-known extensions/mimetypes?

Code organisation:

I've hived off all the new logic into a new class; arguably it could instead be part of BaseRestResource and/or DatastreamResource; feedback welcomed. The mime-to-extensions mapping ArrayList is implemented as static - the REST classes get instantiated for every invocation so this is to avoid repeatedly reading this

Outstanding issues:

Relationships API currently only supports the latest version of RELS-INT (not asOfDateTime); so filenames specified there will always be returned as the latest (rather than the one specified at the time).

Predicate to use in RELS-INT: I've used hasDownloadFilename in the fedora relationships namespace - not sure what we want to use here, should this be in the model namespace?
