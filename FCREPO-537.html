Description

The error occurred again, and this time we are able to reproduce it. As
far as I can tell, it looks like when Fedora checks and verifies that a
foxml file is well-formed, it then creates a stub object, then checks
the datastreams. If validation of the datastreams fails under certain
conditions, Fedora returns an error, but leaves the stub object in the
file system and in the database.

To reproduce this:
The steps to reproduce the error are (using attached files)

1. Compare the content of DemoFail.xml and DemoSuccess.xml. They should
differ only in the location of the attribute xmlns:xlink: on the element
<foxml:digitalObject> (DemoFail) or <mods:mods> (DemoSucess).

2. Ingest object demo:failObject from DemoSuccess.xml; it should be
successful.

3. Purge the object demo:failObject.

3. Ingest object demo:failObject from DemoFail.xml; it will fail because
of the location of the xlink namespace declaration.

4. Since the object was not ingested, try to repeat step 2. It will fail
with an ObjectAlreadyInLowlevelStorageException. At this point, you can
neither ingest nor purge the object demo:failObject.

Comments (2)

Aaron Birkland, 2009-10-06 22:55 UTC

Certain defects in an object can get past the object validation stage of Ingest, and cause errors only upon reading and deserializing from storage. In this case, the specific defect is declaring an XML namespace outside of an inline XML datastream where that namespace is referenced.

The sequence of events leading to the error are as follows (all occurring within the scope of ingest)
1) Object passes validation
2) Triples are saved to RI
3) Object is saved to storage and registry
4) Object is loaded from storage and deserialized for the purpose of populating FieldSearch
5) Exception is thrown in deserialization process
6) Rollback procedure is initiated - it is supposed to clean up RI, registry, and storage
7) In clearing the RI, the object is read from storage to determine triples to delete
8) Exception is thrown, cleanup process is aborted as a result. Triples, object XML, and registry entry are intact
9) Fedora reports failure of ingest

Aaron Birkland, 2009-11-25 20:20 UTC

Fixed the obvious un-recoverability problem by removing unnecessary retrievals from storage, instead relying on already known/retrieved/submitted data. Added a validating deserialization step to discover errors in a controlled fashion and provoke a failure upon ingest. The changes end up balancing out as far as performance, with the submitted fix perhaps achieving a very slight performance increase

Used a live system test to verify fix, in configB only. DOManager itself is a bit too unweildy to test with an offline test without a significant amount of effort.
