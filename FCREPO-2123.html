FCREPO-2123 Tombstone Content-Type is incorrect

Description

When you retrieve an URI at which a tombstone is present, you get

Discovered tombstone resource at /foo

{jcr:createdBy=bypassAdmin, jcr:primaryType=fedora:Tombstone, jcr:created=2016-08-24T14:24:58.099-04:00}

You get this even if you put an RDF mimetype into the Accept header of the request.
1) There should not be any JCR cruft in there.
2) There ought to be a real RDF response when one is asked for.

OR

We should just get rid of tombstones (I really think this is what we should do.)

Andrew Woods Part of what is described in this ticket has already been resolved in other efforts (i.e. the JCR serialization "cruft"). From the current master, I get this in the response for a deleted resource:

    HTTP/1.1 410 Gone
    Server: Apache-Coyote/1.1
    Link: <http://localhost:8080/fcrepo/rest/deleted/fcr:tombstone>; rel="hasTombstone"
    Content-Type: text/turtle
    Content-Length: 82
    Date: Thu, 27 Oct 2016 23:11:50 GMT

    Discovered tombstone resource at /deleted, departed: 2016-10-13T09:38:45.614-04:00

What I would propose is this: reworking this PR so that the response type is text/plain (rather than text/turtle – which it clearly isn't) and omitting the change to the link header. I do think that link header is incorrect, but I agree that it should wait on the API specification effort.

Also, we should note somewhere (in the context of the API specification effort) that the link headers for tombstone and other resources should have fully qualified link relations if those relations aren't defined by IANA.

Unknown, 2016-10-27 23:32 UTC

The PR for the change to the ontology has been closed, pending consideration by the API specification effort.

The PR for fcrepo4 has been reworked so that it does not change the serialization of tombstone responses or the link headers, but it does fix the clearly incorrect Content-Type header. The details of the serialization should be based on recommendations by the API specification effort, and any changes to that should wait until then – at which point we may want to either re-open this ticket or create a new ticket.
