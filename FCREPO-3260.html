Description

This task is to add content to the Fedora 6 System Administration wiki docs that details the known limitations for known OS platforms... and have clear points of configuration for Fedora installations that can not fit within those limitations.

Source materials for documentation:

  • https://github.com/UW-Madison-Library/ocfl-java/blob/master/ocfl-java-core/src/main/java/edu/wisc/library/ocfl/core/path/constraint/DefaultContentPathConstraints.java
    ￼
  • https://github.com/OCFL/spec/issues/407#issuecomment-553561928

From Slack:
In regards to https://github.com/UW-Madison-Library/ocfl-java/issues/4
ocfl-java's behavior by default is as follows:
Maps logical path directly to content path
Stores the file at the content path
Throws an exception if it can't write the file to content path due to file system restrictions (such as file name length)
If you add content path constraints it behaves as follows:
Maps logical path directly to content path
Applies content path constraint
Throws an exception if the content path does not satisfy the constraints
In this case, you could modify the logical path on the application side so that it can be directly mapped to a content path. For example, shortening file names or removing special characters.
Finally, you can provide custom path sanitizers. When you do, it does the following:
Passes the logical path to the sanitizer, which returns a safe content path
Applies any configured content path constraints
Attempts to write the file to the content path
This is essentially the same thing as the example using just the content path constraints, except that the code for cleaning up logical paths is executed within the ocfl client rather than outside of it.
Why doesn't ocfl-java make safe logical -> content mappings by default? Because, I don't want it to make assumptions about what portions of a file name are important to users.
