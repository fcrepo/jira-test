FCREPO-1760 WebAC: Non-Admin user gets 404 if target has versions

Description

When using WebAC, if a non-admin user tries to access a resource to which that should have permission AND that resource has versions, a 404 is returned.
Note: admin users have no issue.

To reproduce:

  • Create acl/authorization:
    ===========
    PREFIX acl: <http://www.w3.org/ns/auth/acl#>
    PREFIX pcdm: <http://pcdm.org/models#>

INSERT

{ <> a acl:Authorization ; acl:accessToClass pcdm:Object ; acl:mode acl:Read, acl:Write; acl:agent “testuser” . }

WHERE { }
===========

  • Create a resource of type "pcdm:Object" and link to the acl:
    ===========
    PREFIX acl: <http://www.w3.org/ns/auth/acl#>
    PREFIX pcdm: <http://pcdm.org/models#>

INSERT

{ <> a pcdm:Object; acl:accessControl </fcrepo/rest/my-acls/acl> }

WHERE { }
===========

  • Create a version of the resource
    ===========
    curl -ufedoraAdmin:secret3 -i -XPOST -H"slug: v0" localhost:8080/fcrepo/rest/resource/fcr:versions
    ===========
  • Access the resource as "fedoraAdmin" – works
    ===========
    curl -ufedoraAdmin:secret3 -i localhost:8080/fcrepo/rest/resource
    ===========
  • Access the resource as "testuser" – FAILS with at 404
    ===========
    curl -utestuser:password1 -i localhost:8080/fcrepo/rest/resource
    ===========

Michael Durbin, 2015-10-27 14:11 UTC

Is the jcr namespace bound to ns001? That seems odd to me, but perhaps things have changed since I last explored this area.

As for versioning, it's laid out here (http://www.day.com/specs/jcr/2.0/15_Versioning.html), but basically when you create a version it adds a mixin "mix:versionable" then uses the jcr version manager to create a version snapshot. The copies of the content exist in the system space "/jcr:system/jcr:versionStorage". The fedora 4 implementation does a lot of funny business to make those nodes (in the system space) addressable at URIs of the pattern "/original/node/path/fcr:versions/version-label".

I could imagine an issue if the ACL code makes standard JCR assumptions and invokes node.getParent() or something like that.

If we had the line number where the caught exception is thrown that results in the 404 (or the line where we check whether a node exists) it would be easier to debug the issue.

Andrew Woods, 2015-10-28 22:02 UTC

The RdfStreams are lazy-loaded. In other words, the content of the various streams are only read when they are used (i.e. when creating the HTTP response). The RdfStreamingOutputProvider shows the error because it is the code that is running through the lazy streams. The actual access error is coming from the VersionsRdfContext... when its stream is actually read.
