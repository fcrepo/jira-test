Description

This task is to test the new feature from ModeShape that support many children resources of the same parent (once it has been released):
https://issues.jboss.org/browse/MODE-2109

This should include comparison performance tests, and
clarification of how versioning can still be used.

Comments (10)

Andrew Woods, 2015-08-28 14:03 UTC

ModeShape 4.4.0 has been released.

Esmé Cowles, 2015-11-06 14:25 UTC

Following the directions in the Modeshape wiki:

https://docs.jboss.org/author/display/MODE40/Large+numbers+of+child+nodes#Largenumbersofchildnodes-Unorderedlargecollections

I've updated the CND file to include the new Modeshape unordered collections and I'm experimenting with creating large numbers of children under a single node with both the default type, and with a node with the mode:unorderedHugeCollection mixin added. I also plan to test some of the others to see how they handle increasingly large numbers of child nodes.

Esmé Cowles, 2015-11-10 16:22 UTC

I've created a wiki page for my test results which I'll update as tests continue:

https://wiki.duraspace.org/display/FEDORA4x/Modeshape+Unordered+Collections

The two smaller unordered collection types (mode:unorderedTinyCollection and mode:unorderedSmallCollection) look like they are scaling much better than the existing default container.

Esmé Cowles, 2015-11-24 19:55 UTC

I've updated the wiki with my most recent test results:

https://wiki.duraspace.org/display/FEDORA4x/Modeshape+Unordered+Collections

I'm seeing failures at around 300K objects, even with different kinds of containers, different levels of hierarchy, etc. That said, the mode:unorderedTinyCollection and mode:unorderedSmallCollection do perform better than the other options.

Andrew Woods, 2016-03-02 23:40 UTC

Is there any more work you plan on putting into this, Esmé Cowles?

Esmé Cowles, 2016-03-04 15:38 UTC

Andrew Woods: No, I think my tests basically wound up finding that the mode:unorderedSmallCollection is a reasonable improvement over the current default behavior, but no silver bullet for the scalability problems we've seen with large numbers of children under a single node.

We could add mixins users could add to a container to trigger the different collections, like this commit: https://github.com/fcrepo4/fcrepo4/commit/e14950b303e8ac5c0cd6d4ed950f5c5bd1987db7
