Stephen Bayliss, 2010-05-18 15:53 UTC

Suggest that a Fedora 3.4 implementation should at least replicate the functionality available via the SOAP API methods addRelationship, deleteRelationship, getRelationships.

Note that the SOAP API conceptually treats all relationships for an object as a whole - there's no differentiation between RELS-INT and RELS-EXT relationships (potentially this could be extended in the future to modify eg DC relationships). (The API calls currently perform some mediation based on the subject to determine if a relationship is in/for RELS-INT or RELS-EXT).

REST implementation

Resource URI:
/fedora/objects/

{pid}/relationships

This identifies all relationships for the object (RELS-EXT, RELS-INT, DC, object properties, datastream properties).

This is effectively the URI of a collection of relationships.

Potentially individual relationships could be identified using a syntax such as
/fedora/objects/{pid}

/relationships/subject/predicate/object/objectType
But this would get pretty ugly with URI encoding, so this is not proposed.

HTTP Verbs:

GET

  • return all relationships
  • return a subset of relationships by providing query parameters eg for Subject, Subject + Predicate
    Q: Is this an acceptable use of REST and GET (using query parameters in this way?)
  • provide query parameter for the format of the results (initially RDF/XML, could extend to other formats)

PUT

  • the intended use of PUT seems to be replace everything at the URI - so this would not seem applicable

POST

  • from Wikipedia, this is "create a new entry in the collection", but elsewhere the definition seems quite a lot broader (see for example http://www.elharo.com/blog/software-development/web-development/2005/12/08/post-vs-put/)
  • it would seem therefore to be acceptable to use this for adding and deleting relationships

Format for updates:

  • POSTing an RDF/XML document (specifying content type) would add
  • would we want to support POSTing an RDF/XML document for deletions, for instance by specifying a query parameter?
  • POSTing SPARQL/UPDATE (http://www.w3.org/Submission/SPARQL-Update/)
    • suggest we only implement INSERT DATA and DELETE DATA (specifying explicit triples to add and delete)
    • what content type to use for the POSTed data?

DELETE

  • delete entire collection - don't implement

Still to think about

  • HTTP response codes
  • responses from the methods

Implementation

  • aim for some generic implementation code that could be used (writeable methods for example) to perform generic updates on RDF datastreams
eddie, 2010-05-19 19:15 UTC

On yesterday's call, we talked about supporting something like the following for the request syntax:

http://localhost:8080/fedora/objects/

{pid}

/relationships/

{subject}

/

{predicate}

/

{object}

I had assumed URL encoding the path params would be sufficient to accommodate this, but then I came across:
http://tomcat.apache.org/security-6.html#Fixed_in_Apache_Tomcat_6.0.10

So in order to support this request syntax, Tomcat users would need to set
org.apache.tomcat.util.buf.UDecoder.ALLOW_ENCODED_SLASH to true (false by default)

So, setting this param to true lets us have the request syntax we want at the cost of: 1) the potential security issue this fix was supposed to address and 2) minor hassle of having to set an additional system property (e.g. add it to JAVA_OPTS along w/ the ssl props)

I don't know what the situation is w/ other containers.

eddie, 2010-05-20 02:20 UTC

I saw that discussion too. As far as I can tell the reporter never did open an issue (did a few searches on the Tomcat Bugzilla). I've also seen reports of this same behavior in Glassfish and Grizzly.

In Tomcat, if ALLOW_ENCODED_SLASH is false, the servlet never sees the request. Setting it to true at least passes the request through, but as noted, already decoded. I did have a functioning workaround by double-encoding the slash, e.g. "info:fedora/demo:1" as "info:fedora%252Fdemo:1" but that's just silly and would be mangled in a correctly behaving container.

For the time being, I've committed a strawman impl that uses query params in lieu of path params.

Stephen Bayliss, 2010-05-20 08:58 UTC

How annoying...

This means that there's also a problem with the LITE APIs - as PIDs allow octet-encoded characters (the example being converting a Handle to a PID, encoding a slash as %2F), and the LITE APIs require the PIDs in the path not to be escaped.

So with Tomcat, path parameters will never work (unless they fix this behaviour) - either the slash (and request) will be disallowed, or it will be incorrectly decoded by Tomcat into a path separator.

And the only Tomcat-friendly path parameter solution would be some alternative non-standard encoding. Double-encoding I don't like either... Base64 encoding? Replace slashes by octet-encoded backslashes? All starts to become a bit hack-ish.

Going with query parameters is probably the best way to go for now, as it means we can get this useful functionality out there - the most important thing.

We can always add a more REST-ful implementation in the future. Not going with path parameters, but allowing POST/PUT of documents to the objects/pid/relationships URI, containing specification triples to add/delete etc.

I guess I'm a bit uncomfortable with using query parameters and POST/PUT/DELETE-ing to the relationships resource as it starts becoming less REST-ful - specifically what's the resource being addressed by GET/PUT/POST/DELETE when the SPO is specified by query parameters?

I wonder if we should make an explicit non-REST-ful statement with this implementation: possibly introduce non-REST-ful endpoints, maybe a relationships/modify for POST/PUT/DELETE, and relationships/query URI for GET.

Or maybe we just make it clear in the documentation that using SPO query parameters on the relationships resource is not strictly REST-ful and that a more REST-ful addition to the implementation is to follow...
