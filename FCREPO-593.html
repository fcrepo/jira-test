Description

Rebuilding the resource index fails due to null pointer exceptions. This appears to be traceable to the fedora classes being loaded by the bootstrap loader (via the endorsed override), which causes calls to Class.getLoader to return null ( see http://java.sun.com/javase/6/docs/api/java/lang/Class.html#getClassLoader%28%29 ).

Chris Wilper, 2009-12-08 13:39 UTC

Just some more thoughts on this:

This reason this is now happening (vs with 3.2.1) is that the server classes are now put into the war as a .jar in lib/, and not in classes/ – so they're loaded via the bootstrap loader.

The java.endorsed.dirs hack in the scripts was really just a way to get around the need to specify each .jar that might be needed in WEB-INF/lib. Java 6 now allows one to specify a pattern for jars to include in the classpath, but since we're still Java 5-friendly, we can't rely on this capability. If we could, I would certainly favor it.

Two other options for avoiding java.endorsed.dirs, to exclude from consideration:
1) Hardcode the lib filenames in the server jar's manifest.
2) Hardcode the classpath in the scripts
Both of these wouldn't be good options because we don't know all the filenames beforehand...for example, the user may be using a different JDBC driver than we had anticipated.

So this leaves two options:
a) Dynamically build up the classpath within the scripts (.sh and .bat), based on the content of lib/
b) Modify the code to use Class.forName and (required for the SQLRebuilder case) somehow get a robust reference to an appropriate classloader.

It seems like other people may done a)...I'm going to look around and see what I can find.

Chris Wilper, 2009-12-08 14:58 UTC

a) wouldn't work very reliably because the length of a single command (or environment variable) in windows is limited to ~8k. Consider that we've got ~115 jars in lib/ and the path to each on a given user's system may well exceed 71 characters.
b) works if all we need is to do Class.forName, but I am unsure of a way to get a resource from the bootstrap classloader as a stream, as is needed in the SQLRebuilder case.

Another option:

c) just explode fcrepo-server-version.jar into /classes within the webapp when it's built (and don't put it in lib/). Basically, restore it to how it was originally. I just tested this and it works for both the RI rebuilder and SQL rebuilder, with Mulgara and Derby, respectively.

I am still somewhat troubled by the use of the bootstrap classloader here, though. As soon as we depend on a jar that needs to getResourceAsStream (or tries to get a reference to the classloader), things could still break...and then it will be out of our control. For example, if an Akubra plugin or JDBC driver that was used for rebuilds happened to want to load some localized messages via ResourceBundle.getBundle(..)
