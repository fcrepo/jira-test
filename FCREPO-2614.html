Description

Responses to LDPRm HEAD and GET requests must include headers as outlined below. These headers should be returned both when the LDPRm is retrieved via timegate datetime negotiation or directly by URI.

  • link rel="timegate" must point to the LDPRv: e.g. http://localhost:8080/rest/versioned_container1
  • link rel="timemap" must point to the LDPCv: e.g. http://localhost:8080/rest/versioned_container1/fedora:versions
  • link rel="original" must point to the LDPRv : e.g. http://localhost:8080/rest/versioned_container1
  • link <http://mementoweb.org/ns#Memento>; rel="type"

Remove the following headers:
< Link: <http://mementoweb.org/ns#OriginalResource>; rel="type"
< Link: <http://mementoweb.org/ns#TimeGate>; rel="type"

Jared Whiklo, 2017-09-27 16:43 UTC

I think that the LDPRm should not be returning the Content-Location header.

This header should be returned by the LDPRv when receiving a HEAD/GET request with a Memento-Datetime header. The Content-Location header would point to the appropriate LDPRm for that Datetime. 

I got this off the pattern in section 4.1.2 of the Memento spec.

Ben Pennell, 2017-09-27 18:48 UTC

Jared Whiklo

You are correct that the response from HEAD/GET to LDPRv should return Content-Location, since the response is a memento (although I will mention that Accept-Datetime is the header which requests should include for negotiation, Memento-Datetime is included in responses).  This ticket describes the headers that should be included in any response for an LDPRm, retrieved via either datetime negotiation or direct ldprm uri.

I agree that the Content-Location header is of questionable value when directly requesting a LDPRm's uri.  But 4.1.2 does explicitly say that a memento response should include the Content-Location header, so we had left it included for both responses.  This might be a good question to ask the memento people though, to see if they feel like it is required in both methods of retrieving the LDPRm.

Ben Pennell, 2017-09-27 19:24 UTC

The specification is clear about the Content-Location being used during datetime negotiation.  It also states the the GET response during date time negotiation is a representation of the memento at the end of section 4.1.2:

   In a subsequent request, which is the same as Figure 4 but with HTTP
   GET instead of HEAD, the user agent can obtain the representation of
   the selected Memento.

What it is not clear on is if the fact that a memento has a distinct URI means that accessing the memento in different ways can produce different responses.  My interpretation was that you were effectively accessing the same resource whether it was direct or negotiated because of this language, but I think it would be useful ask.
