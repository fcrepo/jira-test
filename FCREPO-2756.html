Description

As a follow on to https://jira.duraspace.org/browse/FCREPO-2745,  the task of this story is to ensure there is a support for creating ACLs at <resource-path>/fcr:acl.   In addition to ACLs on user created resources, it should be possible to overwrite the default root acl.  However,  if the custom root ACL is removed, the default root acl should automatically be reinstated.  

Ensuring that clients have permission to alter ACLs is covered by a separate jira.

Danny Bernstein, 2018-04-19 21:45 UTC

Situ, Longshou:  we discussed the issue in the tech meeting this morning.  There seems to be some consensus on the notion that the ACLs will be stored as a child resource in  jcr:node under the resource in a way similar to time maps.  However it should not appear in the RDF of the parent resource returned on a GET to the parent.

Situ, Longshou, 2018-04-19 23:03 UTC

Danny Bernstein Thanks. I'll store it as a child resource in jcr:node under the resource in a way similar to time maps for now then. For the pathname, how about using the same pattern as TimeMap like "fedora:acl"? That is, for resource /path/to/resource/a, the ACL will be stored as child node in /path/to/resource/a/fedora:acl. With that said, it seems like we no longer need to link it to the resource with predicate acl:accessControl like "<> acl:accessControl </path/to/resource/a/fedora:acl>" and the processor should be updated to look up the ACL node directly, does it sound correct?
