Esmé Cowles, 2017-09-11 18:47 UTC

The payload headers are: Content-Length, Content-Range, Trailer, and Transfer-Encoding

Is there any benefit to omitting Content-Length and/or Content-Range?

Aaron Birkland, 2017-09-11 19:06 UTC

I think the only downside is that somebody might write a client that assumes that they're present.  Some servlet containers and/or proxies might eliminate or modify them as well (e.g. if they convert to chunked transfer encoding).  Also, if the codebase ever moves in the direction of streaming RDFSources, then we wouldn't have a useful Content-Length in the first place.

Esmé Cowles, 2017-09-14 21:05 UTC

It looks like we are sending Content-Length: 0 on HEAD responses.  Idealy, we shouldn't be sending a Content-Length header at all, but this is less than ideal.  I tried various ways of removing or setting it to -1, hoping those would disable it.  But at least with mvn jetty:run, I'm getting the Content-Length: 0 header no matter what I do.

Esmé Cowles, 2017-09-15 14:07 UTC

Tomcat (as of 8.0.34, 8.5.1) does not set the Content-Length header when responding to GET requests.  See https://bz.apache.org/bugzilla/show_bug.cgi?id=59310#c8

Esmé Cowles, 2017-09-15 14:09 UTC

I don't believe there is any action required here — there are tests to verify that the Digest header behaves the same for GET and HEAD ( FCREPO-2598 Closed ), so I think we can just close this.
