Joshua Allan Westgard, 2016-12-16 20:13 UTC

So far I've seen two distinct issues:

  1. rdf resource mismatches – these occurred when unicode-escaped characters were present in the serialized resource on disk, but not present in the turtle that Fedora was giving back. The tool should be able to deal with these characters.
  2. binary mismatches – Bethany Seeger and Jared Whiklo identified a place in the regular expression that is used to capture the SHA1 checksum provided by Fedora where variable lengths of whitespace can cause the match to fail. A fix for this is being added to PR#17.

I have confirmed that manual altering of both RDF and binary resources after export will produce a mismatch upon subsequent verification runs, so it does work at least some of the time. The issues don't seem to be fundamental, easily reproducible problems, but rather of a more subtle type that may only occur sometimes.

Joshua Allan Westgard, 2016-12-16 21:39 UTC

Jared Whiklo, when you have a chance (assuming you are still able to look at this after the sprint ends) it would be great if you could try to reproduce these errors against the current open PR branch (https://github.com/fcrepo4-labs/fcrepo-import-export-verify/pull/17).

This branch includes a fix for the problem with variable lengths of whitespace in capturing the SHA1 from the metadata, which could be the cause of the binary checksum mismatches reported in this ticket.

So far, I haven't been able to reproduce the failure of the tool to notice changes to either binary or RDF files, but the whitespace was causing Bethany Seeger's test to fail for binaries and the fix seems to have resolved it.
