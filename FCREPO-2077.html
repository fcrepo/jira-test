Description

https://wiki.duraspace.org/display/FEDORA4x/RESTful+HTTP+API#RESTfulHTTPAPI-GETRetrievethecontentoftheresource offer the "Limit" header option but no way to get the "next batch".   2. Performance of loading all of the children of a container (including the root container) can take a long time.

Unknown, 2016-07-20 12:07 UTC

Until Fedora supports LDP Paging (which, itself never made it into the LDP recommendation – it is merely published as a "WG Note" https://www.w3.org/TR/ldp-paging/), I wonder if this isn't, more like something a triplestore would be better designed to handle.

Effectively, what you're asking the repository to do is very much like "list all keys for a bucket" in Riak and other such types of non-relational databases: http://docs.basho.com/riak/kv/2.1.4/developing/api/http/list-keys/. And like with Riak, while this operation is possible over HTTP, it is not recommended for production use. This is especially true if the client reading the response buffers that data entirely in memory (if you're not processing the response as a Stream, you will eventually run into memory problems). It is precisely for this reason that the triplestore indexer excludes LDP Containment triples (it keeps resource size small), since in a triplestore you can either use inference to get the ldp:contains triples or use the inverse property fedora:hasParent.

A. Soroka, 2016-07-20 13:21 UTC

Yes, definitely this is a job more appropriately assigned to a triplestore or other index. One way to think about this as a principle: the closer to actual end-user consumption a request is formulated, the more likely it is that the request should go to some service on the asynchronous periphery of the repository-centered integrated system.

Unknown, 2016-07-20 14:14 UTC

David Chandek-Stark (old account) w/r/t "scaling", you need to be more clear about why the current behavior doesn't scale. If you are trying to read the entire response into memory (which IIRC active-fedora does), then no, that won't work. But that's because of how the response is read, not because of how the response is produced. Traversing the resource hierarchy should always be done with a client capable of working with streaming RDF: either a SAX parser (for XML) or a n-triples based parser, where triples of certain types are acted upon (i.e. pushed onto another queue) as the response is being streamed through the client.

Benjamin Armintor, 2016-07-29 20:58 UTC

A. Soroka sorry, for some reason I missed this thread. Introducing a limit is complicated for this work because there's currently no consistently defined order for objects, and the limit is on triples and thus may interrupt a resource if contained resources are included.

I initially had a violent reaction to what I thought was an obtuse deliberation from the WG on this, but (as usual) it turns out that they had been thoughtful and I had been rash. Addressing this really requires either a sidecar index, a sidecar flat store, or providing a query facility.
