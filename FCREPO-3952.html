FCREPO-3952 Uncommitted transactions stay in index after container restart

TypeBug
StatusClosed
ResolutionFixed
PriorityMedium
ReporterDavid Novák
AssigneeBen Pennell

Updated2024-10-01 15:25 UTC

Affects versionsFedora 6.4.0

Description

If an uncommitted transaction exists when the container restarts, it is automatically removed from the ocfl storage after the restart. However, it will remain registered in the DB index tables, where it must be manually removed (rollback via API no longer works - the transaction is not found).

Comments (4)

Ben Pennell, 2024-09-10 20:45 UTC

I have confirm that this happens with postgres and h2, which should be helpful for testing. I’ve also noticed that staged files do not get cleaned up for resources that were created during a transaction that was not committed before shutting down fcrepo. With mvn jetty:run they are located in target/fcrepo-home/data/staging/

As noted on the other ticket, there is no database entry for a transaction. Fedora effectively just keeps track of transactions using an in-memory ConcurrentHashMap, along with some additional in memory transactions for tracking file changes associated with the OCFL session bound to the transaction. So after restart all of that is gone.

There is not currently a mechanism to rollback/cleanup transactions either at shutdown or startup time. Since the map doesn’t exist anymore after a restart, it can’t lookup transaction ids supplied by the user in order to manually rollback transactions, plus all the other OCFL state would be gone.

While the database does have containment_transaction and the other transaction tables which could provide us with a list of TX ids leftover from before a restart, I don’t think there is much we can do with that due to losing the details about what files were going to be changed in OCFL.

So the only approaches I can think of to resolve this are:

  1. Brute force method, where at startup with wipe the _transaction tables and delete everything in staging. It feels slightly scary, but its effectively what we’d do with a more systematic rollback approach anyways. All changes in a TX are isolated from the persisted OCFL and database states, so it’s probably safe.
  2. Attempt to cleanup/rollback transactions before shutdown. We would still have all the state info at that time so rollbacks could work, assuming we are able to trigger it early enough in the shutdown process. However, this wouldn’t help with unceremoniously shutdowns, like running out of memory or hard kills of the process, so we would still end up with leftover records occasionally.
  3. Rework transaction implementation to be more persistent, so that we could retain all the details of the transaction through a shutdown, so we could either rollback or revive transactions on restart. I’m not really sure it’s worth the effort just so we can rollback immediately, and it seems a little opposite the point of transactions.

Ben Pennell, 2024-09-18 15:15 UTC

https://github.com/fcrepo/fcrepo/pull/2092

The PR rolls back transactions and ocfl sessions during shutdown. During startup it only cleans up transaction database entries, so staging directory files will not get cleaned up in a hard shutdown scenario. My reasoning for this was:

  1. If OCFL clients other than fedora interacted with the same OCFL root, fedora wouldn't be able to differentiate which staged data belonged to it.
  2. ocfl-java and fcrepo-storage-ocfl do not provide a way to address the staging directory or purge all staging directories without having active sessions, so it felt unsafe to go around its back, and may potentially have not worked in cloud storage environment.
