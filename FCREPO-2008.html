Description

This task is to make the messaging around updated containers consistent in how the fcrepo-audit and fcrepo-audit-triplestore behave.

There is filtering in fcrepo-audit that ignores updates to parent containers when a child resource is added:
https://github.com/fcrepo4-exts/fcrepo-audit/blob/master/src/main/java/org/fcrepo/audit/InternalAuditor.java#L149-L153

However, these messages are still omitted for general consumption. The fcrepo-audit-triplestore consumes the parent container messages and creates audit events for them.

This ticket is to either move the logic out of InternalAuditor.java and into JMSTopicPublisher (or the like),
https://github.com/fcrepo4/fcrepo4/blob/master/fcrepo-jms/src/main/java/org/fcrepo/jms/observer/JMSTopicPublisher.java
...or remove the filtering logic altogether.

This behavior can be verified by spinning up fcrepo4-vagrant with the default configuration (Fedora and triplestore audit enabled), create a container and a child resource in Fedora. The Fedora audit will have two entries and Fuseki will have three.

Andrew Woods, 2016-04-27 13:41 UTC

No. The primary question here is, "What events should be captured in the audit log"? ...followed by, "and let's make sure that the internal and external audit features are consistent".

The mention of generalizing the message filtering from InternalAuditor to JMSTopicPublisher was just recognizing an approach to consolidating logic... potentially by marking certain events, etc.

Esmé Cowles, 2016-04-27 13:53 UTC

I agree that the first question here is whether the events should be emitted at all. Since if we are fine with emitting them, then just removing the filtering would be the easiest approach.

I believe the rationale for doing that filtering was that adding a binary should emit just the event about the binary being added, and not also emit an event for the parent's last-modified being updated. But the last-modified is indeed changed, so I can imagine people might want to update it (e.g., to update the Solr or triplestore's count of attached binaries). So that rationale seems pretty suspect to me now. Are there other reasons to keep the filtering?

Andrew Woods, 2016-04-27 13:57 UTC

I think there are two separate questions:
1. Should all repository updates, direct or indirect result in messages - I believe the answer is "yes".
2. Should the audit feature create a log entry for all repository updates, or does the audit only care about direct updates? - Thoughts?

Unknown, 2016-04-27 14:11 UTC

To question 1: I feel strongly that the answer is "yes". This is especially important for external indexes such as triplestores. Basically, the parent resource has changed – it has a new ldp:contains triple and the lastModified triple has changed.

To question 2: I don't have much of an opinion here, though I do think that it will become increasingly difficult to separate direct updates from indirect updates. The Direct/Indirect container example is one such instance where a single create operation will trigger multiple messages (it doesn't at present but it will with FCREPO-1742 Closed and FCREPO-1498 Closed ). HTTP MOVE operations now also trigger all sorts of additional events.

Overall, I would be inclined to remove the filtering.

Esmé Cowles, 2016-04-27 14:14 UTC

I am also inclined to just remove the filtering. I don't think there's a strong rationale for doing the filtering, and having limited and inconsistent filtering is worse than none.
