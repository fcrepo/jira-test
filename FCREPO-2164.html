Esmé Cowles, 2016-09-08 11:56 UTC

I'm a little confused about the workflow here. I thought the workflow was:

1. Run the export command with an optional config file option, but allow all options to be specified directly on the command-line (to make scripting easier)
2. The export utility saves the total configuration used to perform the export.
3. Run the import utility with the saved configuration file and optional arguments to override (e.g., a different baseURL).

But I don't think that's what's going on in PR #25 — it seems to require the config file, save the original options (not the final effective options), and not allow combining the config file options with command-line options.

Andrew Woods, 2016-09-08 13:35 UTC

What this PR does is allow for either passing in:

  • normal command-line args, or
  • a config file.
    ...there is no merging of the two.

The idea is that you can use a config file as a shortcut to re-providing the command-line args. It so happens that each run of the utility results in persisting the config to disk at /tmp/config.txt, if that file does not already exist.

You can save that /tmp/config.txt, or ignore it.

Esmé Cowles, 2016-09-08 13:50 UTC

OK, I think I understand now. The /tmp/config.txt is merely saving the options passed to the utility as a convenience, and it would be up to the user to move and rename that file if they wanted to keep it for future use. So users who wanted to pass all of their options on the command line could ignore it, but users who wanted to use a config file would see it referenced in the log output.
