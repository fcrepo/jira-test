Description

Adding/editing an invalid FESLPOLICY datastream results in a failure of the API call, however the changes are saved. This is due to the order in which policies are propagated to dbxml - after the main API call has been made. Need to cater for the situation where both the API call and/or the propagation to dbxml (where the validation takes place) could fail.

Probably not a blocker for 3.4.

Stephen Bayliss, 2010-12-20 16:59 UTC

Closing - won't fix - as covered by FCREPO-842 Closed (can't implement this without transactioning)

Stephen Bayliss, 2011-01-04 00:58 UTC

Reopening - thinking again on this, it would be useful to do policy validation (if enabled) on the xacml before we attempt the datastream modification, and fail the api call at that point - ie if attempting to add/modify datastream to invalid XACML then the datastream should not be modified.

This will mean looking at where the validation takes place - currently it's in the dbxml update layer; it should be further up the stack, with the validation removed from the lower levels.

However existing behaviour - if the dbxml update for some (other) reason fails, this should not prevent further updates to the policy index, and the datastream update should succeed - that's the fix already committed; though currently provoked by the lower-level xacml validation exception.

Stephen Bayliss, 2011-01-15 12:12 UTC

Closing as FCREPO-848 Closed covers the outstanding validation issue. Also there are tests in ConfigC for the behaviour reported by this issue.
