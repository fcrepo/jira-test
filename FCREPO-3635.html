Initial task is to determine how this can be accomplished without having two branches to maintain.

Michael Ritter, 2021-11-16 23:06 UTC

There’s a migration tool provided for Tomcat 10: https://tomcat.apache.org/download-migration.cgi

I was able to run it and deploy on Tomcat 10 without issue, still need to test with Jetty but since it creates a new war it should be ok. Easiest way to support both versions would be to incorporate that tool in the CI pipeline but keep in mind it only goes from javax → jakarta so we would need to keep the fcrepo codebase on java ee 8.

Ben Pennell, 2021-12-02 13:59 UTC

Will war files built this way still work with jetty 9/10 and tomcat 9? Is there a compelling reason to move towards jetty 11 support at this time, given that jetty 10 and jetty 11 are intended to be the same except for the servlet and accompanying api versions?

The tomcat migration tool is still marked as a “work in progress” in their readme, so I’m not totally sure they intend for its use in production? On the other hand, some of our dependencies probably won’t work with servlet v5 for a while, such as spring which I believe isn’t going to support it until spring 6 releases at the end of 2022.

Ralf Claussnitzer, 2025-08-12 11:08 UTC

Since Fedora makes heavy use of Spring Framework anyway, why not get rid of the Tomcat and Jetty integration/deployment and move over to SpringBoot? This way the SpringBoot folks handle most of the dependencies and HTTP runtime issues. It also makes native deployment as SystemD Unit a no-brainer. There is a maintained Maven Plugin to handle all that. This might actually help with reducing the amount of dependencies the project has and help with moving along with new Java versions.

Ben Pennell, 2025-08-12 13:24 UTC

Thanks Ralf, it would make sense to do that, but it seems like it’d require some significant refactoring. For what it’s worth, the main branch for fcrepo should work in jetty 12 now. I don’t know if anyone has tried it with tomcat 10 yet or not.
