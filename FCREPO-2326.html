pketienne, 2016-12-07 14:02 UTC

Completed a backup of a mirror of our production data via our staging server (~212GB). No immediately feasible avenue for testing the restore of this backup into Fedora 4.7, but should be viable with sufficient disk space.

Have been working on export of this same production data through use of the fcrepo-import-export tool. So far, I've gotten through 157 of 212 GB without errors, however I've run into a few of the following kind of errors:

ERROR 17:46:57.627 (ImportExportDriver) Error performing import/export: Export operation failed: unexpected status 500 for http://localhost:8080/SSstagingFedora4/rest/prod/mk/61/rg/99/mk61rg99w/content

Browsing to http://localhost:8080/SSstagingFedora4/rest/prod/mk/61/rg/99/mk61rg99w/content/fcr:metadata and then uploading any file seems to resolve the issue, and allows the export process to run again without failing on this record.

I believe these export errors are just a side effect of some of our data not having valid content.

pketienne, 2016-12-12 15:23 UTC

There ended up being about 10 records that "contained bad data" (described above). Once those records were fixed, the export worked as expected. I performed two different exports of the data based on slightly different versions of the import/export utility. Both ran successfully.

pketienne, 2016-12-12 15:29 UTC

Running the verify.py command (RHEL 6.8, Python 2.6.6) results in the following error:

/usr/bin/env: python3.5: No such file or directory

Editing the verify.py file to "#Unable to render embedded object: File (/usr/bin/env python" from "#) not found./usr/bin/python3.5" resolves this issue. The README.md of the project does say that python 3 is the recommended environment so reverting to the earlier version of python that's included with RHEL 6.8 may not be the appropriate answer.

pketienne, 2016-12-12 20:35 UTC

Got a little help from bseeger - noted that the error I'd been experiencing may be due to using python 2.x. Attempted several different methods of getting python 3.x running on the rhel 6.8 box. All methods resulted in the same error as before. This was due to conflicts between the system python and the additional python I'd installed specifically for using the verification tool. In short, this problem with conflicts between system and user python versions is the same or at least very similar to the process of setting up system rubies/gems versus user rubies/gems. I then setup pyenv and pyenv-virtualenv to handle python from my user's perspective on our staging server. This resolved the import issue.
