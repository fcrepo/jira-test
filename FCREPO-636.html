Stephen Bayliss, 2010-06-24 11:27 UTC

It would seem that the XACML 2.0 hierarchical resource profile http://docs.oasis-open.org/xacml/2.0/access_control-xacml-2.0-hier-profile-spec-os.pdf is relevant to this.

The basics that seem to be appropriate:

Resource identifiers (section 2)

  • hierarchical URI representation to be used to indicate resource identity in the context of its collection membership
  • if a resource has multiple parentage, there will be several different URI representations of the resource identifier,
  • need to be explicit that these URI identifiers for resources used as part of XACML are distinct from the REST API identifiers and the info:fedora/ identifiers
  • section 2 specifies that the authority part of the URI is mandatory; it would seem appropriate that an HTTP URI scheme should be defined (eg http://local-fedora-server/objecthierarchy/<collection>/<child> (doesn't need to be rereferenceable)
  • currently FeSL just specifies the path component of the URI(ie no authority/scheme part of URI specified)
  • need ability to include datastreams within the resource identifier URIs

Request context

  • should provide full set of hierarchical resource identifiers
  • where resources are members of multiple collections (which themselves might have multiple parentage), the request context should contain all of the potential paths from the resource to its ancestors

Policy

  • resources can be specified as a regular expression on a URI
  • so regexp could specify "any descendent of" "immediate children of" etc (as well as the resource itself)
  • MatchID="urn:oasis:names:tc:xacml:2.0:function:anyURI-regexp-match" (in FeSL currently)
  • FeSL uses the XML datatype for anyURI, the spec above as a xacml vocabulary datatype for the same

Relationships

  • relationships should be used in determining resource parents and anscestors
  • eg config file specifying which relationships indicate "parent" for the context of XACML policy
  • better would be to have this config as an object in the repository
  • relationships would be used in creating the request context - ie given a PID, look up the ancestry and build the URIs with the various ancestry paths

Subscribing to policies using relationships

Using the above, we could support the scenario where

  • a collection has a policy, with the policy directly identifying the collection (rather than through a relationship)
  • resources subscribe to the collection through relationships to the collection

This issue seems to identify a need for going further than that - rather than the XACML policies directly specifying the identifiers of the resources, resources subscribe to policies through relationships (policy resource identifiers are implicit rather than explicit). ie we have XACML policies that do not identify the resources; similar to the way the native Fedora XACML implementation has policy datastreams that implicity are for the object containing the POLICY datastream.

This suggests that the PolicyFinderModule should be capable of locating applicable policies through these subscribing relationships. And within this needs to be able to match the policies to the request context hierarchical URI(s) identifying the resources.

So we seem to have
1) find policies directly based on matching the request context hierarchical resource identifier URI(s) with URIs and regexps in policies (for the scenario where policies directly identify resources)
2) find policies through relationships, eg for a hierarchy consisting of
/node1/node2/node3
a) find all policies matching <node3> hasPolicy <?>
b) find all policies matching <node2> hasPolicyForChildren <?>
c) find all policies matching <node2> hasPolicyForDescendents <?>
d) find all policies matching <node1> hasPolicyForDescendents <?>
3) potentially find policies from the policy datastream of the object?

Need to consider impact on

  • policy caching/indexing layer (currently DbXML) - whether to cache all policies, or whether to locate policies directly from Fedora objects (noting that policies may be further constrained eg on subject, so indexing is desireable even when relationships are used for implicit resource identification in the policy. Note here that a policy with no resources specified applies for all resources, so need to be able to differentiate between that and a policy where resources are implicitly specified through relationships)
  • policy combining algorithm - order of precedence

Indexing and resource identifiers

  • the above reference also defines parent and ancestor semantics to be used when identifying resources (in request contexts and policies). It may be more efficient to use this than the hierarchical URI scheme for resource-in-collection identification as this could potentially avoid needing to do regexp matches using regexps specified in each policy.
Stephen Bayliss, 2010-07-13 18:24 UTC

Suggestion for an implementation:

Scenario:
Policies are stored in Fedora objects ( FCREPO-577 Closed ) for the purposes of editing. When policies are added, modified etc, they are cached/indexed, currently in DBXML (see FCREPO-576 Closed ) but maybe in an alternative caching/indexing layer in the future.

Relationships such as the following (full URIs tbd) are specified in RELS-EXT to "apply" policies to resources:
isPolicyFor (or inverse: hasPolicy)
isPolicyForChildren (policy applies to children of a collection) (or inverse: hasPolicyParent)
isPolicyForDescendents (policy applies to all descendents of a collection) (or inverse: hasPolicyAncestor)

The mechanism for updating the cache is through the decorator pattern ( FCREPO-577 Closed ).

So we could:

1) Have policies in Fedora objects which do not specify a XACML resource
2) When updates are made either to the XACML policy or to RELS-EXT containing the above relationships:

  • as well as caching/indexing the policy (as per current scenario), build the resource specification part of the XACML policy based on the relationships, ie the Fedora object "template" policy is filled in and the filled-in version is the one pushed to the cache/index.

eg
pidns:collectionPolicy1 isPolicyForChildren pidns:collection1 results in XACML resource spec "/pindns:collection1/" (all children of collection 1, irrespective of rest of parent hierarchy)
pidns:policy1 isPolicyFor pidns:object1 results in XACML resource spec "pidns:object1"

(Ancestors could be an issue, not sure if there is a XACML resource ancestor syntax such as "pidns:collection1/**" or something similar).

In effect, the XACML policies with no resource spec in Fedora objects would be regarded as "template" policies, filled in by examining relationships.

XACML policies that do have a XACML resource spec would not be regarded as "templates" and would be cached as-is (so relationships "applying" policies to these would have no effect). Alternatively some kind of attribute could be used to indicate a template vs a complete policy.

Alternatives - a customised of the XACML schema to explicitly specify a "template" resource section identifying how relationships are used to apply the policy.

TBD: how would this be used with policies that eg apply to datastreams belonging to objects that are members of a collection?

There are probably some alternative design choices here (say, allow for POLICY and POLICYTEMPLATE datastreams), but that's the basic principle.

Gregory Jansen, 2010-11-11 22:48 UTC

The inheritance model here will be more flexible if RELS-EXT relations can also be expressed as "parent contains child" relationships. The implementation proposed seems to allow one to specify a custom "hasParent" type of property, but not a "hasChild" property. In the ontology we use at the CDR for instance, the parent has a RELS-EXT property pointing at the child.

I realize that this is harder to implement in terms of the lookup of the triples. IMHO it may be time for such lookups to use the triple store. It could still be considered an optional configuration, but the flexibility is far greater.

Stephen Bayliss, 2010-11-12 14:12 UTC

Agree this should be flexible in
(1) specifying how collection membership is implemented (relationship from child to parent, relationship from parent to child) and
(2) identifying how the policy applies to the collection and children (policyForCollection, policyForCollectionMembers, policyForCollectionMembersAndDescendents) etc.

Ideally specify this in config rather than code.

For (1) what would be ideal would be to support multiple types of collection implementation (eg both isMember and hasMember of, etc).

For simple situations it could be a case of RELS-EXT lookups, for more complex situations it could be specified as queries on the resource index (SPO, TQL, SPARQL).

Stephen Bayliss, 2010-12-03 23:28 UTC

Suggest an initial implementation as follows:

Configuration currently supports specifying child->parent relationships, extend this to also allow parent->child relationships

  • however note that relationships are currently queried directly on the object; we would (optionally?) need to allow RI queries to support parent->child

Then we could support the following:

Policy object:
fesl:policy1

Specifies resources in XACML as:
/fesl:policy1/*

Resource:
ns:pid -> hasPolicy -> fesl:policy1

Grouping of resources for navigation could be completely distinct from applying policies. (ie, the existing isMemberOf relationships could be removed from the config).

Datastreams - could be handled by other stuff in XACML, for instance a separate ResourceAttributeDesignator and attribute finder (the incoming resource identifier(s) will identify the datastream in any case, we just need to make sure it is "exposed" so that it can be included in the XACML). Currently I don't believe FeSL supports datastream IDs.
