Description

When performing a fixity check on a binary resource, "fcr:content" and "fcr:data" resources are exposed in the generated RDF.
To reproduce:

  • Create a binary resource:
    curl -XPUT -H"Content-Type: image/jpeg" --data-binary @image.jpg localhost:8080/rest/image.jpg
  • Get the result of a fixity run:
    curl localhost:8080/rest/image.jpg/fcr:fixity
  • See JCR leakage:
    ...
    premis:hasContentLocation </image.jpg/jcr:content/jcr:data> .
    ...
    </image.jpg/jcr:content/jcr:data> a premis:ContentLocation ;

Unknown, 2015-11-01 13:36 UTC

If we are going to confine ourselves to "single subject responses" (which I think we should), then the premis:hasContentLocation should be something like this:

<./path/to/resource#fixity/(timestamp)/location>

The timestamp portion of the URI would be the same as it is for the rest of the response.

We have more flexibility with the string-based premis:hasContentLocationValue triple. For that, it would be nice to indicate something about the physical location of the data. Depending on what modeshape provides through its public API, it would be nice to indicate the name, type and a hint of the location of the binary in the underlying storage layer.

Unknown, 2015-11-04 14:52 UTC

The issue with file paths is that, if someone is using an infinispan grid as their blob store, there is no "filepath". In that case a "file" is just a blob that's split up into a lot of small pieces. Or, if a binary is really small, it may go into the leveldb cache, just as how, if a property is really big, it goes into the binary store.

Esmé Cowles, 2015-11-04 15:46 UTC

As it turns out, I don't see anything in the Modeshape API that would give us a filename or equivalent storage information for stores that didn't map directly to disk. See http://docs.jboss.org/modeshape/4.3.0.Final/api/org/modeshape/jcr/value/binary/StoredBinaryValue.html – we can get the file size, mime type, an input stream, and a key (which is just the SHA-1 checksum). So I think the file's path/URI is the only thing we have that's relevant – is it worth putting that as the value of premis:hasContentLocationValue? Or should be just remove the ContentLocation block?

Unknown, 2015-11-04 15:56 UTC

Can we get the name of the binary store? That might be useful information, but I'm a little inclined to just remove the ContentLocation block. I also don't know what happens if you have multiple binary stores: does JcrRepository::getConfiguration::getBinaryStorage get the correct value?

Esmé Cowles, 2015-11-04 17:35 UTC

We can get the type (transient/file/cache/database/composite/custom) and the binary store class name. In the case of multiple binary stores, they should be wrapped in a CompositeBinaryStore, so we could find the store that contained a file using the findBinaryStoreContainingKey method. But I'm not sure the type or class name are really appropriate for premis:hasContentLocationValue, which seems more geared towards a filename, URI, byte offset, etc. that would be used to access a file, not a description of the kind of storage system used.

So I think we should simply remove the ContentLocation block.
