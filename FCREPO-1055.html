Description

Currently object FOXML validation (via schematron - xslt - and schemata - xsd) is inefficient as the stylesheets are compiled for every validation.

Create some kind of shared resource for XML operations such as transformations and validations with some kind of caching mechanism so that compiled invariant XML resources can be re-used. In the future this component could form a good candidate for separate OSGi service(s).

Comments (6)

Stephen Bayliss, 2012-01-27 13:20 UTC

Will need to consider the lifetime of any cached resource carefully, and how to control this.

Eg something like the FOXML schema and schematron xslt is not likely to change; but a datastream schema specified by a CModel (ECM) may get updated.

A. Soroka, 2012-01-27 20:47 UTC

A quick start would be to accept only resources that we are confident will not vary over application lifetime (e.g. schemata for FOXML or OAI DC).

One simple approach to begin caching resources with a "sell-by" date would be to start with those such resources that can be derived purely from a Fedora object or objects, and then decorate the Management module (in time-honored Fedora fashion) to "stale-ify" a cache entry when the object or objects to which it is associated have changed.

Starts to make me think that an internal event bus for Fedora could be a very handy thing. It could power all kinds of notifications, external or internal to the app.

A. Soroka, 2012-01-27 21:00 UTC

Another possibility would be to engage with a good general-purpose object pooling system (e.g. Apache Commons' Pool component). That might be overkill for the XSLT/XSD stuff we're talking about immediately, but I'm throwing it into the conversation because I would expect that we may very well want to pool other resources in the future in the core Fedora services and also that we will want eventually to expose pooling as a service in the Fedora internal architecture. In that light, it might be better to begin with a general-purpose solution rather than generalize a specialized solution. Or maybe that's pointless and expensive generality up front.

{grin}
A. Soroka, 2012-01-27 22:34 UTC

A practical note: we will have to generate a plan to discover all of the places that this facility might be employed. IDEs can help with the search, but we may need to produce a little machinery to help organize the work, like a list of places in the code we could alter and whether they've been done, that sort of thing. Eclipse Mylyn could be handy-- it integrates with Jira quite well.

A. Soroka, 2012-11-13 22:51 UTC

Given the significance of a move to OSGi, and the fact that we've already committed to Spring, we may want to start down this process by running through the various places (mostly in fcrepo-server, I would imagine) and replacing the construction of XML tools with their injection. Then at least we can centralize the construction and pooling/caching of these guys. If we restrict ourselves (as noted above) to resources that are immutable during the lifetime of a running instance, we won't have to think any more about thread safety, staleness, etc. then is required by the underlying XML facility. In many cases (e.g. using Templates and not Transformers) we can probably dispense with pooling entirely.

Another pure-Java way to do this would be with the ServiceLoader and provider metadata. While I like the fact that this moves us towards a registry and towards the pattern of the OSGi service model, it's probably a lot more work for not much immediate gain, and (as noted) we already are committed to Spring.
