Description

We have started running migration tests using migration-utils, and are receiving an out of memory (OOM) error after migrating a few thousand objects, with heap sizes tested between 1-5 GB. The OOM is observed in the migration-utils JVM.

For example, for one test we specified a max heap of 2 GB. After 25 min the JVM started running full GCs; after 40 min the JVM was spending most of its time in full GC, and an OOM was thrown at 50 min after 1533 Fedora 3 objects were migrated. The gc and migration-utils logs from this run are attached.

Similar results were experienced with max heaps specified in the range of 1-5 GB, see table below. It appears that the heap usage grows linearly with the number of objects migrated to the max available, and some objects in the heap are never garbage collected.

On one of these runs I took a snapshot of the heap and looked at it through jvisualvm. A fair amount of memory is consumed by char arrays and Strings, whose values appear to be triples. Perhaps these triples are not garbage collected?

Max heap # objects Time to OOM
1 GB 1262 25 mins
2 GB 1533 50 mins
4 GB 3145 1 hr 41 mins
5 GB 4032 2 hr 8 mins

Environment:
migration-utils-4.3.1-SNAPSHOT, running on the same CentOS server as the destination Fedora.
Source data is from Fedora 3.8.1 legacy-fs format.
Target is Fedora 4.3, running with 5 GB max heap.

Eventually we would like to use this utility to migrate two different Fedora repos, each with approx. 3.5M objects.

Thanks!

The fix appears to have largely resolved the OOM error.

I have been running the migration process for over 20 hours, and migrated 32K objects so far, without problems. Memory usage is down significantly. Total heap size is steady state at 120 MB, essentially unchanged from JVM startup. A quick minor gc occurs every few seconds, and about 34 MB is collected off the heap. See attached _fix logs for details.

There does still appear to be a very slow leak which perhaps could be problematic at large scale. Uncollected heap usage does seem to grow at about 1.6 KB per object. This could be problematic if attempting to migrate millions of objects within a single migration process - if this rate holds, 1M objects migrated would consume 1.6 GB heap in the migration JVM.

In terms of processing speed, I am seeing a rate of approx. 1600 objects migrated per hour, or about 2.2 seconds per object. This works out to perhaps 40K objects per day. One of our F3 repos contains 3M objects which would take 2-3 months to migrate at this rate.

In these tests, we are running F4.3 and the migration tool on the same box. This box is a virtual Linux box running CentOS6 with one CPU at 3 GHz and 8 GB RAM. During this test, steady state CPU consumption is 70% for F4 and 2% for the migration tool. Possibly, we have specified checksums to be computed on more files than really need it, which could slow performance.

We will keep this test running to see how things shake out.

Overall this OOM fix seems fine and our setup seems OK for migrations up to maybe a few hundred thousand objects. Beyond that we would run into time, memory and process issues. We still need to design a solution for migrating a repo with 3M objects, which is out of scope for this particular ticket.

Michael Durbin, 2015-11-16 13:17 UTC

There are a few easy ways to improve performance and some harder ones. This is said without having profiled a long-running ingest operation.

The first, is to perform all the updates issued for a resource version as a transaction. This would be a general improvement and has no real downsides.

Some performance gains may be achieved in changing the way metadata is mapped. Right now certain metadata is maintained in blank nodes. While it's not well established that node and link creation represents a significant amount of time, this may be a target for general improvement.

Other gains may be achieved by tuning/customizing the migration for your own use case. For instance, depending on your migration needs, you may choose only to migrate the latest version of versioned resources. In other cases it would seem conceivable that you wanted to preserve the fedora 3 information but only needed access to a subset moving forward. In such cases, I could see a dramatically faster migration, possibly involving the archival of the fedora 3 data store unmodified and just extracting the current working subset into RDF in fedora 4.
