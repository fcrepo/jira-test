FCREPO-3014 Incremental backup using the import export tool

TypeNew Feature
StatusOpen
PriorityMajor
ReporterDanny Bernstein
Created2019-06-11 18:15 UTC
Updated2021-09-17 17:42 UTC
Componentsf4-import-export

Description

Seth Shaw wrote: I can imagine two separate scenarios:

First:

  1. Given a previous full export of the repository "java jar fcrepo-import-export-0.3.0.jar --mode export --resource http://localhost:8080/fcrepo/rest -dir /data/fcrepo-export --binaries -u user:pass"
  2. When the same command options are used, instead of exiting (since the root resource already exists in the export location), the tool inspects the exported resource for the value of "fedora:lastModified" and compares it with the value from the Fedora API response (the HEAD request's "Last-Modified" value should work and make the process more efficient).
  3. If the Fedora resource responds with a lastModified value greater than the exported resource re-exports and replaces the existing one. Otherwise, it continues on to the next resource.

This would allow me to maintain a full export without exporting all the binaries every run. run a tar command over the backup directory with the option to only include items modified/added since the last tar/gzip.

Second:

  1. Add an option to the export that takes a date-time as the value.
  2. The script then checks the resource's last modified date
  3. IF the resource's last modified date is more recent than the provided date-time value, export the resource. Otherwise, skip to the next item. 

This scenario would require the repository to know when the last export occurred, but could support either updating an existing full export, or creating a partial update in an empty directory. In the latter's case I could first run the partial export then tar/zip the package for off-line storage leaving the target directory available for the next incremental export. 

In either case, I imagine that the import process would include importing the first export I made and then importing each incremental in chronological order where the import only changes the items from the most recent import.

Danny Bernstein, 2019-06-19 15:59 UTC

Seth Shaw :  We discussed this ticket on last week's call ( https://wiki.duraspace.org/display/FF/2019-06-13+-+Fedora+Tech+Meeting).  There was some questioning of whether this functionality would belong in the import/export tool,  or whether it would make sense to have a separate tool for doing incremental backups.  The tool was designed with the use case of exporting a complete repository and importing into an empty repository.   There was some concern expressed around the drifting away from that simple use case and specifically dealing with the  added complexity of accounting for resources that exist on disk (from a previous export) that were then deleted in a subsequent export.   Adding in support for tracking deletes would add some overhead since we would need to remove the set of items on disk that are no longer present in the repo.  Daniel Lamb made the observation that if we're going to be tracking file system deltas we're essentially reinventing git. 

So coming back to your use cases:  it seems that you have two concerns you are trying to address:

1) Improve the performance of exports by having the option to not export binaries that haven't changed.

2) Reduce data duplication in offline storage.

Do I have that right?
