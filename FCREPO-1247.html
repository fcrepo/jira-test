Description

This task is to determine why "fcr%3aversions" is not being decoded and interpreted in the example detailed here:
https://groups.google.com/d/msg/fedora-tech/qw3GlptWBQw/CaGXHMuiRXIJ

Then, likely update the logic to decode the URL but recognize the "fcr" prefix and treat it differently.

*Background of issue (by Jared)*
The issue is that we map URLs based on their structure and in Jersey if you have a URL
http://localhost:8080/base/action1/action2/action3
and mappings
Path = .*/action1
Path = .*/action2
Path = .*/action3

Then Jersey acts on the path match closest to the hostname first (action1 in my example), then the next one (action2) and so on (action3).

So in our case we are matching on fcr:versions first and trying to perform this action. FedoraVersions doesn't handle fcr:fixity (nor expects it to be in the URL) so it fails. My assumption is that if this had succeeded then Fedora would have attempted to perform the fcr:fixity tasks next.

My solution was to alter the fcr:versions @Path matching to not match if the URL has fcr:versions but ends with fcr:fixity.

Jared Whiklo, 2017-06-20 18:58 UTC

I have confirmed this behaviour and it seems to be because based on the Jersey @Path parameter, the fcr:versions is handled before the fcr:fixity.

Andrew Woods suggested URL-encoding the fcr:versions in the Link Header (ie. Link <http://localhost:8080/rest/this_thing/fcr%3Aversions/v0/fcr:fixity;rel="hasFixityService">), which would work because Jersey would no longer match the fcr:versions path, but does seem odd compared to the other Link headers.

Also the error will still occur, just that we have changed the URI for the versions fixity service.

The only other alternative I can think of is to modify FedoraVersions to not match if the Request URI ends with fcr:fixity and allow it to fall through to FedoraFixity.

I'm experimenting with the Jersey @Path parameter, if anyone has a suggestion I'll take it.

Jared Whiklo, 2017-06-21 14:58 UTC

jrochkind URL Encoding the colon in fcr:versions effectively does the same thing as my change, it causes the Jersey Path matcher to not match and so it passes through to the fcr:fixity which does match. This means that this change should have no effect on your workflow, other than you no longer need to URL encode the fcr:versions in the URL.

I'd (of course) suggest you give it a test to make sure, but as this is a single line change and does not affect how either versions or fixity operates I think the impact should be negligible.
