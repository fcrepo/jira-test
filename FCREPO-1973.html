Scott Prater, 2016-04-06 03:47 UTC

The problem appears to be a character encoding issue: if you remove the inverted exclamation point from the bf:title value of the test bibframe record in the integration test, the test then passes on Windows. Put it back in, and the test fails.

https://github.com/fcrepo4/fcrepo4/blob/master/fcrepo-integration-rdf/src/test/java/org/fcrepo/integration/rdf/BibframeIT.java#L57

I'll look into this more: as far as I can tell, that character is a valid UTF-8 character.

A. Soroka, 2016-04-06 14:00 UTC

We shouldn't really ever be using default platform encoding, we should explicitly call out UTF-8 via java.nio.charset.StandardCharsets.UTF_8. He wrote, knowing that he rarely does that.

Scott Prater, 2016-04-06 14:11 UTC

Should that be built into the test? or into the server that handles the PUT request?

The quickest-and-dirtiest approach to fixing the test is to remove the inverted exclamation mark. I'm okay with that, since it is a bibframe test, not a character-encoding test.

That said, I'm wondering about character encoding issues out in the wild, and how to handle those gracefully. At the very least, shouldn't the server detect if there's an encoding mismatch, and return something a bit more enlightening than a java.nio.charset.MalformedInputException? I'm thinking it may make more sense to fix this test, then open up an enhancement ticket for later on, to gracefully deal with encoding issues, complete with some sample curl transactions to test the behavior (later to be fleshed out as character encoding integration tests).

A. Soroka, 2016-04-06 14:21 UTC

Definitely built into the server (the fcrepo-http-api or -commons code, I should think). Everything flowing in after the HTTP machinery should be UTF-8. That's how we get rid of this nonsense once and for all. I think we could do something here with JAX-RS machinery to ensure it.

I take your point about the test in question being about Bibframe, but ironically, library metadata is an oozing, crusty pit full of badly-formed characters washing around in a greasy puddle of XML that lies about its own encoding. It's probably where this kind of problem would first appear, anyway.

Scott Prater, 2016-04-06 14:28 UTC

Ideally, I'd like to PUT 2049 bytes of /dev/urandom to the Fedora server, and have it say something gently remonstrative and useful to me about why that won't work.
