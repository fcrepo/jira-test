Description

If Fedora is started with JMS messaging turned on and configured for an external broker with direct connection (and not through a JNDI provider) but that broker is unavailable at startup, the entire server goes back down. That seems like a pretty drastic failure.

To duplicate:

0) Turn off a repository.

1) Turn on the Messaging module and assign an external broker to "java.naming.provider.url" in fedora.fcfg, e.g.

<param name="java.naming.provider.url" value="tcp://localhost:61616"/>

2) Make sure the external broker is not available.

3) Start up Fedora.

You'll see something like:

FATAL 2010-09-21 09:59:55.571 [main] (Server) Module (fedora.server.messaging.Messaging) failed to initialize
fedora.server.errors.ModuleInitializationException: Could not connect to broker URL: tcp://localhost:61616. Reason: java.net.ConnectException: Connection refused
at fedora.server.messaging.MessagingModule.initModule(MessagingModule.java:81)
at fedora.server.Module.<init>(Module.java:63)
at fedora.server.messaging.MessagingModule.<init>(MessagingModule.java:58)
...

and then a server shutdown. Much better would be to see some kind of warning, then attempts to connect as appropriate with warnings thrown on failures.

It's not known to me whether this behavior is the same with a JNDI-provided ConnectionFactory, because I've never been able to get that stronger configuration to work, which is a whole 'nother problem.

Scott Prater, 2010-09-21 19:52 UTC

I'd like to see more robust connection management built into the Fedora JMS producer service. Something along these lines:

1. If messaging is configured, Fedora will try to connect to the message broker upon startup, log a warning if it cannot connect;

It will reattempt to connect at a specified interval (configurable in fedora.fcfg), log a warning after every failed connection attempt;

It will quit trying to reconnect after a specified number of attempts (also configured in fedora.fcfg), logging an INFO message that it will no longer attempt to connect. If this parameter is not set, it will try to keep reconnecting forever.

Some sort of stepped reconnect attempt interval may also be desirable, such as doubling the time between attempts on each connect after the first five (or X, again configurable?) attempts.

2. Any messages that are generated while the message broker is unavailable will be stored in a (cache? hash?). As soon as the message broker is contacted, all the stored messages will be sent and then deleted. This will also happen at startup (which argues for some sort of persistent on-disk cache, with a predetermined max size, also configurable in fedora.fcfg).

Fedora will stop storing undeliverable messages after max attempts have been made to contact the message broker, or after the cache size limit has been reached. A warning will be logged to that effect.

Scott Prater, 2010-09-28 02:07 UTC

Upon further investigation, I think this may be a broker configuration issue, rather than a deficiency in the Fedora code base.

ActiveMQ and other brokers have hooks to configure connection management. ActiveMQ, in particular, has the "failover" transport macro, which allows you to periodically poll for a remote broker, along the lines I specified in my previous comment.

I was able to implement a store-and-forward topology, using the ActiveMQ broker embedded in Fedora to forward messages to a remote broker. Using the failover transport, the embedded broker holds messages when the remote broker is unavailable, and sends them along when it comes back online. It periodically polls the remote broker until it successfully connects. I tested this setup under a number of different scenarios (starting Fedora first, then the remote broker; starting the remote broker, then Fedora, then shutting down the remote broker, then starting it up again, etc., sending messages both when the remote broker was down and when it was up), and in every case, the messages eventually reached their endpoints, as desired.

I posted my notes on how to configure this for Fedora at http://sdg.library.wisc.edu/blog/2010/09/27/configuring-activemq-with-failover-in-fedora-for-higher-availability/ .

Given that properly configuring ActiveMQ can fix the problem addressed by this issue, I suggest that we resolve the issue by updating the Fedora Messaging documentation: explicitly pointing out the problems that can occur when configuring an external broker to consume messages, and offering this technique as a way to fix the problem.

Scott Prater, 2010-09-28 17:16 UTC

Thinking more about Fedora's startup behavior, two different use cases presented themselves to me. If messaging is not a crucial part of your environment, but provides some nice value-added features (such as reporting data, etc.), then you may want not want Fedora to halt if the message broker cannot be contacted. If, on the other hand, you absolutely cannot afford to lose a single message, since messaging forms a critical part of your repository workflow, then it may be preferable that Fedora shut itself down if the broker is not available (in which case, you'd probably want to implement some sort of redundant, high-availability network of brokers, anyways).

I wrote a simple patch that introduces a new parameter into the messaging module's configuration: failGracefully. If the value is set to "true", then Fedora will log a warning to the log file when the broker is not available upon startup, and disable messaging. If set to "false" (the default), then Fedora will shut itself down if the JMS broker is not reachable.

I still need to write an integration test for this patch before submitting it, but I'm not convinced it's really a necessary patch. Any other opinions? Maybe this is a question that could be briefly addressed and decided by the committers?

Scott Prater, 2010-10-28 05:46 UTC

After a discussion with the committers, it was decided not to incorporate the graceful fail feature into Fedora, but to offer it as a patch for whomever is interested. The patch is attached to this issue.

I'll update the Fedora documentation to include the instructions for configuring a store-and-forward broker bridge with ActiveMQ; this will be recommended as a best practice for messaging in production environments.
