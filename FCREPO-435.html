Objective:

To provide a method to support running a batch of API-M
operations as a single atomic operation. Benefits:
atomicity and performance. Atomicity: Fedora clients
would not need to manually compensate if the series of
operations failed part way through. Performance:
a) A single network request vs. many
b) A single database transaction vs. many (transaction
setup/teardown can be expensive)

Basic process:

  • Takes a series of API-M requests in one "package".
  • Starts a transaction
  • Executes each request, in order.
  • Commits and returns a series of corresponding API-M responses.
  • If anything fails along the way, rolls back and throws a fault.

Daniel Davis, 2008-12-09 16:58 UTC

Group discussed on Dec 9th, decided we needed more community input in order to refine this. Is the main goal performance? Should this be restricted to non-destructive (add-only) requests, so that compensation is more feasible? User doesn't necessarily want to formulate a package. Wants to mark a transaction start, do stuff, and end. How close can we get to that ideal without complicating the implementation too much? Another point that came out in this meeting: If we define a package format, it should NOT be transport-specific. That is, the same thing should work over SOAP and REST.

Chris Wilper, 2009-06-22 18:01 UTC

Discussed again June 22, 2009. Changed title because the main issue here is being able to send in a series of requests in an atomic way. This might be done in a variety of ways...a batch method is one. Another is to expose Fedora as a transactional resource. Another is to do this outside of Fedora, as a service that compensates. In the latter case, if it's done that way, this may be out of scope for the Fedora Respository Project itself.
