FCREPO-4032 False positives in ghost nodes detection

Description

There is a bug in the way ghost nodes are detected which leads us to get 409 Resource path xxx is an immutable resource. errors.

For example, if fcrepo/rest/erudit:unb.jcim1499352.jcim13_1 exists, we get the error when trying to create fcrepo/rest/erudit:unb.jcim1499352.jcim_3_1.

My colleague Maxime Turcotte traced it to the way ghost nodes are detected, using the LIKE SQL operator, which interprets {} as a wildcard for any single character. Since fcrepo does not escape {} nor %, it detects that erudit:unb.jcim1499352.jcim_3_1 is actually a ghost node for fcrepo/rest/erudit:unb.jcim1499352.jcim13_1.

This makes it impossible to migrate our data to Fedora 6 for now.

Basil Marti, 2025-10-10 15:24 UTC

The current implementation (underscores and percent signs are not escaped in the LIKE query) also creates another problem:

We have significant performance issues in installations with a large number of resources (20 million or more), where the creation of new resources takes longer and longer, the more resources you have in the Fedora DB containment table.

If you have an URI with underscores (in our case all URIs have at least 2 underscores, and some even more than that), a LIKE query like LIKE "abc_123_235/%" is very expensive to execute, as there are multiple wildcards in the query and the current DB indexes only help if there is a single wildcard at the end of the string. Correctly escaping the underlines (e.g. {{LIKE "abc_123_235/%")}}can reduce the time needed to execute the query from a few seconds to a few milliseconds, solving our performance issues.

I created a fork of the Fedora code and solved this issue there (including some tests which will fail if underscores and percent signs are not escaped). I will create a PR and hope this can be added to the next release of Fedora.

Ben Pennell, 2025-10-15 19:00 UTC

Since this case is tricky, but relatively easy to replicate with the right setup, it would be good to add a integration test to verify it works. The following could be added to FedoraLdpIT, you’re welcome to do so since I can’t update the PR:

    // Replicates FCREPO-4032
    @Test
    public void testPutParentWithUnderscores() throws IOException {
        final String subjectURI1 = serverAddress + getRandomUniqueId() + "/te_st";
        final HttpPut putMethod = new HttpPut(subjectURI1);
        try (final CloseableHttpResponse response = execute(putMethod)) {
            assertEquals(CREATED.getStatusCode(), getStatus(response));
        }
        final String subjectURI2 = serverAddress + getRandomUniqueId() + "/te_st/child";
        final HttpPut putMethod2 = new HttpPut(subjectURI2);
        try (final CloseableHttpResponse response = execute(putMethod2)) {
            assertEquals(CREATED.getStatusCode(), getStatus(response));
        }
        final String subjectURI3 = serverAddress + getRandomUniqueId() + "/t__st";
        final HttpPut putMethod3 = new HttpPut(subjectURI3);
        try (final CloseableHttpResponse response = execute(putMethod3)) {
            assertEquals(CREATED.getStatusCode(), getStatus(response));
        }
    }

I also tried doing a simple performance test with the branch and without it, creating 50k children nodes in the same ghost node containing underscores and percent signs. The updated branch slightly out performed the original version, but not by a significant margin.

It may be that a different setup would have demonstrated the difference better. Also, looking at the queries, I suspect it’d have a larger impact if I’d been using transactions, since that version of the query repeats the LIKE clause three times. It may also have a bigger impact for larger repos, or when using a database other than H2. Regardless, I did see the time required to create new resources gradually increase, from about 8ms to a consistent 120+ms at the end.

Did it improve the performance issue you were seeing? This change seems good either way, I’m just curious
