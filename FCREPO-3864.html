FCREPO-3864 Items added quickly can mask some momento versions

TypeBug
StatusOpen
PriorityMinor
ReporterQuinn Hart
Created2022-11-09 22:27 UTC
Updated2025-06-12 15:59 UTC
Affects versionsFedora 6.3.0

Environment

docker 6.3.0-SNAPSHOT

Description

If you update an item too quickly, the one second timestamp for versions can be too coarse for all versions to be available:

  version=6.3.0-SNAPSHOT
  docker image pull fcrepo/fcrepo:$version
  docker run --rm --name=fcrepo --publish 8666:8080 fcrepo/fcrepo:${version} 2>fcrepo.err >fcrepo.log &
  sleep 5
  docker exec fcrepo bash -c "{ apt-get update; apt-get install tree; }"

  info_fedora="<http://localhost:8666/fcrepo/rest">
  put_art="curl -XPUT -u fedoraAdmin:fedoraAdmin -H'Content-type:text/x-ascii-art; charset=utf-8' --data-binary @-"
  #          sleep 2
  echo -e " n n\n(o.o)\n l \\ \n mm/\\===\n" | $put_art $info_fedora/pet:/99/ashley/image.art
  #          sleep 2
  echo -e "  ∧_∧\n ̳o.o̳\n  |♡\\ \n" | $put_art $info_fedora/pet:/99/ashley/image.art
  #          sleep 2
  echo -e "\\    /\\ \n )  ( \`)\n(  /  )\n \\(__)|" | $put_art $info_fedora/pet:/99/ashley/image.art

  docker exec fcrepo bash -c "tree fcrepo-home/data/ocfl-root"
  for i in $(curl -u fedoraAdmin:fedoraAdmin $info_fedora/pet:/99/ashley/image.art/fcr:versions \
                  -H'Accept:application/ld+json' |\
                 jq -r '.[]["<http://www.w3.org/ns/ldp#contains"][]["@id"]')> ; do
      echo $i ;
      curl -u fedoraAdmin:fedoraAdmin $i;
  done
  docker stop fcrepo

Without sleep, not all versions are available, though the data is fine.

This is part of the Memento specification, so as you note while multiple versions are stored in Fedora the Memento specification only allows for the second granularity. So we return the last version within any given second.

https://www.rfc-editor.org/rfc/rfc7089#section-2.1.1

Jared Whiklo, 2022-12-09 15:18 UTC

We wanted to keep the output of versions consistent and not have a difference of result depending on the Accept header. It seemed wrong to show 4 versions for one but 5 (or 6, 7, 8) for the other.

As for using a name versus the date/timestamp, OCFL stores the date time of the version creation. To avoid tracking a new “name” attribute used only for versions we just reuse that date/timestamp. It also gives you the opportunity to decode that information from the URI.

If you could explain your use case a bit it would help me see how we could account for it.

Lastly, I would also say that I would personally avoid making too many versions within a single second. There is some weight to OCFL, so if you are making multiple changes (presumably by code) within a second then (IMHO) you should use a transaction to wrap them into a single version.

Quinn Hart, 2022-12-13 21:59 UTC

I agree that the number of versions should stay the same, but that’s why I suggest the timemap just shows every version even if they share the same timestamp. That would help to decode the issue.

regarding the name, that’s why I suggested just using the native OCFL versions (v1,v2..) of the object, so that the versions in the fcr:versions are consistent w/ the versions you’d see if you were looking at the OCFL filesystem directly.

Regarding the use case, we originally identified this problem trying to track down an intermittent issue on imports that occasionally failed, but the more obvious example is when different clients are PUTing to the same resource, and they don’t know of each other. I haven’t yet checked to see if you can get this same condition even if you are checking state tokens, on your puts, but I can check that later.

Quinn Hart, 2023-02-27 20:54 UTC

Just a note that I think this is more than a minor issue, since it means you can get different results with the exact same requests, just based on the computer’s time.

Also, as discussed, it seems to me this against the momento specification that requires a timemap show every version.

Jared Whiklo, 2023-09-14 20:13 UTC

There was discussion about this at past Tech call’s and the resolution was to allow for displaying the versions when retrieving from the timemap as non application/link-format content-type.

So this ticket is now to alter the display of a TimeMap to leave showing the most recent version for each second when viewing as application/link-format and to show ALL versions when viewed as another RDF type.
