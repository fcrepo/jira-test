Description

Batch ingests of large "archival" base-64 encoded objects were failing with a StorageDeviceException error. The following was also appearing in fedora.log: com.mysql.jdbc.MysqlDataTruncation: Data truncation: Data too long for column 'dcRelation' at row 1

In the table doFields, the column type for dcRelation was altered from TEXT to LONGTEXT and ingests were successful. Could Fedora automatically create the table with this column type?

Comments (4)

Stephen Bayliss, 2010-04-23 14:30 UTC

MySQL has a 65,535 character limit for TEXT fields (LONGTEXT is 4,294,967,295) - other databases impose no such limit (PostgreSQL) or have a much larger limit (MS SQL Server 2GB, Oracle CLOB - used for "text" - 4GB) so it would seem sensible for the MySQL interpertation of the "text" field specification in DefaultDOManager.dbspec to be LONGTEXT (org.fcrepo.server.utilities.MySQLDDLConverter).

Similarly we might consider using LONGBLOG instead of BLOB for binary fields (though currently all of the binary fields are specified as varchar, so won't cause an issue.).

Stephen Bayliss, 2010-04-27 16:13 UTC

This would require (should) a rebuild on upgrade to 3.4 to ensure everyone's databases are consistent - we may want to consider whether or not we include it in 3.4 on that basis

eddie, 2010-04-27 16:16 UTC

This is minor, but just so it's documented: additional storage requirement for LONGTEXT vs TEXT in MySQL is 2 bytes: http://dev.mysql.com/doc/refman/5.0/en/storage-requirements.html
