Description

sorry, but I love Gradle. The Groovy DSL really makes Maven's XML seem archaic and incredibly rigid. It is also fast. A clean fcrepo build takes around 30 seconds (without docs and IT tests).

Here is a first look at the commit of my changes.
https://github.com/pan-dora/fcrepo4/commit/6514f233573bfae3c350f3e1a1e35d3f2912e483
My main reference for this was the Spring Framework, who have a rather complex build in Gradle. There are a lot more tasks that can be added. I have also made a docker task that can create and tag an image. The image can be customized for different test scenarios.

The main issue is that Gradle build properties must be in Camel case so the current use of property names like "fcrepo.some.config" has to be changed to fcrepoSomeConfig in the repository configuration files. It is still possible to expand the Camel case properties at build time into the expected "system properties variables" (i.e. with the dot separator) for runtime injection in a global gradle.properties file.
https://github.com/pan-dora/fcrepo4/blob/gradle-build/gradle.properties

I also found and fixed several missing dependencies, primarily with the tests.

My overall (future) goal is to do integration tests with the jdk.incubator.httpclient using JDK 9 / JUnit 5 / Spring 5. With a Gradle build, it is (for me) also easier to address the probable compilation problems that are the result of the strong encapsulation requirements in JDK 9. I have not tried it yet with fcrepo, but I have built the client.

Unknown, 2017-08-23 18:58 UTC

I will probably not be on the tech call, but let me describe my experience with Gradle.

I have used Gradle for several years on probably 20-30 JVM-based projects (Java and Clojure). I vastly prefer it to Maven, and every new JVM-based project I have started in the last year or two uses Gradle. Having released a good number of artifacts over the years to Maven Central (using both gradle and maven), I can also attest to the fact that Gradle is actually considerably easier than Maven – at least it's a lot easier than the way Maven is set up with Fedora4.

Between Gradle and Maven, the Gradle configuration is also considerably smaller – in some of the conversion projects I've worked on (IIRC), it ends up being about 10-20% of the size of the maven configuration, which in my book is a massive win.

In terms of working with Gradle, I would also vastly prefer using the Groovy syntax over XML. I actually don't know much Groovy – only enough to work effectively with Gradle; one doesn't need to be an expert in Groovy to work effectively with Gradle.

Christopher Johnson has already mentioned the performance advantages of running the build and test suites with Gradle; I have also found that to be true: it is considerably faster to use Gradle than to use Maven.

Gradle is also entirely self-contained. Whereas with Maven, a developer must first install maven on their computer, with Gradle, there is no installation step; all Gradle needs is a jar file, and if that's not available, it downloads it for you.

Fedora uses a lot of Maven plugins. Every one of those plugins can be replaced with some equivalent in Gradle. (I know what plugins are used with Fedora4, and I have Gradle equivalents in much of the code I maintain). Well, there is one exception: the maven-site plugin – the plugin that generates pages like this: http://docs.fcrepo.org/site/4.7.4/fcrepo/ Admittedly, I haven't looked extensively for an equivalent Gradle plugin, as I've never been convinced of the utility of these maven-generated pages.

Gradle also gives you considerable more control over the build phases in comparison to Maven. This is especially useful for OSGi integration testing where you need a local mvn install to occur before mvn test, which isn't really possible with Maven.

One advantage that Maven has over Gradle is the use of parent poms that get inherited by external subprojects. Gradle has something that is sort of equivalent (external build scripts), but I have never used those. I also think that extensive use of parent POM configuration is a little over-rated, and I don't think it would justify not using Gradle.

The thing about Gradle is that it has a very different view of what a build system is. Maven is pretty rigid, in that it consists of plugins that are applied and configured, but there is very little flexibility beyond that. With Gradle, you have an entire scripting language at your command, and using that you can control the details of the build process much more effectively.
