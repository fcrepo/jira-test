Description

Legacy storage:
INGEST: foo:1 201310091500000
1) DOManager checks the pidRegistry Db for foo:1
2) if no, creates

{OBJECTS}/2013/10/09/1500/000/foo_1
Akubra storage:
INGEST: foo:1 201310091500000
1) ditto
2) if no, MD5 “info:fedora/foo:1”
3) build directory structure from hash advantage: you don’t have to look up path in Db
Scenario: As of 20131010, Db is corrupt, or not up to date, or incomplete, or maybe the last val for PIDs in namespace just reset
Legacy:
INGEST: foo:1 201310101500000
1) DOManager checks the pidRegistry Db for foo:1
2) if no, creates {OBJECTS}

/2013/10/10/1500/000/foo_1
Where are you now? Original foo:1 is orphaned, but exists, as do datastreams
Akubra:
Everything that has the same id gets overwritten irreperably
Circumstances that this happens in:
1) pidRegistry is jacked
AND 2) you use sequential pids (as opposed to random, or UUIDs) AND 3) you use Akubra (Legacy you just have orphan objects)
What can we do?
1) Legacy, we can build a report of duplicates, and possibly provide a FCSU command to move them to a unique PID
2) Akubra, we can really just tell you that an objectCreation date is out­of­sequence with it’s PID (this is crappy)
Is this behavior on ingest in the context of a bad Db fixable?
1) Legacy: not really. To do this without the Db, you would have trawl the corpus of FOXML, which would not only be slow, but the would be maximally slow
on the non­error requests (ie, a new PID). Non­starter.
2) Akubra: Yes, because the DOManager could be required to ping an Akubra objectstore as part of the objectExists() call. Raise an exception.

Michael Durbin, 2013-10-17 01:41 UTC

I did some initial testing regarding the impact and have determined the following:

For Fedora 3.6.2 using a mySQL database and the akubra-fs store:

1. To "corrupt" the database in a way that might result in problem described above one can simply interrupt a database rebuild operation.
2. Corruption in this manner is already detected in cases where the process is interrupted before all four fedora system objects are ingested and no data corruption/overwriting would occur.

Detailed analysis:

That an interrupted or partially complete database rebuild (at least with mysql in the default configuration) can leave the database in a state where fedora starts up without an error is a pretty significant problem. I would think we could do something with transactions to ensure that either the database rebuild completed or didn't so that errors would be more easily identified. (ie, fedora started and has zero objects)

That said, the cases where you'd end up with a database state that would allow startup but would have a value in the pidGen table that could result in reuse of pids is unlikely to occur. For that to happen the pids for all four service objects (who, when missing from the digital object registry but presence on disk result in a failure of fedora to start) would have to have hash values lower than the hash value for the object with the highest pid. Unfortunately in my initial testing, this wasn't the case and I have yet to demonstrate an organically produced case that would actually result in the ability to overwrite data in the akubra file store.

Methodology:
1. Installed fedora 3.6.2
2. started server and verified that it worked
3. stopped the server
4. replaced its data directory with one that had > 10k objects
5. performed a fedora database rebuild (fedora-rebuild.sh
7. hit CTRL-C to abort the database rebuild
8. attempted to start fedora

Remaining steps for akubra-fs investigation and mitigation:

1. Produce a case where the hash values result in a repository that is incompletely rebuilt but starts up and see if normal API calls will actually overwrite data in the akubra-fs
2. Alternately or additionally, search the code for cases where Blob.openOutputStream() is called with overwrite set to true, or Blob.delete() is called and trace to see if this poses a vulnerability with possible invocation sequences
3. Fix the fedora database rebuilding utility to prevent this from occurring
4. Create a way to verify a database reflects all files for an akubra store

Benjamin Armintor, 2013-10-30 01:11 UTC

Michael Durbin's observation adds an additional criterion for Akubra risk: A failed rebuild job must have indexed all the system objects, which (assuming MD5 hashes) is about 1/2 of any given repository (system objects will be in buckets 08, 2e, 74, and 9c by default). Also (perhaps obviously), custom configs that introduce date-driven paths to Akubra will behave like the Legacy store.
