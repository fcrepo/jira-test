Comments (4)

Ben Pennell, 2026-07-16 15:56 UTC

We discussed this issue in today's fedora tech meeting. The current behavior originated from this ticket in 2018:

https://fedora-repository.atlassian.net/browse/FCREPO-2923

In which the premis:hasSize field was changed from being a strictly server managed triple to being a server generated triple that could also be set by clients. This was to support some external binary scenarios in which fedora is unable to determine the size of a binary.

We will investigate the implementation and try to determine how to support both the needs of external binaries and the need for accuracy with internal binaries, as well as meeting RDF requirements. Two potential approaches discussed were:

  1. Prioritize the user defined premis:hasSize over the system generated one.
  2. Make premis:hasSize server managed for internal binaries, and server generated for external binaries.

We will need to research how the property is set in update and creation scenarios, and determine if the way in which overridden premis:hasSize properties are stored needs to be adjusted. For example, rather than storing the overrides as RDF, could we modify the fedora header file instead?

Ben Pennell, 2026-07-27 14:01 UTC

As an immediate fix for the issue in this ticket, we could deduplicate the RDF response if there are two premis:hasSize or premis3:size properties with identical values. So if there are two properties with value 0, we'd end up with one, but if they have different values we'd return both. This is only to prevent invalid RDF responses.

For a longer term fix, my recommendation would be to make overriding the binary size exclusively to external binaries by introducing a "size" parameter to the ExternalContent Link header (we already have a custom param in this header, "handling") used to create/update them, for example:

curl -i -H"Link: <file:///local/file/storage/wonderful.tiff>; rel=\"http://fedora.info/definitions/fcrepo#ExternalContent\\"; handling=\"proxy\"; type=\"image/tiff\"; size=\"6551596\"" -XPUT -ufedoraAdmin:fedoraAdmin http://localhost:8080/rest/test_proxy

We would set the fcrepo size header for the binary from this value. It is used to set Content-Size and premis:hasSize/premis3:size in responses. If its not supplied, then the size would be set with existing behaviors.

To support this, premis:hasSize/premis3:size would become server managed triples again. This would prevent accidentally setting stale or duplicate properties. The existing behavior is also misleading since the supplied premis:hasSize values aren't used for setting Content-Size response headers, which depend entirely on the fcrepo header field in fcrepo 6+.

We could introduce the Link header change either in a patch or minor release, since its either a new feature or a corrected way to perform an existing feature. For the server managed triple aspect, that might require a major release (or at least a minor one) since it would block a workflow that clients might depend on. Although I will note that premis3:size was just introduce in 7.0.0 so the likelihood of an integrations there are extremely low, so we could possibly move more quickly on that.
