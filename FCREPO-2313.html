FCREPO-2313 Fedora violates RFC 7232 with 304 responses

Description

RFC 7232 explicitly states that 304 "Not Modified" responses to conditional requests MUST not contain an entity body:

"A 304 response cannot contain a message-body; it is always terminated
by the first empty line after the header fields."

Responses from Fedora do have an entity body. When Fedora accessed via clients such as Apache Httpclient, this can cause apparent corruption of responses from Fedora. HttpClient does not consume entity bodies from requests that return a 304. The bytes from the errant entity body returned from Fedora can remain in internal HttpClient buffers, corrupting reads from subsequent responses.

Elliot Metsger, 2016-11-18 04:39 UTC

HTTP 304 responses must not have an entity body, and there is no behavior required by the specification when a 304 response with an entity body is encountered. Therefore, servlet containers are free to respond in whatever way they wish when processing these errant responses.

Attached is a script which elicits this behavior from Fedora, and example output from a variety of servlet containers and versions Fedora. Tomcat 8.5.6 exhibits the best behavior (strips out the entity body; responses appear as if the entity body was never added), Tomcat 9 exhibits the most bizarre behavior (multiple responses!), and Jetty sits somewhere in the middle. Fedora 4.6.0 and 4.7.0 were tested. The master branch has the bug, but was not directly tested.

PRs for all three major branches of Fedora have been produced:

  • https://github.com/fcrepo4/fcrepo4/pull/1141
  • https://github.com/fcrepo4/fcrepo4/pull/1142
  • https://github.com/fcrepo4/fcrepo4/pull/1143

To view this behavior, launch Fedora and execute the attached script, FCREPO-2313 Closed .sh. It requires netcat, and by default will connect to Fedora running on localhost, port 8080. The script accepts a hostname and port as command-line arguments.

Example usage ("apix" is a Docker container running Fedora under Jetty):

$ ./FCREPO-2313.sh apix
HTTP/1.1 304 Not Modified
Cache-Control: no-transform, must-revalidate, max-age=0
ETag: ""
Content-Type: text/turtle
Content-Length: 13
Server: Jetty(9.3.9.v20160517)

$

What you are looking for is some kind of indication of a malformed response, which will manifest itself differently depending on your servlet container. In the above example, you can see that there is no entity body, however there is a Content-Length header of 13 bytes, which indicates an entity body once existed on the response, but was stripped out.

Other example output:

HTTP/1.1 304 Not Modified
Date: Fri, 18 Nov 2016 03:00:43 GMT
Cache-Control: no-transform, must-revalidate, max-age=0
ETag: ""
Content-Type: text/turtle
Server: Jetty(9.2.3.v20140905)

Date mismatch

A different version of Jetty, which doesn't attempt to do anything with the entity body; it just passes it along.
