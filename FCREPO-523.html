Description

From the RFC for HTTP 1.1:

The POST method is used to request that the destination server accept
the entity enclosed in the request as a new subordinate of the
resource identified by the Request-URI in the Request-Line.

If a resource has been created on the origin server, the response
SHOULD be 201 (Created) and contain an entity which describes the
status of the request and refers to the new resource, and a Location
header (see section 14.30).

Whilst an initial create is conformant to the spec as the posted resource becomes GETable at an alternate location (/content), not returning a Location header is highly confusing for new users/developers.

POST for creation is typically reserved for POSTing to a collection URL, which will return a URL of the created resource (if created)

Chris Wilper, 2009-11-26 21:23 UTC

The more I look at this one, the more I find the use of POST vs PUT for "add" and "modify", to the same URI, to be strange.

I think PUT might be the wrong verb for modify altogether; should the operation really be considered idempotent if the default behavior is for Fedora to create a new, accessible revision of the datastream? (for one request, this would result in a different datastream "history" than for two identical requests).

It seems safer, semantically, to use POST for both.

Stephen Bayliss, 2009-11-27 09:49 UTC

Doesn't Fedora's notion of versions vs history come in to this?

a "modify" via PUT could be considered a modification of the datastream content, with Fedora in the background keeping track of changes and the datastream history. If Fedora doesn't consider versions as identified resources in their own right, but instead permits access to the history of datastreams, then it seems to me that this is ok. The response then doesn't need to return a URI for the new version created, as this can be considered "internal" to Fedora. From the perspective of the datastream content URI it is idempotent as multiple calls will result in the same datastream content. (and the location header should just be the datastream content? - ie the resource which was requested to be modified?)

And if versions are promoted to first-class identifiable resources then it should be a POST to a datastream versions URI, with a new subordinate being created. (And in that case I'd recommend using datastream version Identifiers directly and treat the modification date as an attribute, not as part of the identifier).

So in fact we could support both if we expose versions as a collection; PUT to the datastream content (modify) and POST to the datastram versions (returning a URI for the new version).

Is the intent of the method to modify a datastream, or is it to create a new datastream version? Personally I like the idea of versions being internal, with Fedora being capable of showing an object's history.

Chris Wilper, 2009-11-28 10:11 UTC

Steve, thanks for your comments on this. I also found this particularly relevant:

From http://tech.groups.yahoo.com/group/rest-discuss/message/7387
"What matters is the effect on the interface as expected by the client, not what actually happens on the server to implement that effect."

Actually, the whole thread there really speaks to this question. And the subsequently-updated httpbis draft now clarifies here: http://trac.tools.ietf.org/wg/httpbis/trac/changeset/657
"It is important to note that idempotence refers only to changes requested by the client: a server is free to change its state due to multiple requests for the purpose of tracking those requests, versioning of results, etc."

So I think you're right, that it boils down to the intent of the client. Although it may be aware that Fedora is keeping an accessible history of revisions around, the primary reason for making the request is to replace the resource in question (the current revision of the datastream) with the one implied by the request.

As you point out, in the current REST API, we have not made datastream versions first-class web citizens. I'm also happy keeping them that way for now.

- You're POSTing to a resource that doesn't yet exist.
- If we agree that "modify" is idempotent as described above, then surely "add" has the same property.

PUT {pid}/datastreams/{dsId}

Chris Wilper, 2009-12-01 12:49 UTC

Ugh. I've been updating the webadmin (flash) client, and have uncovered a problem that argues for continuing to support POST.

To quote myself:
> If PUT to the datastream URI is adequate to support the functionality we want to expose, I would favor just having one way
> [...]
> If a client has problems doing "real" PUTs, there's always the X-HTTP-Method-Override trick.

In order to upload content from the user's filesystem, the webadmin client reverts to standard browser behavior (a file upload form) due to file upload limitations with Flash (it cannot reliably provide file upload capabilities when the server is protected by http authentication).

Unfortunately, browsers generally don't support PUT as the method for file upload, and we also cannot manipulate the HTTP request headers when such a form is employed (so the X-HTTP-Method-Override trick doesn't work).

Using XMLHttpRequest to submit the request is also not an option in this case: browsers generally don't provide javascript access to file content when "Browse..." is invoked on a form.

Of course, this problem isn't just limited to the webadmin client. If someone were to try to develop a non-flash (ajax) interface that allowed upload of content to Fedora, they would run into this problem as well. For this reason, I think it makes sense to continue supporting POST for adding and modifying datastreams.

Modifying, you ask? Yes, although the current REST API documentation (as of Fedora 3.2.1) states that adding is done through POST and modifying is done through PUT (and this is true), it omits the fact that modifying a datastream is also possible via POST. This fact needs to be documented.

Chris Wilper, 2009-12-01 16:07 UTC

Fixed in trunk. Now, on successful POST to this url, response will be:

  • Status code 201 (Created)
  • Location header to this url
    On successful PUT to this url, response will be:
  • Status code 200 (OK)
    In either case, response body (text/xml) is now the resulting datastream profile xml.
    Updated javadocs to clarify that POST may be used for add or modify.
    If PUT is attempted for non-existing datastream, response will be 404.
    Added tests for each of these cases

This does not address the REST-oddness of POSTing to a resource that doesn't exist (which, btw, also exists in the case of ingest), but it should be backward-compatible with clients that worked with 3.2.1, since it just adds additional information to the responses.
