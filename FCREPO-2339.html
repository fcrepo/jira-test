FCREPO-2339 Separate OSGI (blueprint) code from the JAVA code in fcrepo-camel-toolbox

Description

At present, the camel-toolbox components each contain a Blueprint-based configuration. This is convenient, but it makes it impossible to run multiple instances of any of the components in a single container. It also prevents "advanced" customization of the various components.

What I propose is removing the blueprint configuration for the existing fcrepo-* artifacts, and then creating separate artifacts with the OSGI configuration. The included features.xml file should be updated so that the installation process doesn't change from a user's perspective.

A README note mentioning how to extend these routes would be good, too.

Aaron Birkland I would be curious to know what you think of this ticket and the prospect of getting it into the fcrepo-camel-toolbox/4.7.0 release.

I see two particular use cases for this – one is a use case that I have at Amherst, and another is something I've heard from Peter Matthew Eichman.

The basic issue here is that, by separating the blueprint configuration from the java code, it is possible to do more "advanced" configuration of the toolbox components. For example:

At Amherst, we will be using some linked data endpoints in combination with fcrepo-ldpath that aren't supported "out of the box", such as Getty endpoints. By customizing the blueprint configuration, I can reuse all of the other code. An alternate option is to put the Getty customizations into the main configuration – but the reason I'm hesitant to do that is that I don't know where that would stop – do we cut a new release every time someone wants to add a specialized endpoint (e.g. a new Stanbol entityhub or some new linked data endpoint)? That seems like an unnecessary combination of code and configuration. By separating the configuration, it will allow us to provide a minimal blueprint configuration for general use while making it possible to customize this.

The other use case that I have heard comes from UMD. At present, it is not possible to run multiple toolbox components in the same Karaf container – e.g. a triplestore indexer for the production repo and an indexer for the dev repo. By separating the blueprint config from the fcrepo-indexing-triplestore bundle, that fcrepo-indexing-triplestore bundle can be reused by multiple blueprint configurations – e.g. a "simple" one – i.e. like what currently exists and a custom one based on different configuration properties.

While this change would be entirely transparent to users, I still think it falls under the category of "breaking changes" since the core OSGi bundles would no longer export the blueprint configuration (those would be exported by other bundles).

Thoughts?

And this would be the last bit of development work before the release of fcrepo-camel/4.5 and fcrepo-camel-toolbox/4.7

Also, it may be worthwhile to look into Declarative Services and the Service Component Runtime (SCR) at some point; I don't think it'd be incompatible with this approach, and could be retrofitted into the now-blueprint-free existing bundles at any point, should need arise.

One aspect I like about Declarative Services (which may be relevant to the use cases driving this ticket) is how it interacts with ConfigurationAdmin. I'm particular, it's easy (via the way Karaf wires felix fileinstall into its ConfigurationAdmin) to create new instances of services merely by dropping new configuration files into /etc or /deploy.

In particular, I've used the following pattern before with some success

  • If a feature is deployed, nothing runs by default
  • Drop a config file with a name like org.example.whatever-A into /etc, then it deploys an instance of the service initialized with the properties from that file
  • Drop another config file with a name like org.example.whatever-B into /etc, then it deployes a second instance of the service, initialized with the properties of -B
  • Remove a configuration file to remove the service instance associated with it.

So the above pattern would work well for multiple instances of toolbox services that differ only in properties configuration. I have not found a way to get that pattern to work with Blueprint; only DS and SCR. So if blueprint is removed from the existing bundles, there's an opportunity to non-invasively enable the above behavior with a little bit of effort.

Bethany Seeger As I see it, this change would be entirely transparent for end users. Here's a specific example with the fcrepo-indexing-triplestore:

At present, there is a single bundle called fcrepo-indexing-triplestore, which contains both the Java classes (which implement the Camel routes) and the Blueprint data for tying everything together: the ActiveMQ broker, the Karaf-based configuration properties and the Java implementation code. The Karaf features.xml file includes only that fcrepo-indexing-triplestore bundle (plus other dependencies).

The change would be like so: the implementation code would still reside in the fcrepo-indexing-triplestore bundle, but that bundle would not contain the OSGI-INF/blueprint/blueprint.xml configuration. Instead, the Blueprint data would be in a separate artifact, say fcrepo-indexing-triplestore-blueprint. The features.xml file would then also reference the blueprint-based artifact.

This way, if one wants the "standard" indexer, one would simply do the standard: feature:install fcrepo-indexing-triplestore command. But one could also add a custom blueprint.xml file to the ./deploy directory with separate configuration values (and perhaps a separate message broker), and the two indexers would work well in the same container.
