Stephen Bayliss, 2010-01-29 01:07 UTC

PIDs can contain escaped octets (http://www.fedora-commons.org/confluence/display/FCR30/Fedora+Identifiers), however the % character itself will need to be URL-encoded when the PID is used as part of a URL (or indeed in a query string). Specifying "%2F" as any part of a URL will result in URL-decoding to the slash character.

http://tools.ietf.org/html/rfc3986#section-2.4 specifies that the % character itself must be encoded if the octet is to be used as data.

Stephen Bayliss, 2010-05-12 21:45 UTC

I'm not sure if we should treat this as a regression.

RFCs 1738 (2.2) and 2396 (2.4) are pretty explicit on this: if a % character is to be treated as data then it must be escaped in URLs and URIs.

So if the (normalized) PID is hdl:2200%2F20061002130521143T then in a URI this must be represented as hdl:2200%252F20061002130521143T

If the previous behaviour was to not URL-decode the percent-escaped octets, then this was in fact a bug.

The position with regard to ":" appears to be more ambiguous:

RFC1738 2.2 - Reserved
states that ":" may be reserved, and if a character is reserved then it must be encoded. However in the path part of a URL ":" is technically not reserved (only / ? & # are used as separators) and therefore does not have to be encoded.

RFC2396 2.4
states that it is up to the implementation (ie the scheme - in this case http) as to whether a character is a subcomponent delimiter and therefore must be escaped. It would seem that in this case it is not a subcomponent delimiter (although it is used as such in other parts of a URL) and therefore does not have to be escaped.

It's perfectly valid in any case to percent-encode an unreserved character (and the URIs should be treated as semantically equivalent) - so both ":" and %3A forms should be accepted.

Most software seems to accept ":" unencoded in a path without a problem, although most URL/URI encoders seem to encode ":" as %3A.

So I would suggest
(1) we accept ":" and "%3A" in URLs - but in any UI we render as "%3A" to be consistent with most URI encoders and decoders (Java URI decoding and encoding should handle this seamlessly)
(2) we ensure that all path segments/delimited sections of URLs are correctly decoded in REST API calls, so that % characters in PIDs must be encoded as %25 (it looks like this is currently not happening in the LITE APIs, looking at FCREPO-224 Closed and the testing above, but appears ok in the new REST API)
(3) the search, object view etc pages need reviewing to ensure they're correctly encoding URLs in the pages

It would appear from the testing above that the LITE APIs do not do URL-decoding correctly, but the new REST API does (but this needs further testing). If the LITE API behaviour has in fact changed recently we could consider this a regression, and fix it in the LITE APIs as well (although we could consider not doing this as the LITE API is to be deprecated).

(For info - and warning - , Firefox has the behaviour of un-escaping percent-encoded characters in the address bar - however if the address is copied and pasted elsewhere the percent-encoding is in fact retained. So if a URL which contains %3A is clicked on, the address will appear in the address bar to contain ":". This gets even more confusing when a % character has been encoded to %25 so an encoded sequence such as %2525 will get rendered as %25 - looking like an encoded character when it's not...)

Stephen Bayliss, 2010-05-13 17:28 UTC

Noting that
(a) the original bug report is concerned with HTML views produced by API-A LITE, specifically incorrect URLs in links
(b) object view production (through xslt) is shared with the new REST API (apart from the "search" view)
(c) all object views produce URLs referring to the new REST API
(d) the LITE APIs do not accept (or require) URL-encoding
(e) the new REST API requires URL-encoding

fhe following has been implemented

  • modify all xslt producing HTML views to correctly URL-encode PIDs
  • modify both API-A LITE and new REST API search interface HTML production to correctly URL-encode PIDs
  • modify the describe API method to render URLs (including URL-encoding of PIDs) within the new REST API (was using API-A LITE)
  • modify the XML output from getObjectProfile to URL-encode PIDs in the dissemination and item index URLs
  • update documentation for API-A LITE to indicate that URL-encoding is not necessary (and is not accepted)
  • update documentation for REST API to indicate that URL-encoding is mandatory (particularly applies to percent-encoded octets in PIDs)
  • reopen, and unlink, FCREPO-224 Closed , as this is not fixed by the above and now appears to be a separate issue
