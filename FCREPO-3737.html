FCREPO-3737 RELS-EXT should be included in the migration to OCFL as native RDF

Description

Currently RELS-EXT data migrates to OCFL as a binary file. We would like the RELS-EXT, which contains RDF, to migrate to OCFL as native RDF.

Peter Winckles, 2021-09-10 19:23 UTC

@Geoff Scholl: I was just thinking about this ticket, and I’m not sure if it makes sense to migrate RELS-EXT as an RDF container rather than as a binary.

At UW-Madison, and my assumption is that this is true for you as well, RELS-EXT describes relationships for the Fedora 3 object. When the object is migrated to Fedora 6 it loses the distinction between an object and its datastreams. Instead, objects are modeled as RDF containers that contain all of their datastreams, which are modeled as binaries.

Let’s look at a concrete example. We have object info:fedora/1711.dl:52O74PJ27SFY58D in Fedora 3 which has the following RELS-EXT:

<rdf:RDF xmlns="info:fedora/fedora-system:def/model#" xmlns:dc="http://purl.org/dc/elements/1.1/" xmlns:fedora="info:fedora/fedora-system:def/relations-external#" xmlns:foxml="info:fedora/fedora-system:def/foxml#" xmlns:oai_dc="http://www.openarchives.org/OAI/2.0/oai_dc/" xmlns:rdf="http://www.w3.org/1999/02/22-rdf-syntax-ns#" xmlns:rdfs="http://www.w3.org/2000/01/rdf-schema#" xmlns:uwdc="https://digital.library.wisc.edu/1711.dl/rdf/1.0/relations#" xmlns:uwdcr="https://digital.library.wisc.edu/1711.dl/vocabulary/resourcetype#" xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance" ID="RELS-EXT">
  <rdf:Description rdf:about="info:fedora/1711.dl:52O74PJ27SFY58D">
    <hasModel rdf:resource="info:fedora/1711.dl:CModelUWDCObject"></hasModel>
    <hasModel rdf:resource="info:fedora/1711.dl:CModelMaster"></hasModel>
    <hasModel rdf:resource="info:fedora/1711.dl:CModelSimpleText"></hasModel>
    <fedora:isMemberOf rdf:resource="info:fedora/1711.dl:6YV6NVSHOUAN48A"></fedora:isMemberOf>
    <uwdc:isMemberOfProject rdf:resource="https://digital.library.wisc.edu/1711.dl/WWILibraryPrj"></uwdc:isMemberOfProject>
    <uwdc:hasAccessPolicy rdf:resource="https://digital.library.wisc.edu/1711.dl/Access-policy-open-access-all"></uwdc:hasAccessPolicy>
  </rdf:Description>
</rdf:RDF>

Now, when that’s migrated to Fedora 6 there will be two resources, info:fedora/1711.dl:52O74PJ27SFY58D, an RDF container, and info:fedora/1711.dl:52O74PJ27SFY58D/RELS-EXT, a binary. If we changed the second to be a container, it becomes weird because those triples would be applied to info:fedora/1711.dl:52O74PJ27SFY58D/RELS-EXT. That is to say, info:fedora/1711.dl:52O74PJ27SFY58D/RELS-EXT is not a info:fedora/1711.dl:CModelMaster – info:fedora/1711.dl:52O74PJ27SFY58D is.

What might make sense instead is if RELS-EXT was not migrated at all and instead its triples were added to the container resource that represents the object.

Similarly, with RELS-INT, it might make sense to not migrate it at all and add its triples to the resources that they apply to.

Demian Katz, 2021-09-10 19:52 UTC

Peter Winckles , I agree – and I think the intent of our original ticket was actually exactly as you describe: that the triples from RELS-EXT be added to the container representing the original Fedora object, rather than as a binary XML datastream or a separate RDF container.

Depending on the possible complexities and confidence levels, I suppose it might be useful to have a configuration to choose either approach, or even both approaches – e.g. migrate the triples, but also keep the original document as a binary for historical purposes.
