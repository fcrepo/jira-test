Description

In some audit scenarios, it is important to prevent deletion of audit records. To support this, investigate options for access control and/or disabling deletes in an external triplestore.

Fuseki does not appear to have builtin access control functionality (see http://jena.apache.org/documentation/serving_data/#security-and-access-control), but Sesame uses a standard Java servlet container and so should support access control (see http://www.rivuli-development.com/further-reading/sesame-cookbook/basic-security-with-http-authentication/).

Former user, 2015-04-06 13:03 UTC

I don't think this is going to be as simple as configuring the servlet container to disallow deletes. SPARQL Update is used for creating, updating and deleting triples over HTTP POST. So Camel or any other processor would need to be able to POST in order to create audit events.

So, I think there are three options we can consider for implementing this requirement, in order of increasing difficulty:

1. Defer this requirement to phase 2, and assume that users who want to prevent deletion will also want to have in-repository event storage for maximum confidence that all audit records are preserved.
2. Document how to enable access control for Sesame (to give users the ability to query the triplestore without being able to modify it) and that the Camel workflow won't delete triples.
3. Create a SailConnectionWrapper implementation that would actually let you have a Sesame triplestore configured to allow adding statements but not deleting them (see 3. http://rdf4j.org/sesame/2.7/apidocs/org/openrdf/sail/helpers/SailConnectionWrapper.html). I don't know if this would work, or if the system would be usable in this state or not.
