FCREPO-777 REST API: Determine and set appropriate mime-type when a new managed datastream is added without a specified media or mime type

Description

If a datastream is created with the REST API and no media or mime type specified, Fedora sets the dsMIME type as "application/x-www-form-urlencoded" for datastreams of type M, R, and E.

This MIME type is incorrect for most datastreams. For datastreams of type E and R, it doesn't matter so much (the content is delivered correctly); but when you request a M datastream with this type, a header line "content-disposition: inline; filename="[something].bin" is sent, and you are asked if you want to save a file with the content, since the browser cannot determine the MIME type and handle it appropriately.

How should the MIME type be determined, if it is not specified?

Stephen Bayliss, 2010-08-20 00:21 UTC

I would suggest

  • if the media type is specifed, use that, otherwise:
  • for X, E and R I believe the correct headers will be set in any case
  • for M, if none is specified:
    • if getting from an external http source, use the headers, if none specified in the http headers then use the default below
  • for POST/PUT use the headers sent with the request (or the default if none present)
  • for uploaded files use the default (or, could we in fact capture the media type when they are uploaded?)

I would suggest application/octet-stream as the default, as that's all we can really say about the stream. This will still potentially cause browsers to prompt to download, but in the absence of any other information there's not a more sensible option I think.

Scott Prater, 2010-08-20 01:35 UTC

Looking into it a bit more, I see that if you create a new managed datastream with no MIME type set, using the following command:

curl -i -H -XPOST "http://localhost:9091/fedora/objects/uwdc:AddDatastreamNoMediaMime/datastreams/TEST_M?versionable=true&controlGroup=M&dsLabel=ManagedDatastreamNoMediaMime&dsLocation=http://www.cooltattoofinder.com/wp-content/uploads/2008/01/cartoon-unicorn-tattoo.jpg" --data "" -u fedoraAdmin:xxxxx

... curl sets a "Content-type: application/x-www-form-urlencoded" header and sends it to Fedora, and that becomes the datastream's mime type.

However, if you REALLY do not specify a mime type, neither in the header nor as a parameter, like this:

curl -i -XPOST "http://localhost:9091/fedora/objects/uwdc:AddDatastreamNoMediaMime/datastreams/TEST_M?versionable=true&controlGroup=M&dsLabel=ManagedDatastreamNoMediaMime&dsLocation=http://www.cooltattoofinder.com/wp-content/uploads/2008/01/cartoon-unicorn-tattoo.jpg" -u fedoraAdmin:xxxxx

... then NO dsMIME type at all is set on the datastream, and managed datastreams are served by default with a "Content-type: application/octet-stream" header: perhaps set by the web server?

See fcrepo-777-test-output.txt for details.

To follow up on Steve's suggestion, maybe this algorithm can be used to set dsMime type:

  • If the mime type is specified by the mimeType parameter, use that;
  • or if the mime type is specified by the PUT/POST request Content-type header, use that;
  • or if the request is a POST, and the dsLocation is specified, use a HEAD request to get the Content-type from the source location (will this work on file URIs?), and use that;
  • or if the request is a PUT, the mime type remains unchanged;
  • or else set the mime type to "application/octet-stream".

Stephen Bayliss, 2010-08-20 05:02 UTC

And to add to this is character encoding. There's no explicit datastream property for this, but from a preservation perspective this is important ("text" content, XML content where there's no header specifying this). It can be done by including it in the MIMEType property, and this gets delivered in the http headers when getting the content.
