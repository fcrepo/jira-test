FCREPO-645 Treat DSLocation as an opaque value whenever possible

Affects versionsFedora 3.x trunk

Description

Currently, the value of DSLocation for managed datastreams is assumed to follow a particular scheme in serializers and deserializers, and elsewhere. These assumptions should be removed, and DSLocation should be simply passed on as an opaque value wherever possible. For example, several deserializers generate DSLocation values for managed datastreams as "PID + DSID + DSVersionID" (an assumption) rather than re-using the serialized value (treating it as opaque).

Whatever solution is used here should avoid validating DSLocations in multiple places as is done today (in DefaultDOManager and ValidationUtility)

Chris Wilper, 2010-12-07 03:11 UTC

There have been some recent discussions on the mailing list about this, and it's come up as an issue in the DuraCloud pilots in the context of being able to restore a single datastream if the local copy goes away for some reason. The key is storing the actual location of the content inside the FOXML, rather than the "token". This makes it possible for Fedora to report on the real location of the content. And if Fedora were able to do that without requiring knowledge of how the low-level storage paths are "allocated", it'd be possible to develop tools that, for example, restore parts of the repository from backups (DuraCloud or otherwise).

I'm adding my vote since I know this is a pain point for some...Aaron, do you think it's reasonable to scope this for 3.5 (even if we don't have someone identified to work on it yet)? It seems to fall into the category of preparing for future high level storage work.

Stephen Bayliss, 2010-12-07 21:06 UTC

+1 for storing the actual location. This is useful from a preservation perspective in that it means the filesystem of FOXML and datastreams can be interpreted without software. I guess we should leave people free to implement their own low-level storage where the location isn't necessarily a filesystem file, with the health warning that the FOXML might end up being uninterpretable without recourse to software decoding of the location.
