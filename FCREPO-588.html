Comments (6)

Aaron Birkland, 2009-11-25 20:39 UTC

After a round of configB testing, the repository is clear of all test objects, yet the following triples remain in the RI:
<info:fedora/demo:TEST_PURGE> <info:fedora/fedora-system:def/model#label> "" .
<info:fedora/test:1> <info:fedora/fedora-system:def/model#label> "" .
<info:fedora/test:2> <info:fedora/fedora-system:def/model#label> "" .
<info:fedora/changeme:6> <info:fedora/fedora-system:def/model#label> "" .
<info:fedora/changeme:3> <info:fedora/fedora-system:def/model#label> "" .

This occurs both for Mulgara and MPTStore. Ingesting and purging a new object with no label also results in orphan triples.

This issue has existed since at least 3.2.1, perhaps earlier

Stephen Bayliss, 2009-11-25 23:48 UTC

Did a quick check to see if this is an issue with empty literals (""). Tested in RELS-EXT, that doesn't seem to be the case. (I can add/delete/modify triples in RELS-EXT with empty literals with no "orphans" being left in RI)

Triples are added and deleted from RI by computing differences between before and after states here: fedora.server.resourceIndexResourceIndexImpl.updateTripleDiffs

This uses the following to add the before and after triples, then computes the difference and then issues add/delete to RI: fedora.server.resourceIndexTripleGeneratorBase.add (two method signatures)

They both have (lines 55 and 65)
if (lexicalValue != null)

{ set.add(new SimpleTriple(subject, predicate, new SimpleLiteral(lexicalValue, lang))); }

Suspect the triple is being added with an empty string, and being deleted with a null as the object; hence no deletion.

The trap for a null lexicalValue seems wrong; suggest that is removed, and any npe should bubble up to reveal who/what is trying to add/delete triples with a null literal as the object. That should be sorted at source rather than the code above which appears to try and work around null literal objects.

Aaron Birkland, 2009-11-26 00:05 UTC

My gut feeling is to look at the DOTranslator impl, and see what happens to the label as an object is serialized/deserialized. Stephen Bayliss, 2009-11-26 01:02 UTC

Suspect you're right... however the catch for null literals there still feels wrong and that catch should live elsewhere (I'm away tomorrow and all of next week, otherwise I'd be also happy to take this on)

Stephen Bayliss, 2009-11-27 12:26 UTC

Your hunch is right, inconsistent treatment of null vs empty string for properties on serialize/deserialize.

Seems to apply to FOXML and METS:

Deserialize - treat missing properties as empty string values (rather than null)
Serialize - don't write out properties where the string is empty.

So we have
Missing (null) -> empty string -> Missing, which is ok
empty string -> empty string -> Missing, which is not

Should make these consistent; best solution long term would be to treat missing attributes as null (rather than empty strings) when deserializing and write out attributes unless they are null (ie do write out empty string values); however this is likely to result in npe in other code, which may take a while to sort out.

So the short term fix could be to write out empty string attributes when serializing - this should solve the RI issue, but it still means that deserialize->serialize->deserialize is inconsistent.

Aaron Birkland, 2009-12-01 04:59 UTC

Implemented minimal fixes - mainly on the deserializer side. Basically, the serializers and deserializers should now have the same (if unintuitive) behaviour when presented with null balues or empty strings. Created a new issue FCREPO-589 Closed for revisiting this issue in the future, should we wish to make the serialization behaviour more intuitive.
