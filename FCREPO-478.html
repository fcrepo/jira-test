Description

Issuing a SPARQL query for a CONSTRUCT results in an empty response from the tuple query type service and a Exception is thrown when attempting to use the triples query service:

(Via Tuples
e.g. http://databank.ouls.ox.ac.uk:8080/fedora/risearch?lang=sparql&format=sparql&type=tuples&query=construct%20

{%20?x%20dc:title%20?name%20}

%20WHERE%20

{%20?x%20dc:title%20?name%20}

SPARQL query:

CONSTRUCT

{ ?x dc:title ?title }

WHERE

{ ?x dc:title ?title }

[' make a graph of all triples with dc:title as a predicate.']

Response:
<?xml version="1.0" encoding="UTF-8"?>
<sparql xmlns="http://www.w3.org/2001/sw/DataAccess/rf1/result">
<head>
<variable name="subject"/>
<variable name="predicate"/>
<variable name="object"/>
</head>
<results>
</results>
</sparql>

(regardless to how many dc:title triples are there: e.g. an spo query to pull up 10 dc:title matches - http://databank.ouls.ox.ac.uk:8080/fedora/risearch?lang=spo&format=RDF/XML&type=triples&limit=10&query=*%20%3Cdc:title%3E%20* )

(Via Triples
http://databank.ouls.ox.ac.uk:8080/fedora/risearch?lang=sparql&format=sparql&type=triples&query=construct%20

{%20?x%20dc:title%20?name%20}

%20WHERE%20

{%20?x%20dc:title%20?name%20}

Benjamin Armintor, 2009-10-22 15:44 UTC

The exception message from Trippi is misleading, from what I can see in the 1.4.1 source. MulgaraSession#findTriples(String lang, String queryText) is unimplemented; SPO queries are the only ones that apear to be processed at all. This is also indicated in the single value of MulgaraSessionFactory/TRIPLE_LANGUAGES: "spo".

The triple query aspect of the report is a Trippi issue, though finding a way for the risearch stylesheet to suppress non-SPO triple query options would be good in the meantime.

Overall looks good. Thanks for taking this on. Couple points:

Benjamin Armintor, 2009-11-11 01:09 UTC

FCREPO-478 Closed branch rev 120 consolidates the base model substitutions into doAliasReplacements, removes the irrelevant count overrides, and adds a little test coverage. On my development machine, Mulgara choked on IRIs like <#ri-test>: It tried to append them to default URIs, got a result string that had two hashes, and threw an exception trying to make a URI from it. When I tried removing the hash, mulgara attempted to load a Jena class to parse the resulting RDF. I decided the easiest way was to preserver the general logic of the existing substitution, with a slightly more flexible pattern match.
