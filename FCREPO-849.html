Description

Reported by Janna Wemekamp, see http://permalink.gmane.org/gmane.comp.cms.fedora-commons.user/6275

Updating a DC datastream stored as Managed Content fails if the datastream is not versionable.

This is due to a RI update error.

The triple update compares the "before" and "after" states of an object. Currently it does this after managed content datastream changes have been persisted - so the "before" state is unavailable, and it therefore fails.

We could move the update to happen before the managed datastreams are saved, however if there is an error/exception later in the code, this means that the RI will be out of sync with the object contents.

(note that for a purge, this does in fact happen in this sequence - so we potentially already have the problem that if a purge fails then the RI is out of sync).

Moving the update to happen before the managed datastreams are updated is probably ok as a short-term solution, but ideally we need some kind of transactional behaviour - maybe we modify the RI update code so that it can (a) get a list of updates (adds and deletes) and then (b) later persist those updates.

Moving the RI update code to before the managed datastream-save code does seem to resolve this issue (I have a test case and a fix, using this).

Stephen Bayliss, 2011-01-18 17:47 UTC

Summary of options:

1) Move RI update code to before object changes are committed so that before-state is available
nb if committal of object changes results in an error, RI is out of sync with objects

  • but might be ok as an interim fix?
    2) Cache "old" state of object - cache all object data necesary for RI update, do RI update right at the end based on this cached info and the new object
    nb note we need to ensure all data that drive the RI are cached, this includes object properties in the FOXML, object->datastream relationships, datastream content for DC, RELS-EXT, RELS-INT
    3) Modify RI update code so that:
  • instead of modifyObject(...) we have getObjectModifications(...), return two lists of triples, a set of adds and a set of deletes (this is what modifyObject does under the hood). Do this first thing, before any modifications to object are saved (ie whilst old object is still available)
  • commit these changes later, noting that RI module already exposes methods for add and delete, that could make use of the two sets of triples from above
    4) Modify RI update code
  • implementing proper transactioning semantics, ie RI module has ability to cache a set of changes for later application by a commit (note this is still not truly transactioned in terms of eg Mulgara transactions; but then we don't have proper transactioning currently anyway; this might be appropriate to revisit after High Level Storage?)
Stephen Bayliss, 2011-01-19 14:59 UTC

Discussed at committer meeting 2011/01/18 - it was decided that this would not be included in the 3.4.2 release (due very shortly) due to time constraints on implementing a proper solution that would allow backing-out of RI changes if commiting the datastreams/foxml generates an error (a situation that could arise by moving the RI index update to before the object/datastream update).

In the meantime, warnings added to documentation in the wiki.

Jonathan Green, 2013-03-12 22:06 UTC

A note for anyone coming across this ticket that might happen to have a large number of objects that are broken because of this problem. A somewhat quick workaround for this without re-ingesting all the objects is to turn off the triple-store, set version-able to true on your objects, turn back on the triple-store.
