Environment

Fedora Core 10. Fedora Commons 3.2. Tomcat included / external (latest) / Jetty (latest) / JBoss 4.2.3, database : Mysql (5.077) / Derby(included in 3.2) / McKoi (included in 3.1). Resource index turned on (Mulgara). Apart from that out-of-box configuration.

Description

While using Fedora Administrator and after performing lots of operations on objects (i.e. viewing, updating, purging...) the client hangs up and the progress bar shows "Find Objects...".

After calling netstat on the server, the list shows 100 sockets in CLOSE_WAIT state. [100 - default value of 'maxActive' instances in the connection pool]
...lines...
89 tcp 1 0 ::ffff:127.0.0.1:43562 ::ffff:127.0.0.1:3306 CLOSE_WAIT
...lines...
Mysql server (in this case) shows no open connections, so the problem occurs on the application side as the number of maximum active connections have been reached .

The same thing happens while using external Tomcat, Jetty and JBoss instead of included tomcat. Furthermore, the connections become hanged regardless of the database (tested MySql, McKoi from fedora3.1 distribution and Derby from 3.2).

The problem came out during a writing of a java connection client to the repository with the usage of FedoraAPIA and FedoraAPIM from the FedoraClient class.

Increasing the maximum number of active instances in pool (for instance up to 3000) will not solve this problem, as a scenario causing this bug to come up can be easily found (e.g. lots parallel client calls).

IssueT, 2009-11-05 18:05 UTC

It's easier to provoke this bug if you turn down the max connections in the dbcp props in fedora.fcfg to 5 or so.

It looks like an object create action in the Swing admin app finishes off by doing a field search query to populate the object metadata for the object edit pane. If you turn up the logging to debug and grep on "ConnectionPool", you can see that a connection gets passed out to FieldSearchResultSQLImpl to run this query "SELECT doFields.pid FROM doField" and then another connection gets passed out immediately after. Most connections are returned to the pool immediately, but this one is not. Even if you do a field search through the Web GUI, you can see that the ConnectionPool hands out a connection and then it gets returned immediately.Much later, you can see the connection being returned to the pool, presumably when that FieldSearchResultSQLImpl instance is expired.

It seems like FieldSearchResultSQLImpl is designed to hold onto a connection in an object field so the result set can remain open to satisfy subsequent resumption token calls, which leaves the pool open to connection starvation if the caller doesn't maintain FieldSearchResultSQLImpl lifecycle properly.

I assume this doesn't happen in the new admin client because it's using a REST operation to get the object metadata rather than a field search.

I'd spend more time figuring out what about the Swing client's usage of that api does to not clean up that FieldSearchResultSQLImpl instance, but I presently have to get back to work. If nobody else pokes at this, I can devote more time to it tonight. At this minute, I can't really explain those CLOSE_WAIT sockets, because that actually looks like a connection getting closed, not pooled.

In the meantime, it seems like a quick workaround would either be using the Flash admin client, or changing whenExhaustedAction to 2 for the db pool. I haven't tested this assumption, however.

Chris Wilper, 2009-11-17 16:40 UTC

Thanks for looking into this in detail, Michael. It appears to be a resurfacing of FCREPO-172 Closed .

Ultimately, the server should be returning the connection to the pool as soon as the resultset is exhausted. In this case, it's performing a query that we know has one result. So it appears that the bug is with the logic of FieldSearch*SQLImpl ... I had written an integration test for FCREPO-172 Closed , so my next step is to figure out why that's not provoking this issue.

Chris Wilper, 2009-11-18 12:59 UTC

Ok, I've dug further and can now reproduce this in an integration test.

It only occurs when the client requests a single result per page from the server when running a query (this is what Util.java happens to do after a new object is created in the swing admin gui). In those cases, even when there is only one result, the server keeps the session (and thus db connection) open, waiting for another (empty) "page" of results to be returned.

The reason it wasn't showing up in the previous test written for FCREPO-172 Closed was because that test always performed queries with maxResultsPerPage=10.

Chris Wilper, 2009-11-18 14:23 UTC

More thoughts:

The issue can be generalized beyond the "1 result requested per page, 1 actual result" case. The unnecessary, empty page of results occurs any time the number of actual results is a multiple of the client-specified maxResultPerPage. In other words, when the last actual result falls on the last possible position on a page.

When the client doesn't "know" how many responses to expect, this normally doesn't cause a connection pool exhaustion problem because it would just keep requesting the next page of results 'till the list is exhausted.

Without resorting to changing the FieldSearch API itself, the proper way to solve this is to have Fedora "look ahead" into the result set and see if it's really necessary to keep the session open. This is exactly the kind of thing that java.sql.ResultSet#last() was designed for. Ideally, this can be used, but it requires the underlying JDBC driver to have scrollable result set (TYPE_SCROLL_INSENSITIVE) support. Since we're aiming to support a wide variety of databases, I think it would be better to have Fedora not require this and just do the "peeking ahead" itself, on a normal (FORWARD_ONLY) resultset.

Chris Wilper, 2009-11-18 23:22 UTC

Fixed in trunk. Employed the "peeking ahead" solution that can use a regular (non-scrollable) resultset, and added a test for this case.
