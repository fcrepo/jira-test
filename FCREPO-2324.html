FCREPO-2324 WebAC module does not follow all containment relations

Description

Presently fcrepo-module-auth-webac follows ldp:contains relations in basic containers (via jcr node containment), but not other containment arrangements. It was suggested that the WebAC specification indicates that the model should work with other containment relations, such as pcdm:hasMember via ldp:IndirectContainers.

The following test is run against the fcrepo4-vagrant vm with authentication set to true (fcrepo version 4.7.0), and shows that a policy assigned to container does not inherit to its child via indirect containment:

https://github.com/bbpennel/fcrepo-webac-test

There are some questions about the practicality of addressing this issue, particularly in multiple containment situations.

As a point of clarification, LDP (and Fedora) have a very specific definition of "containment" which is limited to a parent container / child resource relationship. Any given child resource can have only one parent container, therefore resources can have one and only one containment relation.

This ticket should be reworded in the context of an updated title along the lines of: "WebAC module does not inherit policies from arbitrarily related resources".

Unknown, 2016-12-07 14:18 UTC

I would note that the WebAC spec (as defined by the SOLID project) defines how WebAC inheritance should work: https://github.com/solid/web-access-control-spec#acl-inheritance-algorithm. The Fedora API specification explicitly refers to this algorithm, and this is, basically, how the existing WebAC implementation works.

That spec states that the algorithm should look in a resource's "parent" container. The spec does not define "parent" (i.e. parent via basic LDP containment vs. direct/indirect containment), so there is a possibility that one could define parent in different ways. However – and I want to be very clear here – if there are multiple parent ACL definitions (which will absolutely happen if you use anything that's not based on basic containment), it is entirely undefined how those different ACL interact.

The other thing to keep in mind is: say you're using pcdm:hasMember via indirect LDP containment – what happens if I set a simple property on the resource that is </some/private/resource> pcdm:memberOf </some/public/resource> OR </some/public/resource> pcdm:hasMember </some/private/resource> (that is – not using LDP membership triples). If multiple ACLs are interpreted by means of set UNION, it becomes really easy to hijack any existing ACL permission structure. If, however, you use set INTERSECTION, you are, arguably, going against some basic principles of RDF.

So, while I don't want to dissuade you from exploring alternate definitions of "parent" in the context of WebAC, I do want to encourage you to exercise great caution.
