Former user, 2009-11-23 10:38 UTC

Yes, still relevant. Here are some more details:
I see two problems in the WADL:
1) duplicate slashes in request path, like: /fedora/objects//objects?resultFormat. This comes from the prepended / in the @Path("/

{pid}

") annotation in the respective REST servlet that's appended to the entry point as defined in the servlet mapping.
2) resource base and resource paths don't yield valid paths. For example:

<resources base="http://localhost:8080/fedora/objects/">
<resource path="/objects">
<method name="GET" id="searchObjects">
...
will add up to http://localhost:8080/fedora/objects//objects/searchObjects

Maybe this is perfectly valid WADL, but I wasn't able to create a functional REST client out of it without some tinkering.

The tools used were SoapUI 3.0.1 and a hand written Groovy parser.

Jasper Op de Coul, 2010-05-06 09:16 UTC

Yes, as Kai pointed out there were still issues.
I ignored the resource base path, and then added '/objects' to the url if it was not already there.

It would make more sense if the reources base path were set to '/fedora', then there could be one resource called 'objects' below that containing the searchObjects and nextPID methods, and then all other resources would be below this '/objects' resource. This would probably also solve the 'double slashes' problem.

Besides that, the RISearch method is missing and the searchObjects method is missing the fieldname params. In the WADL file it only has 'terms', 'query', 'maxResults' and 'sessionToken' as params, but you need to pass some of the fieldnames to actually get results back:

?terms=test&pid=true&label=true

I never worked with WADL before, but It was very easy and fun to implement. It's also nice that you end up with a complete implementation of the API, instead of just implementing the methods you need.
So, I hope support for WADL is continued. If it helpes, I can create a correct WADL file and attach it to this issue, but I suppose the file is auto-generated.

Former user, 2010-05-06 12:55 UTC

Jasper, thanks for your comment.

The problem with the base path is tied to how the REST api is implemented. Thus, it may be difficult to fix the WADL auto-generation without changing the structure of the API and may therefore break backward compatibility.
The RISearch method is not included in the WADL because it doesn't technically belong to the REST api. It lives on its own and may or may not exist because it could have been decativated during installation.

As it stands now I'd opt for turning off the auto-generated version and include a static WADL file. This could also help to include the optional resource index in the WADL during installation. I think we should discuss this at a committer call.

That being said, specifically with regards to the search interface, OpenSearch might be worth looking into as a complement / substitute to WADL (http://www.opensearch.org, http://bitworking.org/news/193/Do-we-need-WADL).
