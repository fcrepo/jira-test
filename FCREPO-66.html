Description

Add support for AttributeSelectors to the ResourceAttributeFinderModule.

This will allow the use of AttributeSelector elements (contrast AttributeDesignators)in policies which can 'select', using an Xpath query, attributes of the resource the policy pertains to. This affords the ability to write policies based on elements contained in XML datastreams - such as DC, RDF, and many more.

The significance of this feature is that policies will be able to refer to a far greater range of resource attributes such as true object metadata (rather than the system level metadata available now), and relationships to other objects e.g. composition, aggregation.

The XACML 2.0 core spec insists that the RequestContextPath attribute of AttributeSelector elements should be an xpath expression whose context node is the <xacml-context:Request> element, which seems to read that AttributeSelectors should be evaluated against the request context. Things get hazier after comparison with the Sun implementation where there does not seem to be anything directly corresponding with the XACML context handler as illustrated in the XACML data-flow model - although the EvaluationContext seems pretty close.

What this boils down to is my confusion over whether it is valid (according to the XACML spec) to interpret RequestContextPaths for AttributeSelectors as a compound string comprising "Datastream ID""Absolute XPath expression over Datastream" such as, "DC""/oai_dc:dc/dc:publisher" which would be written in XACML as:
<AttributeSelector RequestContextPath="DC/oai_dc:dc/dc:publisher" DataType="http://www.w3.org/2001/XMLSchema#string"/>
and evaluate to a string bag of matching values. I suspect that it is technically not allowable, however I can see no reasonable alternative that does not render the AttributeSelector redundant (such as an AttributeDesignator that performs the same operation). Perhaps this is an unaddressed usage scenario with regard to the spec.

The advantage to including the datastream ID in the path is that it allows a narrowing down of the data required to fulfill the query and hence saves time in retrieval. After receiving no response from the sunxacml mailing lists on the topic I have gone ahead and implemented as described above. The resulting code is now in the custody of Chris and Bill who will hopefully do the commit for inclusion in the 2.3 release.

This feature was never merged in, and Fedora's code has changed significantly since. There is also an effort underway to re-work Fedora's XACML implmentation based on the work done in the Muradora project. See FCREPO-451 Closed for more on that. I'm closing this feature request for now in order to reduce confusion. If anyone still wants AttributeSelectors against the new XACML impl, please check whether it was done by FCREPO-451or submit as a new feature request.
