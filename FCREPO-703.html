Description

With API-A authorisation disabled and XACML enabled, REST API calls to getDatastreamDissemination fails (401). This is because the REST API also calls GetRelationships and GetDatastreamProfile as part of determining a filename to include in the content-disposition header, and these underlying calls are API-M.

This happens even without requesting a download of the file, as by default content-disposition headers are set for the case that the user wishes to do a "save-as" from their browser.

Work around is to change the parameter (fedora.fcfg) datastreamContentDispositionInlineEnabled to false - this disables setting of the content-disposition header.

This should have been caught by the Config A tests - but currently we do not test the REST API in Config A.

eddie, 2010-05-24 22:11 UTC

For history: the original mailing list thread on the subject: http://thread.gmane.org/gmane.comp.cms.fedora-commons.devel/1659

Regarding adding getDatastreamFilename to API-A: as workaround, I get it, but getDatastreamFilename seems like a peculiar method to add to the API.

Also, AFAIK, authorization is not performed twice. The REST API calls delegate to the SOAP apia or apim services, and only then, from Access or Management are the authorization hooks called.

If anything, what's odd/inconsistent is that we class getRelationships as an API-M method and therefore, out of the box, it requires authentication, when getDatastreamDissemination is an API-A method and therefore, by default, it does not require authentication. So, getDatastreamDissemination calls on RELS-EXT and RELS-INT provide access to the same information that getRelationships would provide. Or close enough, I don't remember off the top of my head all the information we assemble in response to a getRelationships call (but in any case, I'm 99% sure all that info is available by API-A calls for datastreams and object properties).

That said, someone might want to restrict access to RELS-EXT or RELS-INT via policies and it would probably be contrary to expectations that adding such policies would have the side effect of breaking getDatastreamDissemination generally. I think we're generally violating the principle of behaving as the user intends if policies (default or otherwise) break an API method because of implementation details.

For an immediate workaround, rather than disable content-disposition entirely, I believe if we default to filename resolution by dsLabel, we sidestep the problem as well.

Stephen Bayliss, 2010-05-25 08:53 UTC

I'd agree that it seems a peculiar method to add to the API - it feels too granular/specific - maybe adding it as a "derived" property to getDatastream would make more sense.

However getDatastream is API-M. So we run into the API-A/API-M inconsistency (it seems odd that getObjectProfile, listDatastreams, listMethods are all API-A yet getDatastream (profile) is API-M, there doesn't seem to be anything returned by getDatastream that one would want to protect to a greater degree than these other methods).

Regarding authn/authz, what seemed odd is that with XACML disabled and API-A set to no auth, then getDatastreamDissemination does not require authentication, even though the underlying methods should. However I can see that XACML authz takes place only in Management and Access.

Defaulting filename resolution to dsLabel I think won't work as-is - because getDatastream is API-M.

However listDatastreams could be used instead of getDatastream to get the label - that is API-A. Similarly getDatastreamDissemination (API-A) could be used directly to get the relationships as noted above - with the potential side effects noted by Eddie of not behaving as the user intends if policies restrict acccess to RELS-INT.

Defaulting it to the datastream ID should work, as would defaulting it to a fixed text string.

Also setting the appropriate XACML policies for the underlying calls would work (though potentially with side-effects elsewhere).

My feel for an "appropriate" fix at this stage is:

  • modify the code to use API-A methods to get the necessary information
  • document the getDatastream REST API method noting the interaction with the other API-A methods and stating what access needs to be specified in XACML; and also note this in comments in fedora.fcfg
  • raise a JIRA issue to cover the dependency on policies applied these other API-A methods, and tackle in more detail when we come to look at refactoring API-A/API-M as part of FCREPO-521 Closed , linking to this issue
Stephen Bayliss, 2010-05-25 21:16 UTC

Discussed at Committer meeting 25 May 2010 - acceptable solution for now is to replace API-M calls with API-A calls and document dependencies on policies. Also update Fedora 3.3 documentation to indicate dependency on policies for API-M calls and how to disable behaviour in fedora.fcfg.
