Benjamin Armintor, 2010-01-29 19:21 UTC

Focusing on the repository model:
Nodes and nodeType:
There is a strong affinity of JCR nodeType to Fedora Content Model, although the former requires an inheritance structure that is not currently supported in the CMA (although Asger's ECM-related work touches on it; see the thread at:
https://fedora-commons.org/confluence/spaces/viewthread.action?key=DEV&id=13140053
). Digital Objects and Datastreams both probably model as nodes. The notion of primary typing of a JCR node doesn't immediately translate to the Fedora CMA.

UUID's could be built in as an auxiliary to, or replacement for, PIDs, particularly if pid generation were modularized.

Properties:
JCR nodeProperties correspond to a number of entities in Fedora: Datastreams, RELS-EXT triples, and system properties to name a few. The parent-child organizational properties might be modelled as RELS-EXT/INT relationships (again, ECM has something to say to this), but there's no explicit action on such properties in Fedora.

Workspaces:
Because the relationships in Fedora all exist in the same graph, I don't immediately see a way to have a Fedora repository act as multiple workspaces without a very awkward translation of organizational relationships to DO's in their own right, or a change to the way that DO's are serialized.

Benjamin Armintor, 2010-02-02 16:50 UTC

After some more thought, most of what would go into a level 1 compliant implementation would probably fit best into a Fedora-Create project of objects and Pluggable modules:

1. A package of default content models (for node and resource types) and system objects (root node)
2. A DOManager/Reader implementation that would assign UUIDs and inject a default location for node objects that don't specify a parent node
3. A FieldSearch module to index the parent-child relationships and node types
4. A BasicServer extension or a new module that implements the javax.jcr.Repository interface and listens on an RMI interface, including a way to authenticate clients in a manageable way (ideally through the user filter? or maybe as back-end security?)

The one immediately obvious departure is that the JSR specifies node type inheritance, which doesn't exist yet in the Fedora CMA ( see https://fedora-commons.org/confluence/spaces/viewthread.action?key=DEV&id=13140061 for thoughts, including implementation efforts under the ECM project). This would also bring to the fore the question of service deployment resolution for Fedora objects.

As an aside, the JSR 170 DOM-like model of nodes and properties is structurally similar to the aggregator/resource model of NCore ( http://ncore.nsdl.org/index.php?menu=services&submenu=services!EduPak ) and not unlike the RODA data model ( http://www.fedora-commons.org/about/examples/roda )
