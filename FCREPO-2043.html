Description

The maven dependency definitions should be cleaned up. Certain dependencies are not stated, and certain others are superfluous.

Comments (6)

A. Soroka, 2016-06-01 13:27 UTC

How does anything build if "Certain dependencies are not stated"? Are you saying that some transitive dependencies should be made explicit? That can be problematic…

Unknown, 2016-06-01 13:30 UTC

I'm saying that if the code uses some library (e.g. import static org.apache.http.HttpStatus.SC_BAD_REQUEST; ) it should explicitly declare that in the POM rather than relying on transitive dependencies to bring in that library. Do you disagree?

A. Soroka, 2016-06-01 13:37 UTC

I'm saying it's not open and shut. Making those dependencies explicit puts extra burden on the devs to maintain version correctness, etc. Only those dependencies which can function by themselves should be made explicit. That is to say, if X is a dependency, and Y is a transitive dependency via X, then we should make Y explicit IFF we could take away X and still use Y. Otherwise, even if we use Y directly, we should leave it transitive/implicit.

Unknown, 2016-06-01 13:47 UTC

OK, we should discuss this on the tech call. As it currently stands, the version definitions are a complete mess. Dependencies are declared in modules that don't use them: i.e. certain dropwizard-based metrics libraries are marked as dependencies in fcrepo-metrics even though they aren't used there at all, but they are used in the http layers – for example: metrics-jersey2; velocity dependencies are declared in http-commons but used in http-api; activemq-based stuff is declared in fcrepo-jms, even though it's only used in fcrepo-webapp; most modules don't declare a dependency on javax.jcr even though the code fundamentally depends on it being there – it's brought in via fcrepo-kernel-api; the transaction implementation is made explicit in fcrepo-kernel-modeshape, but it really should be optional and re-declared in fcrepo-webapp, etc, etc.

In terms of dependency versions – that's already managed through the parent pom and its <dependencyManagement> block.

My point is this: if we ever hope to have an alternate impl run in OSGi (forget about modeshape ever doing this), we need to be explicit about dependencies.

A. Soroka, 2016-06-01 13:53 UTC

I'm not giving any opinion against getting rid of unused dependencies. That's clearly a good move, and I'd like to see us start with a PR that does that and nothing but. I'm also not against separating API and impl where that is possible (e.g. javax.jcr and MODE, or JMS and ActiveMQ). I'm suggesting that repeating transitive dependencies as direct dependencies not only won't help us clean up, it will make things much worse as the exclusions blocks of large frameworks grow and and grow and grow and grow.

As for OSGi, while you know I'm broadly in favor, I'm less and less convinced that it's feasible to get there from here. IOW, I think we may want to talk about a fresh design, leaving the entire MODE impl as a monolith until it is simply replaced by a lighter-weight ref impl.

Unknown, 2016-10-12 19:31 UTC

This is not necessary at the moment and will probably be folded into a larger effort separating the api and the implementation.
