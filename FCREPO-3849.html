Proposal:

Configure 1 Github workflow for https://github.com/fcrepo-exts/fcrepo-docker:

  1. Define list of supported fcrepo releases
  2. For each release: build docker image and run smoke test (on main and PRs)
  3. If branch is main and smoke tests passed → push image docker
  4. Run workflow on main branch every week to profit from changes in upstream Docker image

Open questions:

  • List of supported fcrepo releases?
  • When/how to build/push SNAPSHOT images?
  • Who should be informed, when a scheduled run fails?

Thomas Bernhart, 2022-11-22 09:56 UTC

Summary of the discussion in the Fedora community:

To summarize the decisions made based on the following questions:

Questions

1. What range of Fcrepo images should we rebuild?
→ Will build a docker image for the latest release, then supply tags for tag major, minor, and patch releases

2. Range of images to build:
--> As of now:

  • fcrepo/fcrepo:6-tomcat9
  • fcrepo/fcrepo:6.2-tomcat9
  • fcrepo/fcrepo:6.2.0-tomcat9
    --> When 6.3.0 is released:
  • fcrepo/fcrepo:6-tomcat9
  • fcrepo/fcrepo:6.3-tomcat9
  • fcrepo/fcrepo:6.3.0-tomcat9

3. When/how should we update the -SNAPSHOT images be built? Is daily enough?
--> When commits are merged into the main branch.

4. Who should be informed, when a scheduled run fails?
--> Incoming Tech developer will be notified going forward

5. Is it okay to replace an image if the base image has been changed?
--> Yes; rebuilds will happen on a schedule: weekly should be good enough.
