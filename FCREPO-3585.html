FCREPO-3585 Rollback with auto-versioning disabled can leave Fedora in an inconsistent state

Description

After this PR (https://github.com/fcrepo/fcrepo/pull/1835) it is still possible for a non-autoversioned to be left in an inconsistent state, but only in very specific circumstances. A resource will be left in an inconsistent state, meaning the state in the db does not match the state on disk, if the folllowing occurs:

1. The resource has a mutable head (prior to the start of the transaction)
2. The resource was updated in a long-running transaction along with other resources
3. The db changes for all of the resources were successfully committed
4. The ocfl changes for the resources were successfully committed to the mutable head
5. After committing the ocfl changes, another resource failed to commit its changes, causing the entire transaction to rollback

If that series of events occurs, the db changes will be rolled back but the ocfl changes will NOT be rolled back.

Currently, if this were to happen, users would have to reindex their entire repository.

Fedora could potentially attempt to reindex resources that could not be completely rolled back. However, this code does not currently exist, and would need to take into account updating membership and containment. This is essentially the same code that we'd need if we wanted to support allowing users to reindex individual resources on demand.

For the time being, this problem can be easily avoided by users by:

1. Keeping resources in a mutable state for as short of period of time as possible
2. Not updating resources with mutable heads in long-running transactions
3. Creating an immutable version (memento) immediately before updating the resource in a long running transaction
