Environment

Installing with an install.properties file from a prior release

Description

If Fedora is installed with an install.properties file from a prior release (which does not have a property for the LLStore implementaiton), Akubra will be used by default.

Potentially this could affect users upgrading to this release from 3.3 or before, who may wish to use their existing install.properties during installation. In this case they almost certainly wouldn't want to be using Akubra, so using the default is dangerous.

We need to show a warning during installation if the property is not present in install.properties.

Chris Wilper, 2010-08-18 00:41 UTC

I think showing a warning is fine, but I wonder how common this will actually be. The upgrade instructions haven't ever suggested that one should try to use a prior version's install.properties when upgrading to a new release. But I recognize the risk that someone might try it. In this case, the downside would be mainly that they'd be confused when it came time to point LLStore at their old data, as part of the upgrade process.

To me, this issue raises the question of what to do in other, similar cases. For example, we introduce a new, required module that must be configured. Or we change what the default value is for an existing module. It seems like trying to manage this on an individual module basis, for each upgrade, could get pretty complicated.

Another, simpler idea is to a) explicitly recommend against using a different version's install.properties file, and b) give a big warning at install time if it's attempted. Implementing b) would require that when writing install.properties, we persist the version of Fedora that was installed. Then the installer can check this property against the actual version of Fedora in order to decide whether it needs to throw up the warning.

Stephen Bayliss, 2010-08-18 12:21 UTC

In practice people may have been using install.properties even though we haven't explicitly documented it. Personally I find it quite useful, especially for repeatability of configurations between different releases.

Agreed that in any case users should pick this up later on in the process when they come to edit fedora.fcfg and point at their old data since there'd be nowhere to specify that. Although that might be a bit of an annoyance.

My take on this would be:

  • no properties file: as it is currently
  • properties file: never use defaults - always warn if an expected property is not found.
  • version check would be good as a top-level check, gives an option of quitting at that stage rather than getting half-way through and then having to run it again.

I don't think changing default values between releases is particularly an issue, I think it is implicit that as part of upgrading release notes should be read and configuration should be upgraded should there be anything that someone wants to make use of in the new release. If there is a new module, it should result in the behaviour above - the user will be aware that there is something new that needs configuring.

It does actually raise the issue of what the default values "mean" - are they the preferred option, recommended option, most common option users want? I think this varies on a property-by-property basis.

This is something that has caught us out in testing - a combination of system test properties files not being updated, and a bug in the installer not picking up the default option resulted in FeSL AuthN not being used as the default prior to the RC1 release in our testing, this was discovered very late in the day and resulted in some last-minute fixes.
