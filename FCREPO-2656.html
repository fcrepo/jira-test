Andrew Woods Benjamin Armintor

I was hoping you could help clarify the expectations for this feature, and external binaries more generally.

If the expectation is that providing a header on POST/PUT:

"Content-Type: message/external-body; access-type=local-file; local-file=\"file:///path/to/file.txt\""

would produce a binary that responds with the same Content-Type header on GET, then it seems straightforward. 

Web browser requests to the binary will give an error page, but if retrieved by an informed client on the same file system it can work.  Is this how it is expected to behave, no proxying, as with URL access-types?  That is how the spec reads to me, but wanted to confirm.

The fixity behavior with external binaries seems a bit confusing.  If you submit a checksum when creating a binary it will fail because it is actually storing a 0 byte "file" in modeshape, and checksumming that.  Meanwhile, fcr:fixity always passes since it is checksumming the 0 byte file.  However, if you supply the Want-Digest header, it will stream the referenced file and compute a fresh checksum.

From a preservation perspective, I'm unsure about storing premis:hasSize=0, but I understand that we can't expect to track filesystem info.  I wonder if the property shouldn't be stored in that case?  Similarly, the ebucore:filename is empty, which seems like could be populated.  And perhaps we shouldn't store an empty binary?

 

Andrew Woods, 2017-11-28 22:44 UTC

There are two scenarios that the Modeshape impl should support: proxy and copy

1 - Proxy

PUT/POST creates a resource with "Content-Type: message/external-body; access-type=local-file; local-file=\"file://path/to/file.txt\"".
Subsequent GET returns the same "Content-Type" as provided.
The body of the response to GET is the actual content of "file.txt".
GET/HEAD response MUST recalculate the value of requested digest on requests with `Want-Digest` header.

2 - Copy

PUT/POST creates a resource with "Content-Type: message/external-body; access-type=local-file; local-file=\"file://path/to/file.txt\"; expiration=anything".
This behavior should ingest the file found at `/path/to/file.txt` in a similar fashion to the current functionality of:

curl -i -ufedoraAdmin:fedoraAdmin -XPUT localhost:8080/rest/sample-pdf -H"Content-Location: http://www.dillonrangerdistrict.com/trails/Buffalo_Mountain.pdf" -H"Content-Type: application/pdf"
