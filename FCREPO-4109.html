FCREPO-4109 Concurrent ingest deadlocks on PostgreSQL: containment index commit locks parent rows in nondeterministic order

TypeBug
StatusIn Progress
PriorityHigh
ReporterDavid Novák
AssigneeDan Field
Created2026-09-17 13:17 UTC

Affects versionsfcrepo 7.0.0

Description

Summary

When several transactions that add resources under the same parent containers are committed concurrently, Fedora fails with Failed to commit transaction caused by a PostgreSQL deadlock on the containment table.

The commit updates one containment row per changed parent, in a loop, driven by a query that has no ORDER BY. Two concurrent commits that touch the same set of parents can therefore acquire the same row locks in opposite order, which is a textbook deadlock.

A second, independent problem makes this visible to clients on 7.0.0: fcrepo does wrap the commit in a retry policy for deadlocks, but with Spring 6 on PostgreSQL that policy never matches the exception that is actually thrown, so nothing is retried and the error propagates out as a failed request. On 6.5.1 the same deadlock is still retried and stays invisible, so this half looks like a regression.

Both are one-line-ish fixes; we are running with them applied locally (see Suggested fix).

Environment

   
Fedora 7.0.0 (fcrepo/fcrepo:7.0.0-tomcat10)
Database PostgreSQL 12.3
Spring 6.2.16 (spring-jdbc-6.2.16.jar in the deployment)
Client multi-threaded bulk ingest, one Fedora transaction (Atomic-ID) per record

Both code paths below are unchanged on main as of d11e34c382 (2026-09-10), so this is not specific to the 7.0.0 tag.

Observed behaviour

Over a set of bulk ingest runs our Fedora log contains 700 occurrences of the following pair (same transaction id in both lines, so 700 events, not 1400):

WARN  (ContainmentIndexImpl) Unable to commit containment index transaction <tx>:
      PreparedStatementCallback; SQL [UPDATE containment SET updated = ? WHERE fedora_id = ?];
      ERROR: deadlock detected
  Detail: Process 151 waits for ShareLock on transaction 221057; blocked by process 236.
          Process 236 waits for ShareLock on transaction 221053; blocked by process 151.
  Where:  while updating tuple (1940,28) in relation "containment"

ERROR (TransactionImpl) Failed to commit transaction: <tx>

The Detail lines show a genuine two-process cycle, and the same heap tuple recurs across events, i.e. the contention is on a small number of hot parent rows.

Root cause 1 — parent rows are locked in nondeterministic order

ContainmentIndexImpl collects the parents to touch with (ContainmentIndexImpl.java#L467):

private static final String GET_UPDATED_RESOURCES = "SELECT DISTINCT " + PARENT_COLUMN + " FROM " +
        TRANSACTION_OPERATIONS_TABLE + " WHERE " + TRANSACTION_ID_COLUMN + " = :transactionId AND " +
        OPERATION_COLUMN + " in ('add', 'delete')";

and then updates them one at a time (ContainmentIndexImpl.java#L777):

for (final var parent : changedParents) {
    final var updated = jdbcTemplate.queryForObject(SELECT_LAST_UPDATED_IN_TX, ...);
    if (updated != null) {
        jdbcTemplate.update(UPDATE_LAST_UPDATED, Map.of("resourceId", parent, "updated", updated));
    }
}

SELECT DISTINCT without ORDER BY gives no ordering guarantee — PostgreSQL will typically satisfy it with a HashAggregate whose output order varies. Each commit therefore takes row locks on its parent rows in an arbitrary order, and two commits sharing two or more parents can deadlock.

This only shows up once a workload has two or more shared parents per transaction, which is exactly what a repository with a flat container plus membership/proxy containers produces. In our case every record adds a child to both:

containment.parent children
info:fedora/<server>/record 178 277 (every record)
info:fedora/<server>/model/<model>/member 14 … 37 667 (per model)

All other parents are per-record and never contended. So any two concurrent commits of the same model contend on exactly two rows — enough for a cycle. Two commits of different models share only one row and cannot deadlock, which matches what we see in practice.

Root cause 2 — the deadlock retry never fires on PostgreSQL (7.0.0 / Spring 6)

TransactionImpl commits the indexes inside a retrying executor (TransactionImpl.java#L350), and the policy is (DbTransactionExecutor.java#L36):

.handleIf(e -> {
    return e instanceof DeadlockLoserDataAccessException
            || (e.getCause() != null && e.getCause() instanceof DeadlockLoserDataAccessException);
})

On PostgreSQL the exception that actually arrives is org.springframework.dao.PessimisticLockingFailureException — the superclass of DeadlockLoserDataAccessException — so instanceof is false and the operation is not retried.

Evidence from 102 518 log lines covering the runs above:

class in the Caused by chain occurrences
org.springframework.dao.PessimisticLockingFailureException 700
org.springframework.dao.DeadlockLoserDataAccessException 0

This looks unintentional rather than deliberate: the retry infrastructure was added in #1909 / #1910 ( FCREPO-3720 Closed , May 2021) to address MySQL deadlocks, and the javadoc still says so — "Executes the runnable within a DB transaction that will retry entire block on MySQL deadlock exceptions" (DbTransactionExecutor.java#L60). PostgreSQL appears never to have been covered.

Why this is a regression from 6.5.1, and why it is nobody's fault in fcrepo

The predicate above is byte-for-byte identical in 6.5.1 and 7.0.0 — fcrepo did not change it. What changed is the Spring version underneath (5.3.39 → 6.2.16) and, with it, the default SQLExceptionTranslator chosen by JdbcAccessor.getExceptionTranslator():

// Spring 5.3.39 — a DataSource is always present in fcrepo, so this branch wins
else if (dataSource != null) {
    exceptionTranslator = new SQLErrorCodeSQLExceptionTranslator(dataSource);
}

// Spring 6.2.16 — the error-code translator is deprecated and only used if the
// application ships its own sql-error-codes.xml, which fcrepo does not
if (SQLErrorCodeSQLExceptionTranslator.hasUserProvidedErrorCodesFile()) {
    exceptionTranslator = new SQLErrorCodeSQLExceptionTranslator(obtainDataSource());
} else {
    exceptionTranslator = new SQLExceptionSubclassTranslator();
}

SQLErrorCodeSQLExceptionTranslator knows vendor-specific codes: Spring's bundled sql-error-codes.xml lists 40P01 (PostgreSQL deadlock_detected) under PostgreSQL's deadlockLoserCodes, so it produced DeadlockLoserDataAccessException — and the predicate matched.

SQLExceptionSubclassTranslator knows no vendor codes; it classifies by SQLSTATE class, and class 40 maps to PessimisticLockingFailureException — the superclass. The predicate no longer matches.

  fcrepo 6.5.1 fcrepo 7.0.0
Spring 5.3.39 6.2.16
default translator SQLErrorCodeSQLExceptionTranslator SQLExceptionSubclassTranslator
knows 40P01? yes, from sql-error-codes.xml no, only SQLSTATE class 40
exception produced DeadlockLoserDataAccessException PessimisticLockingFailureException
predicate matches? yes → up to 10 retries no → not retried
what the client sees nothing; a WARN in the log a failed request

This also explains why it went unnoticed: on MySQL, for which the retry was written, the error code translates differently.

The deadlock itself (root cause 1) exists identically in both versions — 6.5.1 just swallows it. Our production instance shows exactly that, and it means an upgrade to 7.x turns a latent, invisible problem into user-visible request failures.

The same deadlock occurs in ordinary operation, not just bulk ingest

This is not an artefact of a bulk-loading tool. Searching ~1.5 years of centrally collected container logs from our production instance (fcrepo 6.5.1, PostgreSQL, ordinary interactive traffic — no bulk ingest) for deadlock detected returns 21 log records, spread over roughly 7 distinct incidents:

period records
2025-02 6
2025-03 6
2026-06 3
2026-07 6

15 of them come from the PostgreSQL container and 6 from the Fedora container, and they are the same failure as above:

WARN (ContainmentIndexImpl) Unable to commit containment index transaction 018cda3d-...
  Where: while updating tuple (0,110) in relation "containment";
  nested exception is org.postgresql.util.PSQLException: ERROR: deadlock detected

The rate simply scales with how many transactions commit concurrently: a handful of incidents per year under interactive load, against 700 in a few hours of parallel ingest. On 6.5.1 none of these reached the client, because the retry still worked there (see root cause 2).

Steps to reproduce

  1. Run Fedora 7 against PostgreSQL.
  2. Create a container /parentA and a container /parentB.
  3. From N ≥ 4 concurrent clients, repeat: open a transaction, POST one child to /parentA and one child to /parentB within that same transaction, commit.
  4. A fraction of the commits fail with deadlock detected on UPDATE containment SET updated = ? WHERE fedora_id = ?.

The rate scales with client concurrency; with a single shared parent per transaction the problem does not occur.

Suggested fix

We have both changes applied to a local 7.0.0 build and are running with them; happy to open a PR if the approach looks right.

  1. Order the lock acquisition. Adding ORDER BY parent to GET_UPDATED_RESOURCES makes every commit take the row locks in the same order, which removes this class of deadlock entirely for all backends. This looks like a one-line change.
  2. Make the retry policy match PostgreSQL. Broadening the predicate to PessimisticLockingFailureException (or checking ConcurrencyFailureException, or inspecting SQLSTATE 40P01 / 40001) would restore the intended safety net. Worth doing regardless of (1), since it currently gives a false sense of protection on any non-MySQL backend.

Notes on workarounds

For anyone hitting this before a fix lands, the only reliable client-side mitigation we found is to ensure that concurrently committing transactions do not share more than one parent container — e.g. by interleaving work across membership containers instead of processing one container to completion, and serialising commits per shared parent.

Reducing fcrepo.db.max.pool.size is not a viable workaround: per FCREPO-3725 Closed , Fedora needs more than one pooled connection per in-flight request, so shrinking the pool deadlocks the application itself.

Client-side retries do work — after retrying the failed records our repository ends up fully consistent — but each retry repeats the whole record, so the cost is real on large ingests.
