FCREPO-2396 PUT to fcr:metadata fails to add/replace non-server-managed triples

TypeBug
StatusClosed
ResolutionWon't Do
PriorityMajor
Reporterkefo
Created2017-02-07 19:44 UTC
Updated2021-09-17 17:37 UTC
Resolved2021-09-17 17:37 UTC
Affects versionsFedora 4.7.1

Environment

Tomcat7/Postgres9.4

Description

This command

curl -X PUT -H "Content-type: application/turtle" -H "Prefer: handling=lenient; received=\"minimal\"" -i --data-binary @add_title3.ttl "http://host:port/fcrepo/rest/a/binary/fcr:metadata"

returns a "204 No Content" response but fails to replace the non-server-managed triples of the special 'fcr:metadata' resource associated with a binary (LDP-NR).

The turtle is simply:

@prefix dc: <http://purl.org/dc/elements/1.1/> .

<>
dc:title "Version 1" ;
dc:creator "kefo" .

The following gist contains a working example that demonstrates the problem. For comparison purposes it also contains an example of a PUT that does work as expected against a generic RDF resource (LDP-RS) and a PATCH request against the fcr:metadata resource that works as expected.

https://gist.github.com/kefo/40ddf654ef96edce523b2559dae26c1a

It seems that a PUT to 'binary/fcr:metadata' fails to update the fcr:metadata resource when using the <> placeholder, but a PATCH to the same 'binary/fcr:metadata' endpoint using the <> placeholder succeeds.

More information regarding this issue is found in the #fcrepo IRC log beginning around 11:54 AM: http://irclogs.fcrepo.org/2017-02-07.html

Aaron Birkland, 2017-02-07 20:47 UTC

Good catch! In this case it seems clear to me that <> is correctly interpreted as <http://host:port/fcrepo/rest/a/binary/fcr:metadata> when interacting with http://host:port/fcrepo/rest/a/binary/fcr:metadata.

The LDP specification mentions that LDP servers MAY ignore server-managed properties in PUT, but your example isn't one of those. If a fedora implementation wishes to disallow triples that contain <http://host:port/fcrepo/rest/a/binary/fcr:metadata> as a subject, then the LDP specification suggests that the response MUST be in the 4xx range (e.g. a 409). PATCH ought to behave consistently to this (i.e. throw 409 whenever it attempts to create triples that are disallowed), but I don't think the LDP spec spells that out.

Given the above, it would seem that a 409 in response to both the PUT and PATCH examples would be consistent with the constraints in place.

Aaron Birkland, 2017-02-08 18:28 UTC

Absent language in the fedora specification defining the default base URI to be the binary's URI, I'd argue that PATCH is technically incorrect. According to LDP 4.2.1.5 and RFC3986, the baseURI in the example is <http://host:port/fcrepo/rest/a/binary/fcr:metadata>

So to do a PACH on the descriptive LDP-RS: http://host:port/fcrepo/rest/a/binary/fcr:metadata:
{{INSERT

{<> dc:title "whatever" .}

}}

.. should result in the addition of the triple
{{<http://host:port/fcrepo/rest/a/binary/fcr:metadata> dc:title "whatever" }}
.. due to the resolution of <> as <http://host:port/fcrepo/rest/a/binary/fcr:metadata> according to the above referenced specifications.

... instead, it resolves <> as the URI of the LDP-NR, and adds this triple:
<http://host:port/fcrepo/rest/a/binary> dc:title "whatever"

This is not an expected outcome according to any published or proposed specification at the moment. If it is indeed the desired behavior, then it would likely be necessary to amend the proposed fedora spec in order to make it allowable.

A. Soroka, 2017-02-09 13:28 UTC

Aaron Birkland: that misses my point, which is to ask where to place those statements. Putting them in the LDP-R violates the single-subject rule, putting them in the LDP-NR is nonsense, and "interpreting <> on http://host:port/fcrepo/rest/a/binary/fcr:metadata as http://host:port/fcrepo/rest/a/binary/fcr:metadata, that would be fine... as long as the ability to add triples that have the LDP-NR as subject (using absolute URIs) remains." is useless.

Interpreting <> that way does nothing to help anyone make claims about the LDP-NR, which is the whole purpose of the work, and adding those other triples violates the single-subject rule again. That is no better than what exists now.

More importantly, the specifications you cite are off-point. Benjamin Armintor already hinted at the right specifications to construe (in IRC linked above): those that deal with the syntax of the message. So for example, SPARQL offers BASE declarations, Turtle offers @base, etc.

There is no way not to break the single-subject rule here. The practical question is how to construct an interpretation of the relevant specifications that gives us the behavior that is clearly what any sensible user wants, and the answer is: Use the abilities in the RDF and SPARQL standards to offer an explicit base, and define that base as we find meet: the resource URI in all cases save when the resource is the target of an intra-repository describedby link, when it should instead be the URI of the described resource.

LDP 4.2.1.5 or RFC3986 should never even come into play.

Benjamin Armintor, 2017-02-16 18:19 UTC

Updating with follow up:

SPEC
<> should resolve to the request URI

CURRENT IMPLEMENTATION (ldpnr <foo>, ldprs <bar>)
PUT to <foo/fcr:metadata> with a subject of <> 204's with no update (deceptively, but maybe correctly)
PUT to <foo/fcr:metadata> with a subject of <foo> succeeds
PUT to <foo/fcr:metadata> with a subject of <foo/fcr:metadata> 403's (incorrect subject)
PUT to <bar> with a subject of <> succeeds
PUT to <bar> with a subject of <bar> succeeds

PATCH to <foo/fcr:metadata> with a subject of <> succeeds
PATCH to <foo/fcr:metadata> with a subject of <foo> succeeds
PATCH to <foo/fcr:metadata> with a subject of <foo/fcr:metadata> fails
PATCH to <bar> with a subject of <> succeeds
PATCH to <bar> with a subject of <bar> succeeds

Hydra uses diamond subjects for LDP-Cs, but explicit subjects for LDP-NR descriptions
Islandora-CLAW does not yet support these updates

Backwards compatibility alone is not a guide here, since the existing PUT behavior is "more correct", and we haven't identified a client relying on the non-conformant PATCH behavior.

I think that if we are going to adhere to spec'd behaviors around <>, the status on PUT to <foo/fcr:metadata> for subjects of <> and <foo/fcr:metadata> should fail with the same informative 403 "foo/fcr:metadata is not in the topic of this RDF, which is foo".

While the PATCH behavior could apparently be brought into specification without breaking ActiveFedora or CLAW, that seems like a different ticket.

As discussed above, there is a clear behavior to use around BASE/@base declarations; I'm only commenting on the unidentified diamond subject.
