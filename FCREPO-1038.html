FCREPO-1038 Calling HEAD on getDatastreamDissemination in REST API calls GET on the underlying service for datastreams in control group E

Environment

Linux 2.6.18-194.11.1.el5 #1 SMP
Red Hat Enterprise Linux Server release 5.5 (Tikanga)

Description

Performing a HEAD call on the getDatastreamDissemination REST API does not seem to result in a HEAD call on the underlying resource for control group E. Instead it seems like a HTTPClient instance is spun up and the whole underlying HTTP request for a GET completes before the server returns a response. This is kind of deadly for large files.

Maybe there's another api I should be invoking? Anyway, this seems like an unintended behavior.

Chris Wilper, 2011-12-10 00:30 UTC

Hmm. I believe that if HEAD isn't explicitly implemented, Jersey will try to honor the request by pretending it was a GET and omitting the response body. That may be what's happening here. And that in itself is not a problem...just an inefficiency that could be improved by explicitly implementing HEAD so the underlying Fedora code knows that only a HEAD should be requested of the underlying resource.

However, what you seem to be indicating is that some resource (the http connection pool?) is getting exhausted (and thus causing future requests to block) after a bunch of HEAD requests to E datastreams.

If that's true, it could be that when jersey omits the response body, it's not bothering to close the associated stream, and that's what's causing the connection pool to become exhausted.

When you say "in a state where it is no longer able to serve out E datastreams", does that mean you're observing Fedora hanging for future requests? Or does it give you an error?

In frank asseg's example, I think most of those headers are set by Confluence. As far as I can see, CXF sends the following back when I send a HEAD request with curl for a datastream dissemination:
***
HTTP/1.1 200 OK
Server: Apache-Coyote/1.1
Set-Cookie: JSESSIONID=94156535D5CA479BE4CE6A014275A72C; Path=/fedora
content-disposition: inline; filename="econ_9495_719.pdf.pdf"
Date: Wed, 02 Oct 2013 19:14:19 GMT
Content-Type: application/pdf
Content-Length: 0
***
So FCRepo really ought to have the latitude to implement HEAD as it sees fit, so long as it reproduces the headers in responses to both HEAD and GET. This is (perhaps obviously) more difficult for JAXB responses, where we can't predict what the length would be- we could probably still provide the Last-Modified and ETag headers, but couldn't really fulfill the contract without the Content-Length.
