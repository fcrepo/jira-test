Description

If a request that's part of a multi-request transaction fails, it's possible for it to leave the transaction in a bad state. However, the transaction may still be committed, potentially putting Fedora in a bad state.

For example: https://github.com/fcrepo/fcrepo/blob/main/fcrepo-kernel-impl/src/main/java/org/fcrepo/kernel/impl/services/CreateResourceServiceImpl.java#L136

That code writes to OCFL staging and makes a number of updates in the database. If any of those fail, the prior changes remain, which means the incomplete updates will be persisted if the transaction is committed.

It is easy to solve the database rollback by adding @Transactional to the service API. This is also required for https://jira.lyrasis.org/browse/FCREPO-3695.

However, it's not possible to rollback the staged OCFL changes because you can't distinguish between staged changes from the current request and those from previous requests. The OCFL changes should be made last to reduce, but not eliminate, the chance of there being an issue here.

Another approach would be to mark a transaction as failed when an exception is encountered and not allow failed transactions to be committed.

It's difficult to create a manual test case that demonstrates this bug because the most likely failure case here is an intermittent connectivity issue with the database.

Note, this problem is not limited to the CreateResourceServiceImpl. It was just given as an example.
