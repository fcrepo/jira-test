FCREPO-2323 Resource with URI property containing hash inaccessible when target is deleted

Environment

Linux, fcrepo 4.7.0, Tomcat 7

Description

When a resource has a property made of a URI pointing to a resource managed by the same repository and containing a hash fragment, if the destination resource is deleted, the first resource is not accessible (404) except with HEAD, and the tombstone of the deleted resource is not deletable.

E.g. </a> ex:link </a/b#c>

Deleting /a/b causes /a to become inaccessible.

Attached is a shell script that reproduces this behavior. Tested behind Apache rev proxy.

This is a critical issue since Hydra/Curation Concerns deletes resources in a way that causes this scenario.

scossu, 2016-12-05 16:25 UTC

A way to find out which resources are affected by the bug is to crawl the repository and send a HEAD request and a GET request on each of them. If HEAD returns 200 and GET 404, the resource is inaccessible.

scossu, 2016-12-05 16:31 UTC

Good news about this is that the data for the missing resource are still in the external indices. The resource can be possibly recovered (we haven't tested yet) with these steps:

  • Retrieve the resource's triples from a triplestore index
  • Delete the resource (it responds correctly to a DELETE request)—do this only after verifying that you have retrieved all the correct triples or the resource will be gone forever!
  • Delete the tombstone
  • PUT the resource again using the previously retrieved triples

kefo, 2016-12-05 17:45 UTC

Also - while I am thinking of it - if you replaced 'b#c' with 'b/c' in the scripts above, I believe they will not result in the resource becoming inaccessible because Fedora responds "400 Bad Request" when attempting to PATCH resource 'a' with a relationship to resource 'b/c', which does not exist. The 'PATCH' fails. This is, of course, in keeping with Fedora behavior of not permitting the creation or updating of resources with relationships to non-existent intra-repository resources. Hence the focus on the hash URI here.

kefo, 2016-12-05 18:16 UTC

I don't know if this note is helpful to diagnosing and correcting this issue, but it may help making resources accessible again.

I noted that you can PUT a new resource under the inaccessible resource/container, after which the previously inaccessible resource will again respond 200 to a GET request.

These lines could be tacked on to test_corruption.sh to demonstrate this.

--------------------
echo; echo; echo "Now, although inaccessible, can we PUT a resource under ${container} ?"
curl -iXPUT "${container}/x"

echo; echo; echo "Let's fetch our new resource."
curl -i "${container}/x"

echo; echo; echo "Let's fetch the container, which should now be accessible (again)."
curl -i "${container}"
--------------------

Andrew Woods, 2016-12-05 21:34 UTC

After some investigation, the issue here is not related specifically to hash-URIs, but instead having links between resources, then deleting a parent of the target resource. The proper clean-up of references is not happening in this case.
For example, if:
</a> ex:link </b/c>
..and we delete </b>, this will result in the same 404 situation documented in this ticket.

It should be fairly straightforward to create a patch that handles these situations. The natural approach is to recurse the children of the resource to be deleted and clean up their inbound references.

kefo, 2016-12-14 23:00 UTC

I want to report on some testing related to this bug.

We are running fcrepo 4.6.1 in production. We have about 30,000 of these inaccessible resources.

We cloned the machine so we could test this fix using 4.7.1 RC1. I backed up the entire repository (fcr:backup), installed 4.7.1 RC1, and restored the repository. I then ran a verification script that evaluated every resource for the GET 404, HEAD 200 pattern. By and large, 4.7.1 RC1 permitted us access to the previously inaccessible resources. However, there were a handful of resources – 12 to be precise – that still matched the GET 404, HEAD 200 pattern. I found that a little odd, but a GET on one of the previously inaccessible resources returned the resource’s triples minus the triple whose object was a non-existent resource. (We can live with the 12, but I felt it important to note that, for some reason, Fedora still refused to serve up resources affected by this bug.)

Still testing, I then figured I’d run the scripts above against 4.7.1 RC1. Although the scripts no longer produced the 404 GET, 200 HEAD pattern (everything was GET 200, HEAD 200), in one situation the scripts still produced unexpected output.

We use httpd (apache) to reverse proxy tomcat. This entails adding a value for the proxyName attribute in Tomcat’s server.xml config file:

<Connector port="8080" protocol="HTTP/1.1"
               connectionTimeout="20000"
               proxyName="server.artic.edu"

If I set the fedora address in the above scripts to ‘server.artic.edu/fcrepo/rest’ and run the above scripts, the outcome is good. I get a 200 GET, 200 HEAD response and there appears to be no rogue triple. If, however, I set the fedora address to ‘localhost:8080/fcrepo/rest’ and I run the above scripts from localhost (obviously), I get a 200 GET, 200 HEAD response (not 404 GET, 200 HEAD), but the triple whose object points to a deleted resource (a non-existent resource) is included in the output. The URI of the triple's 'object,' which is the deleted (non-existent) resource, begins "http://localhost:8080/....". That is, the inserted triple bears the domain of the PATCH request, and not Tomcat's proxyName setting. I'm not sure if this is by design, but it was unexpected and seems related to this issue.
