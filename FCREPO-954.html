Description

We have a use case to expose Fedora datastream/objects to science data tools that are dependent on a meaningful file system and MIME indicators by file extension. For example, Earth and Atmospheric Science community has a tool to read a special format called NetCDF that represents multiple-dimensional arrays and there are data tools serve them via HTTP, but needs to scan the file system for that type of files, rather than read a HTTP stream.

I would therefore like to have the the hints argument in the Akubra API to be populated with the mime type and the parent PID, in order to implement a special storage on the file system for this kind of tool. The Parent PID is to be used to form a correct collection hierarchy, and the MIME type is to be used to write the file extension.

We have had an implementation (using the Fedora 3.4.2 legacy storage system) that used the internal low-level storage API, which needs to be move into Akubra as a true sustainable solution.

Chris Wilper, 2011-06-21 23:26 UTC

Thanks for joining us in today's call, Jerry.

We brainstormed how it could be done, and talked about a pluggable "hint provider" interface, implementations of which would provide the necessary hints (content type, parent id, etc) to be passed down to Akubra at storage time. This interface might look something like:

public interface FedoraAkubraHintProvider {
Map<String, String> getHintsForAboutToBeStoredObject(FedoraObject obj);
Map<String, String> getHintsForAboutToBeStoredDatastream(FedoraObject obj, String datastreamId);
}

One can imagine that implementations of this interface could be injected via Spring.

If implemented for Fedora 3.6, the class that uses this interface would be DefaultDOManager...wherever it makes a call to m_permanentStore.addDatastream, .replaceDatastream, .addObject, and .replaceObject. The hint (map) retrieved would be passed down to the LowlevelStorage implementation, keeping the original method signature, but adding one that specifies a hint in addition to the id and inputstream. Then for the Akubra-based implementation of LowlevelStorage, the hint would actually be passed down to the underlying akubra implementation.

If implemented in Fedora 4.0, the class that uses this interface would be a concrete implementation of HighLevelStorage (specificially, a high level storage implementation that uses akubra for blob storage).

I have opened this issue, signifying that the committers agree that a pluggable "hint provider" for Akubra should be added to Fedora. I have also put it in the 4.0 bucket, signifying that we'd like to see it happen for Fedora 4.0. However, as we discussed in the meeting, this may be possible to add to Fedora 3.6 if a) it is done in time, and b) the implementation, including integration tests, is done by someone other than the committers; we are focused primarily on performance testing and fixes for the 3.6 release.

Jerry, you mentioned on the call that you may have resources put into the implementation of this. That's great. Do you think it may be possible in the next 2 or 3 months? It's a bit early to have a date for Fedora 3.6, but I'd guess that 3 months after 3.5 is the quickest it would happen.
