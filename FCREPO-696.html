Former user, 2010-05-31 08:35 UTC

Here's a more detailed analysis of the issue:
If a datastream is added to an existing object, the following chain of methods gets called:

1) DefaultManagement.addDatastream() (call to ds.getChecksum())
2) Datastream.getChecksum()
3) DatastreamManagedContent.computeChecksum()
4) Datastream.getContentStreamForChecksum()
5) DatastreamManagedContent.getContentStream()
6) ManagementModule.putTempStream(Context, InputStream) --> From 5) to 6) an empty context is passed along which causes the pep to deny auth due to an indeterminate result
7) DefaultManagement.putTempStream(Context, InputStream)
8) DefaultAuthorization.enforceUpload(context)

The error happens when DatastreamManagedContent passes an empty context to DefaultManagement.putTempStream(..). The issue is not related to the ExternalContentManager in any way. Fedora 3.2 shows the same behavior.

Stephen Bayliss, 2010-06-09 17:06 UTC

Full solution for this would be to implement FCREPO-718 Closed .

Interim solution is to remove the dependency on API-M putTempStream (in fact this is for user-uploaded content, with timed cleanup of the temp file, which isn't so appropriate for this case) and manage the files directly as temp:// files (in the same manner as temp files are managed eg for ingest, inline binary content managed datastreams etc); then once FCREPO-718 Closed is implemented revisit and handle properly.

DOManager dCommit will clean up any temp:// file used by a managed datastream, so cleanup will happen as part of current code.

DatastreamManagedContent then needs to handle file:// (directly reading the file), uploaded:// (again directly from the file), plus remote location and existing content location as per current code.
