Description

From https://github.com/fcrepo4/fcrepo4/issues/1045

I have a N3 graph that looks like this.

<http://localhost:8080/fcrepo/rest/object/id:0001> <p1> <o1> ; ... ; <p30> <o30> .
<http://localhost:8080/fcrepo/rest/object/id:0002> <p1> <o1> ; ... ; <p30> <o30> .

and so on for many thousands of ids. I would like to just run a command like this:

$> curl -X PUT -H "Content-Type: application/n-triples" -H"Prefer: handling=lenient; received="minimal"" --data-binary "@update_rdf.n3" "http://localhost:8080/fcrepo/rest/object"

and have the consumer understand that the subjects are just children of the topic. AFAIK, this is not yet supported and the only way to do this is to create separate data-binary import files for each subject and then point the target command at each child. (If there is an existing method I am missing, please let me know!)

The motivation for this is in line with LDP UC4: Update existing resource (https://dvcs.w3.org/hg/ldpwg/raw-file/default/ldp-ucr.html#dfn-f4.2)

The workflow is index the Fedora data into Fuseki, do a selective SPARQL UPDATE, construct and reserialize the graph as N3, and replace the parent container in Fedora.

I'd like to ask you, Christopher Johnson (who filed the Github issue), to comment a bit more about the immediate use case. Are you trying to avoid the cost of managing the many separate requests that would normally be use for this action or trying to avoid the performance penalty of many HTTP requests, or something else entirely?

What Esmé Cowles said about HTTP/2 is quite true, of course, but there are many more problems with the idea of batch action. That's part of why LDP Batch did not become part of the larger LDP standard. Sending serialized commands against a special endpoint is not RESTful at all. Fedora is pretty grim and serious about its RESTfulness.

If you are trying to avoid the overhead of management, a simple approach in which you use some external tool like a script to factor a large graph into many graphs and produce requests for each would seem to work. Otherwise, we can parse out your requirements a bit more before proceeding.

A. Soroka, 2016-06-02 13:25 UTC

It's really not a question to me of mechanics, but of whether this is an approach that actually fits the Fedora API, and I rather think it isn't. The Fedora API is a RESTful API for an object repository, which means that it expects to be addressed at a given identifier with properties for that identified resource, not a probably-related set of resources with syntactically-similar identifiers (keep in mind that the syntactic hierarchy immediately available from Fedora has no semantic beyond LDP containment).

What are your needs for atomicity? If a SPARQL Update fired and only some of the resources received their modifications, would that be catastrophic, annoying, or no big deal?

A. Soroka, 2016-06-02 13:44 UTC

My suggestion of a script for "factoring" your update was indeed given with the example of an exported graph in mind:

  1. Make modifications in your triplestore as desired, using whatever techniques are useful.
  2. Export a big fat graph.
  3. Open a repository transaction.
  4. Use a script to loop over all repository resources named in the big graph and:
    1. Split out a single graph for a single resource from the big graph.
    2. Fire an update with that small graph at that single resource.
  5. Commit the transaction.

With proper design, I shouldn't think that script would have to be a "one-off", and it should give you both control of when the delta is moved and (if you do need it) atomicity. If you'd like some help with writing that kind of script, I think we can arrange for that.

A. Soroka, 2016-06-03 13:48 UTC

I'm not quite clear on what you mean by: "it is possible to create duplicate records with SPARQL insert…" SPARQL (nor RDF itself) has no notion of "record". It is not possible to create duplicate triples within a graph in the RDF model. Are you discussing the possibility of your SPARQL Updates generating more than one copy of the same triple? If so, there might be a problem with the data model you are intending to use with Fedora, and we should discuss that as a separate point.

Fedora currently does implement LDP Indirect Containers, so if that functionality would meet your need (I admit that it's not clear to me how it would) then that would be wonderful-- you have a road forward.
