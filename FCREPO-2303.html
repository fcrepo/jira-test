Description

Triples are defined as being the "same" when the predicates and objects match, and the subjects are "relatively equivalent" (i.e. they match in the path portion of the URI, but not necessarily in the domain, subdomain, or port).

For export operations, it is straigtforward to compare the RDF on disk to all triples returned by fcrepo for the corresponding resource path. For import operations, the comparision is more complex. Because certain triples are 'server-managed' and the current import/export tool cannot modify these triples, there can be no guarantee that server-managed triples will have the same values as the resource in its on-disk representation after import.

The algorithm to verify RDF resources created during an import operation, therefore, should look something like this:

1. For each resource on disk, request both all triples and minimal triples for the version of the resource on fcrepo;
2. Create a graph for each set of triples, and compare the two graphs; the server-managed triples are the triples in the full set that are not also in the minimal set;
3. Create a graph from the pre-import representation of the resource on disk;
4. Iterate over the triples in this pre-import resource, removing the triples that match the predicates of triples in the server-managed set calculated previously;
5. Compare the set of triples that remain to the minimal triples returned for the corresponding resource in the post-import fcrepo instance; the sets should match exactly.

Implementation of this algorithm is complicated by the fact that in the current implementation of the verification tooling, objects of the "Resource" class are not natively 'aware' of their counterparts in the second location (either fcrepo or on-disk, depending on the operation being verified). Re-conceptualizing the 'resource' object as an abstract entity with two related instantiations would simplify the implementation here, but is probably not required in order to make this work.
