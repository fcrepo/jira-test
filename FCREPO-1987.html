Peter Matthew Eichman, 2018-10-05 17:29 UTC

I have a working implementation that allows hash resources to be added to binary resources. It creates a "#" node as an additional child of the nt:versionedFile that represents the binary. That is, it is a sibling to the "fedora:description" and "jcr:content" nodes.

Currently, I don't have any working integration tests. I've tried adding them to the FedoraBinaryImplIT class in the fcrepo-kernel-modeshape project, but it seems that creating the resource via the BinaryServiceImpl doesn't allow for the "#" node to be created. However, running HTTP requests to create and update a binary (as in the ticket description) do work.

Peter Matthew Eichman, 2018-10-08 16:55 UTC

There has been additional discussion of this issue on Slack, and we haven't come to a resolution yet. Here are some of the issues:

  1. The approach in this branch (https://github.com/peichman-umd/fcrepo4/tree/FCREPO-1987) makes the hash resources children of "#" node under the resource node that represents the binary. They are therefore not children of the "fedora:description" node. There was some concern expressed that this decouples these bits of the binary's metadata (those expressed using hash URI subjects) from the rest of the binary's metadata, especially with regard to metadata lifecycle and memento creation.
  2. Changing the storage layout to make the hash URI tree a child of the "fedora:description" would require the HttpResourceConverter to be able to distinguish between the cases where "resource#hash" should become "resource/#/hash" (LDP-RS) and "resource/fedora:description/#/hash" (LDP-NR).
  3. This could be addressed by making the hash URIs hang off of the "fcr:metadata" URI (resulting in URIs that look like http://localhost:8080/rest/resource/fcr:metadata#hash). This is currently not possible, as the repository rejects triples whose path does not match the path of the topic resource (a.k.a., the single subject restriction). Since /rest/resource/fcr:metadata is different from /rest/resource, this kind of update is currently not possible. If that restriction were loosened to allow triples with the same path but with an appended "/fcr:metadata", this should then be possible.
  4. There may still be some issues in resolving the Modeshape nodes. Currently, when FedoraResourceImpl.updateProperties() calss getDescribedResource() to get the subject resource, if the request URI is a NonRdfSourceDescriptionImpl (as it is in the case of a PUT or PATCH to "resource/fcr:metadata", then it returns the binary resource itself (which will then resolve to the Modeshape path of "resource" and not "resource/fedora:description".
  5. There is an additional tangential concern about allowing (or requiring) hash URIs hanging directly off of the binary URI, in that those hashes could interfere with the use of the hash portion of a URI to identify a document fragment. On the other hand, it is possible that we would want to allow such URIs as subjects, so you could provide metadata about specific portions of a binary.
