Description

When PATCHing with a statement like

prefix ldp: <http://www.w3.org/ns/ldp#>
DELETE { <> ldp:membershipResource ?o }
INSERT { <> ldp:membershipResource </rest/someResource> }
WHERE { <> ldp:membershipResource ?o }

The final graph contains

(triple <http://localhost:59512/rest/f7407624-da02-4617-acca-3b5d30e3a70b/322fd97b-3b0d-4237-86f2-9ff98ce86b85> <http://www.w3.org/ns/ldp#membershipResource> <info:/rest/someResource>)

There is soon to be code in the HttpIdentifierConverter to account for these as external Ids and correctly convert them to internal IDs.

Andrew Woods, 2020-09-08 15:49 UTC

In trying to reproduce the issue described in this ticket, I perform the following steps:
1. Create basic container
$ curl -i -XPUT -H'Link: <http://www.w3.org/ns/ldp#BasicContainer>; rel="type"' -H"Content-type: text/turtle" --data-binary @body.rdf localhost:8080/rest/box

  • Where body.rdf is:
    ```
    <> <http://awoods.com#title> "A title"
    ```

2. Verify the user-triple was created
$ curl localhost:8080/rest/box

3. Update the container with a new triple
$ curl -i -XPATCH -H"Content-type: application/sparql-update" --data-binary @update.su localhost:8080/rest/box

  • Where update.su is:
    ```
    INSERT { <> <http://awoods.com#relation> <http://localhost:8080/rest/someOtherResource> }

    WHERE {}
    ```

4. Verify the triple was inserted
$ curl localhost:8080/rest/box

..all is well. Should the test be different to demonstrate the issue?
