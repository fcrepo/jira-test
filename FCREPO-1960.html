Description

Fedora should publish as part of the ontologies a system of classes and predicates (mostly reusing extant work) for the encoding of published events, such as appear on the Java API's event bus and are currently translated into JMS. Of course, the JMS event tap should also use this encoding.

A. Soroka, 2016-03-25 16:53 UTC

Looks good, thanks for moving this forward. I do have some questions:

1. Why break up the URI into "root" and "resource path"?
2. Do we not have something we can import for timestamp? Maybe from PREMIS or somewhere?
3. Ditto for "user"?

Unknown, 2016-03-25 17:17 UTC

The reason to break up root and resource path has everything to do with how transactions work in Fedora – to start a transaction, one needs to know the location of the Root.

So in a messaging context, if I want to start a transaction, I need to issue that request to the root location. If the message simply has the root and the path concatenated, then the client would need special a priori knowledge about where that root location is.

Another thought was the multi-tenancy context. While this isn't relevant at present, if there were multiple roots, I can imagine that it would be extremely convenient for a messaging system to be able to route based on the value of the root URI.

I am not wedded to that division, but it would make certain operations significantly easier for a client.

Unknown, 2016-03-25 17:32 UTC

The premis vocabulary contains premis:hasEventDateTime which seems like an excellent match for the timestamp property. Premis also includes premis:hasEventRelatedAgent, though it seems from the documentation that a subProperty such as http://id.loc.gov/vocabulary/preservation/eventRelatedAgentRole/aut is preferred.

Either way, seems like we can remove the timestamp and user-related fields from this ontology.

Unknown, 2016-05-19 17:31 UTC

I have updated https://github.com/fcrepo4-labs/fcrepo-event-ontology to use the PROV ontology to express events from the messaging system. An example in compact JSON-LD is provided, using the provided context.json in that git repo.

This further shrinks the potential event ontology to contain only three classes (event:ResourceCreation, event:ResourceDeletion, event:ResourceModification). All properties come from other, existing ontologies (prov, dc, dcterms and foaf).

I looked into using premis for this, but ultimately, PROV proved to be a much more natural fit.
