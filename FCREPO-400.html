Description

Ross@UVA reported that when attempting to run a dissemination where a DSInputSpec-defined datastream is unvailable, but not really required by the particular dissemination being run, it's caught as an error and the dissemination fails to run.

A set of objects that provoke this is attached as hydra-objects.zip

Here is Ross' email describing his investigation of the cause of the current behavior in Fedora 3.1:

—

I think I pinpointed this problem in code for DefaultAccess near line 500:

DisseminationBindingInfo[] bindingInfo;
bindingInfo = new DisseminationBindingInfo[dsBindRules.length];

for (int i = 0; i < dsBindRules.length; i++) {
DeploymentDSBindRule dsBindRule = dsBindRules[i];
String dsPid = dsBindRule.pid == null ?
dObj.GetObjectPID() : dsBindRule.pid;
String dsId = dsBindRule.bindingKeyName;
Datastream ds;

DOReader reader = m_manager.getReader(false, context, dsPid);
ds = reader.GetDatastream(dsId, versDateTime);

if (ds == null)

{ String message = "The object \"" + dsPid + "\" " + "contains no datastream with ID \"" + dsId + "\" " + "that was created on or before the specified date/timestamp " + " of \"" + DateUtility.convertDateToString(versDateTime) + "\" ."; throw new DatastreamNotFoundException(message); }

This logic will throw exception if any of the datastream binding rules are not satisfied. I think part of the problem is that the dsInputSpec definition of binding rules is too broad; it just defines a set of binding rules for a particular sDep and does not differentiate which binding rules are associated with which method.

To fix this, I think you would need to either gather additional information from wsdl or methodMap about which bindings were required for each method or add additional information to dsInputSpec that allows you to specify which method a binding rule is associated with...

I suppose if we wanted to be really loose re referential integrity, you could just omit this check and have the dissemination method fail in DisseminationService at run time. That way, methods with matching binding rules would still work and only ones with missing binding rules would fail...

This logic is probably a leftover from Fedora 2.2 when we wanted to catch any case where binding rules were not satisfied since all binding rules had to be satisfied when referential integrity was tight.

Benjamin Armintor, 2009-03-31 17:55 UTC

I think these two problems are similar in symptom, but different in cause.

The UVA problem comes from a sdep that has DSInputs referring to a named datastreams in their content model. This problem is that, because there is only a single DSInputSpec for the sdep, a particular DSinput may be irrelevant to a service, but still throw the exception if it's missing. This is compounded (if I'm reading things right) by the fact that DefaultAccess also doesn't consider the value of the DSMin attribute before throwing the exception: One can imagine indicating that a DSInput has a minimum occurence of 0 (it might be absent) and that its corresponding parm name be required="true" for a particular method in the methodmap (throw an error at runtime of that method). EDIT: this is a repitition of Ross at the top, I see.

The TUD problem comes from a sdep that has DSInputs (source, xsl) referring to named datastreams absent from their content model entirely- there are defined wsdl message parts of that name, which makes sense given the appearance of the URL of the service. Unless I'm reading the attached document incorrectly, this problem would go away if they changed the DSInput wsdlMessagePartName attributes to 'DATA' and 'XSL'.

The DSInput attribute 'wsdlMessagePartName' is pretty confusing. The DSInputSpecParser uses it to get the name of the datastream to fetch fron the digital object, but there really are named wsdl message parts in the sdep.

Chris Wilper, 2009-05-01 04:39 UTC

Benjamin, thanks for your analysis. You're right, the TUD objects were wrong to begin with and fixable as you suggested. Although the error seen was the same, the cause was different. The UVA objects were failing because of what Ross pointed out: overly-aggressive integrity checking up front.

I modified DefaultAccess to relax in these cases; if a datastream is really required for a particular dissemination, it will be caught later anyway. I tested this fix with demo:14 by purging one of the required stylesheets and running the dissemination that required the other one.
