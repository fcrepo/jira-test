Description

Import fails with a nondescript error:
INFO 12:57:00.426 (Importer) Imported binary: http://localhost:8080/fcrepo/rest/apix/extensions/image
ERROR 12:57:00.433 (ImportExportDriver) Error performing import/export: Index: 0, Size: 0

http://localhost:8080/fcrepo/rest/apix/extensions/image is a binary of type text/turtle, and is in the export directory as "export/fcrepo/rest/apix/extensions/image.binary". A tar of the export is attached

Exported with:
java -jar target/fcrepo-import-export-0.1.1-SNAPSHOT.jar --mode export --resource http://localhost:8080/fcrepo/rest --dir export --binaries

Imported into an empty repo with:
java -jar target/fcrepo-import-export-0.1.1-SNAPSHOT.jar --mode import --resource http://localhost:8080/fcrepo/rest --dir export --binaries

Esmé Cowles, 2017-05-26 17:35 UTC

Aaron Birkland, I assume you created the binary with some other content type and then used PATCH to change the mime type to text/turtle?  It seems like the import utility could do the same thing.

Aaron Birkland, 2017-05-26 17:46 UTC

Esmé Cowles No, I'm pretty sure it was deposited using `Content-Disposition: attachment`, which forces it to be a binary regardless of media type (at least in the modeshape impl).  I don't think I've ever tried patching media type after the fact.  Does the importer need to do that anyway (i.e. deposit the binary, discover the URI of the descriptive LDP-RS the server creates, then PATCH it with the contents of the exported descriptive LDP-RS?)? 

Esmé Cowles, 2017-05-26 17:49 UTC

Aaron Birkland, I had forgotten about the `Content-Disposition: attachment` approach to forcing it to be treated as a binary.  That seems like a very easy fix.

If that doesn't work for whatever reason, we do patch the binary to add the metadata, so we could do that if needed.
