Stephen Bayliss, 2010-05-25 09:22 UTC

What REST endpoint should we use for this? It has been previously discussed that defining a "repository" object would be a good idea - if we could settle on a PID for this maybe the endpoint could be on this object. Otherwise it probably lives outside the /objects URI path.

eddie, 2010-07-07 15:13 UTC

Why is the UploadResource class located in org.fcrepo.server.upload rather than in org.fcrepo.server.rest (where the rest of the REST API impls are)?

Also, the REST API documentation states that the service endpoint is /objects/upload but it's actually at /upload. Without consideration for implementation, is one preferable over the other? Or something else entirely?

Finally, API-M-Lite's upload returned a 201, but this implementation returns a 202. What's the rationale for returning a 202? (Not necessarily objecting, but it would be good to document at least in this ticket the reasoning). I can see how a 201 seems a bit inappropriate since "The newly created resource can be referenced by the URI(s) returned in the entity of the response" and we're returning an "uploaded://" URI. However a 202 seems at least as inappropriate: "The 202 response is intentionally non-committal.... The entity returned with this response SHOULD include an indication of the request's current status and either a pointer to a status monitor or some estimate of when the user can expect the request to be fulfilled."

Perhaps a 200 is the more appropriate response code so long as the documentation explains we're returning an uploaded:// uri that can be passed to Fedora as a dsLocation?

Stephen Bayliss, 2010-07-08 11:48 UTC

REST API documentation corrected.

The intention with the endpoint was to explicitly keep it outside the main REST endpoint as it is in essence a utility method that will at some point go away, and it doesn't logically belong within the REST URI syntax.
