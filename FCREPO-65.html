Description

Blair has suggested that, by providing support for resolving XACML IdReferences, more flexible AuthZ can be achieved in Fedora. This is an enhancement to existing functionality.

On Nov. 13, 2006, Blair wrote:

I'm fairly certain that the idea I'm working on for the ARROW project will provide a more flexible and efficient authz solution. It will hopefully only require a simple addition to fedora.server.security.PolicyFinderModule to add support for finding policies based on idReference. The idea is to make PolicySets that support the intuitive notion of letting more specific controls take precedence in authz evaluation. For example; A Policy denying read access to a particular DO with PID 123 would take precedence over a Policy allowing access to a class of objects that the DO with PID 123
happens to be in (this class would be defined by metadata attributes such as the Dublin Core type).

The plan is to use the reserved POLICY datastream in every DO to hold the top level PolicySet passed to the PDP from the PolicyFinderModule. This would be the PolicySet used for any authz evaluation pertaining
to an action associated with a particular PID - almost all APIA and APIM operations. Any authz controls required on actions that do not have a specific PID associated with them (such as ingest, describeRepository, findObjects) could have policies placed in the default repository wide policy directory, which would otherwise be empty.

The new top level PolicySet would comprise of a set of other PolicySets combined using the FirstApplicablePolicyAlg. Therefore if a match were encountered early in the evaluation the result would be
returned and evaluation finished; other irrelevant policies would not need to be evaluated. The component PolicySets would be ordered from most to least specific with regard to their component Policy's Resource and Subject Targets, thus achieving the desired most specific overrides functionality. See the attached layout for an example; note that this is illustrative of only one possible top level PolicySet structure, different combinations of referencing, in lining and
further nesting could be used.

Blair has submitted the necessary changes to PolicyEnforcementPoint.java and PolicyFinderModule.java

On Feb. 5, 2007, Blair wrote:

The major additions are in the PolicyFinderModule where the cache
operations code lives. The reason for changing the
PolicyEnforcementPoint too is that PolicyFinderModule initialisation
had to be reworked to load the repository wide policies when the init
method is called (this is done by sunxacml when the PDP is created).
Because the init method is declared in the sun code it couldn't throw
an exception if loading of repo wide policies failed, thus I had to
add a check that is called after the PDP is constructed.

There are several customisable parameters that might be worth exposing
in fedora.fcfg:

  • the max cache sizes (that is the number of AbstractPolicies of each
    type, Policy or PolicySet, that can be cached at any time), currently
    100 of each;
  • the referenced policies directory, currently this is set to be
    "referenced-policies" at the same directory tree level as the
    "repository-policies" directory (currently if the directory does not
    exist it will NOT be created);
  • the cache decay rate, this is the time in milliseconds it takes to
    reduce an inactive cache entry's weight by 1 (currently 1 minute).
    The weight is used to select a row to replace on a cache miss when the
    cache is already full.

During testing I came across a rather strange behaviour which I think
may be a bug in the javax.xml.parsers.DocumentBuilder. When a
reference is included in a repo wide policy or another referenced
policy like so:
<PolicyIdReference>
policy.xml
</PolicyIdReference>
it works fine. However when the same lines are included in a FOXML
object's POLICY datastream they cause an invalid URI exception on any
access attempt (making the object unreadable), this seems to be due to
the new line after the opening element. Removing the formatting makes
the problem go away:
<PolicyIdReference>policy.xml</PolicyIdReference>

Certainly the new line is invalid in a URI however it doesn't seem to
be passed along when read from a file, the only difference being which
DocumentBuilder.parse method is called. Just something to be aware of
if/when idreference examples make it into the system documentation.

Chris Wilper, 2009-02-23 03:30 UTC

This feature was never merged in, and Fedora's code has changed significantly since. There is also an effort underway to re-work Fedora's XACML implmentation based on the work done in the Muradora project. See FCREPO-451 Closed for more on that. I'm closing this feature request for now in order to reduce confusion. If anyone still wants IdReference support against the new XACML impl, please check whether it was done by FCREPO-451or submit as a new feature request.
