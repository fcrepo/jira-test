FCREPO-4110 On PostgreSQL 16+ the containment_idx5 LIKE index is silently never created

TypeBug
StatusReceived
PriorityHigh
ReporterDavid Novák
Created2026-09-17 13:22 UTC
Updated2026-09-17 15:32 UTC
Affects versionsfcrepo 7.0.0

Description

Summary

R__Create_containment.sql creates the index that makes fedora_id LIKE 'prefix%' lookups usable only when the database collation is not C. The check reads lc_collate from pg_settings — but that GUC was removed in PostgreSQL 16, so the subquery returns NULL, NULL <> 'C' is NULL, and PL/pgSQL treats that as false. The index is skipped with no error and no warning.

The result is a silent, permanent performance cliff: every existence check on a resource falls back to a full scan of containment. On our repository (~809 000 rows in containment) that was a parallel sequential scan costing ~148 ms and three CPUs per query, at roughly 27 such queries per second — about 29 million rows scanned per second, and ~1000 % CPU on the database container. Creating the missing index by hand brought the same workload down to ~278 % CPU and 0.017 ms per query.

Everything looks healthy while this happens: the schema is created "successfully", queries return correct results, and nothing is logged.

Affected versions

PostgreSQL lc_collate in pg_settings index created?
12 – 15 present yes
16 absent no
17 absent no

Verified by querying SELECT count FROM pg_settings WHERE name = 'lc_collate' on stock postgres:15, postgres:16 and postgres:17 images: 1, 0, 0.

The affected code is unchanged on main as of today.

Root cause

fcrepo-configs/src/main/resources/sql/postgresql/R__Create_containment.sql:

--- Create an index to speed searches for fedora_id using LIKE if your Locale is not C.
DO
  $$
  BEGIN
  IF (SELECT setting FROM pg_settings WHERE name = 'lc_collate') <> 'C' THEN
    RAISE NOTICE 'lc_collate is not C, adding secondary index to resources.';
    CREATE INDEX IF NOT EXISTS containment_idx5 ON containment (fedora_id varchar_pattern_ops);
  END IF;
  END
  $$ LANGUAGE PLPGSQL;

On PostgreSQL 16 and later:

step result
SELECT setting FROM pg_settings WHERE name = 'lc_collate' no rows → NULL
NULL <> 'C' NULL, not TRUE
IF NULL THEN in PL/pgSQL treated as false
containment_idx5 not created, silently

Reproduced verbatim on our instance (PostgreSQL 17.11, database collation en_US.utf8, so the index should be created):

SELECT (SELECT setting FROM pg_settings WHERE name='lc_collate') AS value,
       ((SELECT setting FROM pg_settings WHERE name='lc_collate') <> 'C') AS condition;
-- value: NULL   condition: NULL
SELECT indexname FROM pg_indexes WHERE tablename = 'containment' ORDER BY 1;
-- containment_idx1
-- containment_idx2
-- containment_idx3
-- containment_pkey        <- containment_idx5 missing

The same database created on PostgreSQL 12.3 has all five indexes.

Impact

Without containment_idx5, a b-tree index cannot serve LIKE 'prefix%' under a non-C collation, so SELECT_ID_LIKE_IN_TRANSACTION — issued by ContainmentIndexImpl.hasResourcesStartingWith for every resource existence check while a long-running transaction is open — scans the whole table:

SELECT x.fedora_id FROM (
  SELECT fedora_id FROM containment WHERE fedora_id LIKE $1
  UNION
  SELECT fedora_id FROM containment_transactions WHERE fedora_id LIKE $2 AND transaction_id = $3 AND operation = 'add'
) x
WHERE NOT EXISTS (SELECT 1 FROM containment_transactions WHERE fedora_id LIKE $4 AND transaction_id = $5 AND operation = 'delete')

Measured on our instance with ~809 000 rows in containment, during a bulk ingest:

  without containment_idx5 with it
plan Parallel Seq Scan (2 workers + leader) Index Only Scan
buffers per query 14 727 5
time per query 147.698 ms 0.017 ms
sequential scans per 30 s 2 471 0
rows read per 30 s 873 779 691 0
database container CPU ~1000 % ~278 %

The cost grows with the table, so a new repository looks fine and degrades as it fills — which is what makes this hard to notice.

Steps to reproduce

  1. Start PostgreSQL 16 or 17 with any non-C collation (the stock postgres:17 image defaults to en_US.utf8).
  2. Point a fresh Fedora at it and let it create its schema.
  3. SELECT indexname FROM pg_indexes WHERE tablename = 'containment'; — containment_idx5 is absent.
  4. On PostgreSQL 15 or earlier the same steps produce the index.

Where the condition comes from

The condition is not accidental and was correct when written. It arrived with commit 75ad227f27 / PR #1780 (merged 2020-10-16, JIRA "n/a"), which did two things at once:

- FEDORA_ID_COLUMN + " = :resourceId AND " + TRANSACTION_ID_COLUMN + " = :transactionId AND " +
+ FEDORA_ID_COLUMN + " LIKE :resourceId AND " + TRANSACTION_ID_COLUMN + " = :transactionId AND " +

Switching the lookup from = to LIKE meant the primary key index could no longer serve it under a non-C collation, so the same PR introduced a PostgreSQL-specific schema file adding varchar_pattern_ops. Making it conditional avoided creating a redundant index on C-collation databases — a reasonable call at the time, when PostgreSQL 12 was current and lc_collate was a perfectly good way to ask.

The PR's own test instruction describes exactly the symptom this issue reports:

Build and run and watch that the hasResourcesStartingWith does not slow incrementally with database size.

That is precisely what stopped holding once PostgreSQL 16 removed the GUC: hasResourcesStartingWith now does slow incrementally with database size, on every deployment with a non-C collation.

Suggested fix

Read the collation of the current database rather than a server GUC. This works on every supported PostgreSQL version:

IF (SELECT datcollate FROM pg_database WHERE datname = current_database()) <> 'C' THEN

Alternatively the condition could be dropped entirely and the index created unconditionally: on a C-collation database it is merely redundant, whereas its absence elsewhere costs a full table scan per lookup. That also removes the possibility of the same class of bug recurring.

Since R__ is a repeatable migration, existing deployments would pick the fix up on restart. Operators who cannot upgrade immediately can create it by hand under the same name:

CREATE INDEX CONCURRENTLY IF NOT EXISTS containment_idx5 ON containment (fedora_id varchar_pattern_ops);

Note

R__Create_containment.sql is the only file in the repository using this lc_collate pattern, so this appears to be the only place affected.
