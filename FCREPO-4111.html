Description

We tried to use Camel Toolbox Fixity Checking Service (as described here: https://github.com/fcrepo-exts/fcrepo-camel-toolbox#fixity-checking-service ) but with many objects the queue will fill up, and Camel will stop to make checks. We used the service and have the fixity failure be handled by a script. The confs are here: https://github.com/phaidra/phaidra/blob/main/camel-toolbox-config/configuration.properties The script: https://github.com/phaidra/phaidra/blob/main/scripts/fixity_handler.sh just manage the output of camel to do the proper action, logging, etc. The problem is in Camel Toolbox Fixity Checking Service , after a while this happen:

WARN 09:02:01.781 [ActiveMQ Transport: tcp:///xxx.xxx.xxx.xxx:41094@61616] (Queue) Usage(default:store:queue://fixity:store) percentUsage=0%, usage=1638041234, limit=1073741824, percentUsageMinDelta=1%;Parent:Usage(default:store) percentUsage=152%, usage=1638041234, limit=1073741824, percentUsageMinDelta=1%: Persistent store is Full, 100% of 1073741824. I've incremented the limits several time with a custom activemq.xml, but it reached the new limit and stuck again. Usually the checks starts very fast and over time they start to slow down.

Finally, using 48GB as storage size, I’ve been able to check fixity on 30M datastreams but I had to restart the Camel process once because checks was very slow. After the restart, checks were fast again. Moreover this error appears in the log, even if other threads work correctly and process queue messages:

I have confirmed that the issue is purely the value configured for storeUsage. I set up fedora 7 and camel toolbox and was able to reproduce your log errors. The reason it looks like messages are not being deleted on read is that camel reads 1 message and generates 2 more. one to send the file to fixity and another to traverse it to find any children. this multiplication gives the impression of not reducing the queue size but its actually just adding yet more messages to the already full store. Unfortunately, there is no single configuration that we can ship which suits every user. Some element of configuration at the activemq level will be required dependant on local requirements. This may be a case of better documentation being required, rather than a code/config fix
