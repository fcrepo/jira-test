FCREPO-818 DbXmlPolicyIndex query is not built for XACML-2.0

Description

The XACML elements "AnySubject", "AnyResource" and "AnyAction" have been removed from the XACML schema. The DbXMLPolicyIndex is still building the query looking for the "any" elements in the policy to determine if it is a match. The end result is that policies with no subjects, resources or actions elements in the target are not found by DbXMLPolicyIndex when they should be matched.

Also, it would be beneficial to make the distinction in the XACML Policy Writing guide https://wiki.duraspace.org/display/FCR30/Fedora+XACML+Policy+Writing+Guide that the guide is meant for XACML 1.0 while FeSL uses XACML 2.0 so that people are not confused when the policies they write using the guide dont also work for FeSL.

Attached is a patch to DBXmlPolicyIndex.java that seems to fix the problem. The main change is in the createQuery function. I also added a debug log entry for one of the context attributes that was not sent to the logs that I used when debugging the query. I've also attached a sample policy that recreates the problem. It is based on the access-public.xml sample provided but is modified to allow read access to any resource in the repository except for the datastreams listed in the condition. Since there is no "Resources" section, the previous query could never return this policy.

Agree this is a bug, the policy query does appear to be based on XACML 1.0 not 2.0 in this respect.

Maybe we should support both - ie empty Resources = all resources as well as AnyResource, so that anyone who has existing policies with AnyResource (ie they've created their policy to work with the current code) still works.

Thanks for the patch on this.

Mark Roy, 2010-11-17 00:37 UTC

Not sure if both can be supported. The policies are validated somewhere along the line and I dont think it will allow policies with the "any" elements.

Stephen Bayliss, 2010-11-17 01:13 UTC

That's a good point. The validation is specified in the config files, and is XACML 2.0 - as this comment related to backwards-compatibility in case people had created XACML 1.0 policies then maybe we don't need backwards-compatibility; since the policies would have failed validation unless people had turned validation off. Would be good to verify that policies with the "any" elements do in fact fail validation.

Stephen Bayliss, 2011-03-27 16:58 UTC

Based on work done as part of FCREPO-576 Closed in making the XPath query construction code generic, added changes based on Mark's patch to test for absence of the Target section (which means "any"). Also added test for the XACML 1.0-style AnyResource etc (though if validation is enabled this would mean the policy would not have been accepted). Query now based purely on the policy document and ignores the dbxml metadata.
