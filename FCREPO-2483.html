Esmé Cowles, 2017-05-26 11:32 UTC

Andrew Woods, when I export a collection and it's inbound-linking members, I get a directory that contains the collection and the members at their respective paths.  If I want to import all of them, I can import the whole package (see https://gist.github.com/escowles/4f8b5a94093cde8232c1e117f65f1a72).

The other option would be to leave the inbound reference triples that are materialized by the InboundReferences Prefer header in the collection RDF, and update the importer to filter them out.  All things being equal, I have two reasons for avoiding this approach:

  1. On a practical level, it would shift the implementation from the Exporter to the Importer (which is larger and more complex).
  2. On a more abstract level, the inbound references are triples from the members that are pulled into the collection with the InboundReferences Prefer header.  So I'd rather handle filtering them in the code that generates them, to lessen the amount of coordination that needs to happen between the export and import steps.  Right now, the option changes the export behavior, but then the import can happen with no knowledge of it.

Jim Coble, do you have any thoughts about this?  If all things are not equal, and it's not working the way you expected it to, I'd be willing to change the implementation so importing the collection would automatically import the members.

Jim Coble, 2017-05-26 12:16 UTC

Esmé Cowles, Andrew Woods I believe that the closest thing we currently have to a concrete use case for this functionality – exporting a collection from a production repository for importing into a testing or development repository – would be adequately covered by the proposed solution; namely, export the collection using the inbound option with the appropriate predicate(s) from repo A and then import the entire exported package into repo B.

That said, I can see how someone could easily expect the import side of the tool, when run with exactly the same options as the export side except for the mode, to import exactly the same objects as the export side exported.  I don't think it's unreasonable to address that with documentation rather than functionality, at least until someone comes along with a stronger use case than I currently have.  I don't think there is anything in the current documentation that differentiates between the options that are meaningful on export and those that are meaningful on import – e.g., I presume that the "inbound" option is effectively meaningless in "import" mode.  If I'm right about that, it might be good to get that documented.  Also, I could see value in a "scenarios" document that presents a "how to" on various use cases (such as the one I described above).
