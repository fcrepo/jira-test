Description

At the moment, all special datastreams for Fedora are assumed to be inline XML. But it shouldn't matter to Fedora whether they're inline or managed. In particular, if they're allowed to be managed content, memory requirements can be drastically reduced in situations where many revisions to such datastreams exist within an object.

Aaron Birkland, 2010-05-23 18:47 UTC

The DC datastream will make this a little bit tricky. DefaultDOManager silently modifies the DC datastream if it is is incorrect (e.g. does not have the fedora pid as dc:identifier), and adds it if it is not present. There is the line:

dc.xmlContent = dcf.getAsXML().getBytes("UTF-8");

There is no equivalent for managed datastreams other than, say, modifying or replacing the contents of the temporary or uploaded file created by modifyDatastreamByReference().

A simple hack might be to clone the datastream, with the new one containing a temp file containing the modified DC content. The old datastream and associated temp file would be discarded.

Otherwise.. we may consider having datastreams be able to update themselves by value or reference, or even move the DC modification code into Management and have the modification of DC create a new datastream version and an audit record entry.

Aaron Birkland, 2010-05-23 18:56 UTC

The inline XML datastreams have an uncomfortable coupling with METS deserializers. DatastreamXMLMetadata are the only datastreams that contain "DSInfoType" and "DSMDClass" properties, and determine if the datastream is wrapped in "techMD", "sourceMD", "rightsMD", or "digiprovMD" in METS. This concept is irrelevant to the other serializers.

Stephen Bayliss, 2010-05-23 19:34 UTC

Similarly SimpleDOWriter - purge/add relationship

these require writing to datastream content - fine for DatastreamXMLMetadata, but currently not for DatastreamManagedContent.

There are other places in code where DatastreamManagedContent does get updated by creating a new temp stream from the existing, and pointing DSLocation at the new one, it would seem to make sense to migrate that into DatastreamManagedContent itself.

It would be useful to have an underlying type for DatastreamXMLMetadata and DatastreamManagedContent where we are dealing with XML Metadata datastreams that could be either of these, but that doesn't seem to slot in nicely with the existing Datastream class hierarchy (or the purpose of that hierarchy).
