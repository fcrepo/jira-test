Deployed as a docker stack. The database container is in endpoint_mode: dnsrr and the port is in mode: host

Our customers environments can differ and our mostly running on Windows servers.

Description

When creating or replacing a NonRDFSource in Fedora (fcrepo-http-api/src/main/java/org/fcrepo/http/api/FedoraLdp.java#L440C21-L440C45), the database connections needs to stay open for a long time without any activity because the binary stream (more than 100 gigabytes) is being read within the database transaction (fcrepo-http-api/src/main/java/org/fcrepo/http/api/FedoraLdp.java#L560C1-L560C48). The largest files we can ingest is thus proportional to the time the database transaction can be kept open.

A stack trace of the problem can be found here: Fedora_timeout_large_file.txt

Code location where the binary stream is actually read:

https://github.com/fcrepo/fcrepo/blob/main/fcrepo-persistence-ocfl/src/main/java/org/fcrepo/persistence/ocfl/impl/AbstractNonRdfSourcePersister.java#L89

Wich is called in these 2 locations:

  1. https://github.com/fcrepo/fcrepo/blob/main/fcrepo-persistence-ocfl/src/main/java/org/fcrepo/persistence/ocfl/impl/CreateNonRdfSourcePersister.java#L46
  2. https://github.com/fcrepo/fcrepo/blob/main/fcrepo-persistence-ocfl/src/main/java/org/fcrepo/persistence/ocfl/impl/UpdateNonRdfSourcePersister.java#L59

Proposal: Make the database transactions shorter by fetching the binaries content outside of the transaction.

yuri.carrer, 2026-04-03 10:16 UTC

Timeouts are setup to manage not responding operation, but read is responding here. So a solution can be to read the file in batches (we already use java.io.BufferedInputStream here), and at every batch we extend the timeout using the Fedora internal API on transaction timeout (by using the transaction ID). Deleting the transaction will also have the benefit to stop the long running transaction, giving the repository manager full control over it.

Thomas Bernhart, 2026-04-09 15:48 UTC

Summary of the discussion in today’s Tech Meeting:

We agreed to perform OCFL operations first. If they succeed, we execute all database operations within a single transaction. If the database transaction fails, OCFL serves as the single source of truth: after multiple failures, the transaction will roll back, and database entries will be recreated or updated by reindexing the OCFL object.

The consensus was that if OCFL operations succeed but Fedora fails to reindex the OCFL object, this likely indicates a Fedora bug: Fedora created an OCFL object on disk that it cannot read later.

Note: Fedora currently does not support reindexing an OCFL object, which already is in the database. Only indexing OCFL object not yet present in the database is supported at the moment.
