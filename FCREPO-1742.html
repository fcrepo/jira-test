FCREPO-1742 Last-Modified and ETag should not change with inbound references

Description

Inbound links should not update the last-modified date or ETag. Although inbound links can be retrieved with a resource, they are part of the state of the linking resources, not the linked-to resources.

On a practical level, updating the last-modifed/ETag when a resource is linked to make it very difficult to update resources that are frequently liked to.

Unknown, 2015-09-23 11:16 UTC

I am not sure that I agree with where this ticket is headed. According to the HTTP 1.1 spec (rfc 2616) http://www.w3.org/Protocols/rfc2616/rfc2616-sec14.html, ETags refer to "representations" not "resources". So, if the representation of any given object changes, the ETag should also change. That also means that for the resource /rest/a/b/c the ETag for application/rdf+xml should be different than the ETag for that same resource represented as application/ld+json, which is not currently the case.

Similarly, if the resource (as application/rdf+xml) at /rest/a/b/c gets a new inbound resource (and the representation changes), the ETag should also change. If, however, inbound resources are not part of the response, and there has therefore been no change in the representation of the resource (given a certain set of request headers), then the ETag should not change.

Former user, 2015-09-23 12:38 UTC

Aaron-

I think there are two issues here:

1. We should be using weak ETags, which guarantee semantic equivalence, rather than byte-for-byte equivalence. Right now, using various Prefer and Accept headers will change the representation quite dramatically, and we shouldn't be indicating that those different representations have the same strong ETag. Unless we want to create URL patterns to express all of those, it's not even clear to me how a client could make a POST to update a resource with an ETag based on a combinations of headers, and also provide those headers so we could figure out if they match or not. So I think weak ETags better represent our actual behavior now and resolve the issues from the spec you bring up.

2. If we are using weak ETags, then this question really hinges on what the state of an object is, and whether inbound links are part of it or not. They are definitely usefully-related (hence the Prefer header to retrieve them with the resource). But I think there's a strong case that they aren't part of the state of the resource itself, and are only part of the state of the linking resource instead.

A. Soroka, 2015-09-23 13:32 UTC

I don't think inbound links of any kind are part of the object state. Amongst other problems, you could get into authZ entanglements.

Former user, 2015-09-24 16:23 UTC

I completely agree that we're changing the API. The current behavior is strong ETags, which change with inbound links. The strong ETags are pretty clearly wrong for RDF sources, since they should be different for different formats, Prefer headers, etc. The inbound link aspect is problematic, and arguably incorrect as well (since we seem to agree that inbound links don't change the state).

Right now, the ETags are based on MODE's last modified property, which changes with inbound link changes. I don't know if it's possible to get a last modified property that doesn't include inbound link changes, or if we'd need to maintain our own last-modified property. Of course, there may also be some way to generate a weak ETag some other way. That idea has been brought up a few times, and I don't remember hearing any good alternatives to last-modified.
