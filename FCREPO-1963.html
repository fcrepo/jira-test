Esmé Cowles, 2016-03-24 14:32 UTC

Unknown, thanks for bringing up the HTTP/2 multiplexing feature – I hadn't heard of that, and nobody brought it up at the LDXC session where this idea was discussed (see https://ldcx2016.sched.org/event/6Wrj/4c-ldp-batch).

I see server support (Apache, Jetty, and Nginx but not Tomcat) and client support for many languages, but not Apache HttpClient, or Ruby's Net::HTTP, or any of the other Ruby HTTP clients that can be plugged into Faraday. Similarly, you mention JDK 9, but AFAICT, that's going to released more than a year from now. So I'm not sure what the timeline is for when people would be able to actually use HTTP/2 multiplexing in their applications.

A. Soroka, I thought the batch use case was sufficiently well-known, given the previous implementation and the existing ticket (https://jira.duraspace.org/browse/FCREPO-1530) to revive it. I took a look at the documented Use Cases and they are very old and nebulous. I'd be happy to write up the Hydra/PCDM/Works use case, but you can read the LDCX session notes for more info now.

A. Soroka, 2016-03-24 15:00 UTC

Esmé Cowles, no, I don't agree that the batch use case is straightforward or well-known. I'm not sure which use cases to which you are referring-- the ones that we gathered way back when, or the ones much more recently gathered in connection with the API spec effort?

I'm more concerned about the impact a wholesale adoption of what Unknown rightly describes as "an expired spec whose goals have largely been addressed with a much newer spec" will have on the process going on here.

Let's get this discussed on a public venue (LDCX is anything but public, it is particularly exclusive) like the tech call or the mailing list.

Unknown, 2016-03-24 17:03 UTC

+1 on discussing this in a public forum.

I was in the LDCX session where LDP-Batch was discussed. I didn't raise the concerns I have about this for two reasons:

1) I do not (and will not) have a use case for this sort of thing and didn't want to rain on everyone's party (personally, I feel that there are better ways to address this from a performance perspective), and
2) I had the distinct impression that this would fall under LDP Next and is therefore out of scope for Fedora qua Fedora-API.

Either way, as this feature is currently described, I have very significant reservations about enshrining it in the Fedora API.

On the other hand, if the intention is to define and implement this in some external module or with an external service, I wouldn't want to stand in someone's way.
