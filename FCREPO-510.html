Description

I'm playing with our Fedora 3.2 instance and the REST API. I'm using
the Firefox Poster add-on to do an http POST of some simple valid
FOXML to the (example) http://fedorabox:8080/fedora/objects/newpid:foobar
URI and am running into problems.

The first time I attempt to do the POST, I get the error "The PID
'newpid:foobar' already exists in the registry; the object can't be re-
created." even though it is a brand new object. However, if I search
Fedora for the object, I do find it was created. When I look through
the logs, I see that Fedora tries to create the object twice with this
one request.

If I try to POST a second object with a new pid and new FOXML, the
requests succeeds without error. Fedora only tries the ingest once.

My guess is that the initial authentication handshake with the first
POST causes Fedora to attempt the ingest twice. The second POST
succeeds since the browser is already authenticated, and doesn't need
to go through the handshake. I ran into this because I have some
client software that authenticates with every post (since it's not a
browser) and I keep running into this problem. I did not have this
issue with 3.0 or 3.1. I have included the stacktrace error below.

Has anyone else run into this? Any help appreciated.

Thanks,
Willy

Chris Wilper, 2009-06-26 17:35 UTC

Thanks Willy. I was able to reproduce this by turning policy enforcement off during installation.

Workaround:

1) Modify fedora.fcfg and change ENFORCE-MODE to "enforce-policies"
2) Remove all policy files in the directory $FEDORA_HOME/data/fedora-xacml-policies/repository-policies/default/
3) Add the two policies attached to this bug report. These minimal policies effectively allow anyone to do anything, but require an administrator (e.g. fedoraAdmin) in order to do any repository-modifying operations.

Possible ways of addressing this in future Fedora releases.

A) Don't provide the option of completely turning off policy enforcement. Instead, allow people to choose "minimal" policy enforcement, in which case the attached policies are put in place.
B) Fix Fedora's servlet filters so that when an authN challenge needs to be sent, it doesn't attempt to run the original request through AuthZ anyway. This approach might already be taken by FCREPO-451 Closed (FESL)...need to verify.

Bill Branan, 2009-06-26 20:06 UTC

This has been fixed in trunk. The issue was that the AuthN filter for the REST API was not returning properly after an authentication check. Even if authentication was required it would allow the process to continue. This was fixed by returning the correct value after the auth check.

Bill Branan, 2009-06-29 18:48 UTC

This issue existed as part of Fedora 3.1. The reason that it did not cause an error then was because in 3.1 the ingest method of the REST API would capture the "object already exists" error and pass the parameters along to the update method. This was changed in 3.2 to throw an error instead.
