Description

When replacing/updating a resource's triples whose datatype is 'float' (such as latitude and longitude coordinates), the triples whose datatype is 'float' will not be updated if the new (float) value rounds to the existing (float) value.

For example:

Given this float value: 9.123456
A PUT with this new value: 9.123456123456

Will result in the float value being unchanged. It will remain 9.123456. Other triples, such as a title or text, are updated correctly.

If, however, the new (float) value is 9.12345678910, the value will be updated (presumably because the rounded value is different, but that's speculation).

This gist shows the issue:

https://gist.github.com/kefo/94430d0e10e283d0ca91d32155f66d5a

NB: The replacement PUT invokes the 'lenient' header, but I have seen this issue when not using the lenient header. I do not know what happens when PATCH is used. Will test and report back.

kefo    A floating point number is stored as binary. Please use decimal instead of float.

e.g. 

@prefix geo: <http://www.w3.org/2003/01/geo/wgs84_pos#> .

@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .

@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

 

<>  geo:lat "9.123456123456"^^xsd:decimal ;

    geo:long "-9.123456123456"^^xsd:decimal ;

    rdfs:label "Updated? No."^^xsd:string .

kefo, 2018-05-30 17:37 UTC

I have two thoughts about this issue, the second being perhaps more relevant to Fedora 4 (and 5?).  

1) I don't understand why two distinct float values should be treated as the same, which is what appears to happen, because the more precise one naturally rounds to the other, existing float value.  I understand that the standard for float values (IEEE 754) defines a float as a binary, and so I understand why Java would treat the value as a binary, but I don't understand how it concludes that "9.123456" equals "9.123456123456", if that is what is happening under the hood.  It is worth noting that I discovered, when trying to correct our issue, that Blazegraph also does this.  I wondered if Fedora and Blazegraph shared some (RDF) library that might be the root cause.  Perhaps I simply do not understand what it means to have these values be binaries (it could simply be ignorance), but it feels like something is wrong somewhere.  I do recognize that it may not be something under Fedora's control that is causing this (assuming it is actually not right).

2) In the end, I am issuing a PUT against Fedora.  It is my understanding that, except for server-managed triples (the 'leniency'), all the other triples of the targeted resource should be discarded and replaced with the request body.  That's not happening for geo:lat and geo:long, neither of which is a server-managed triple to my knowledge.
