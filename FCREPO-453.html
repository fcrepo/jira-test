Description

Chris Wilper wrote:
I got a chance to read through your performance wiki[1] again in more
detail and found it quite informative. One part I missed before was
the discussion on "Managed Content Retrieval", where you discuss the
use of a Tomcat FileDirContext in order to avoid sending content in
via the upload servlet. If Fedora just had the option to accept local
"file:///" URLs on ingest, I think that would be even better. There's
a security consideration to doing that, but I think as long as the
repository could be configured to reject file:/// URLs from all but a
set of "allowed" local paths and the input was sanitized (removing
"..", etc), we would be ok.

Benjamin Armintor, 2009-03-13 16:08 UTC

I'm trying to put together a very rudimentary implementation of this, and have run into a few places outside the ExternalContentManager implementation where the presumption of http[s] urls required a change:

  • fedora.server.storage.types.DatastreamReferencedContent
  • fedora.server.validation.ValidationUtility
  • fedora.server.access.DisseminationService

There may be others; I expect you could identify them by looking for uses of MIMETypedStream and seeing if the class is using fedora.common.http.WebClient.

In general, faking HTTP headers into the Property array of the MIMETypedStream and serving up a FileInputStream (or an InputStream from a java.net.URL) seems to work fine, leaving aside the implementation of a security policy. Without access to the DO, you need to guess at MIME type, which is a little unfortunate.

On a related note, working on this inclines me to think that it would be good if classes like ValidationUtility were able to query the ExternalContentManager implementation for supported url protocols, rather than hard-coding them or relying simply on Java not considering them malformed. Maybe querying them for configuration parameters? That seems a little hackish.

Benjamin Armintor, 2009-03-25 18:05 UTC

Some thoughts after working through this:

  • ExternalContentManagers get no direct access to DatastreamReferencedContent objects. This means that the association of a mime-type with a served file is guesswork (and ugly guesswork, at that). The addition of a method to serve content from a DatastreamReferencedContent (rather than a String url) would allow the ExternalContentManager to use the datastream's defined mime-type
  • The exception signature on ExternalContentManager.getExternalContent doesn't allow for an AuthzDeniedException, so authorization failures are shoehorned into GeneralExceptions or HttpServiceNotFoundExceptions, resulting in response codes of 500 instead 40x
  • The lack of a generic policy enforcement method means an existing method has to be hijacked (hence the kind of ugly policy, and the use of PID for the canonical file path URI)

On the other hand, it works, and the policy enforcement is working (in our development environment, anyway).

Benjamin Armintor, 2009-12-16 21:23 UTC

The issue with managed content is that the DefaultDOManager is using too narrow a pattern to pick up all file: url's. This causes it to silently skip the retrieval of the datastream bytes, which results in downstream access errors.

1. fedora.server.validation.ValidationUtility should allow 'E' or 'M' control groups for file urls
2. fedora.server.storage.DefaultDOManager should use a more flexible pattern, and should either log inoperable DSLocations, or throw an exception on same, or do both.

There's also an unpleasant reliance on ValidationException to trigger internal id handling in fedora.server.storage.types.DatastreamManagedContent, but the refactoring a fix would require is probably too ambitious for 3.3.
