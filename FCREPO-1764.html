Description

When you create a fragment URI, I would expect to be able to delete it by running sparql update on the parent resource and doing something like

DELETE

{ <hashuri> ?p ?v }

WHERE

{ <hashuri> ?p ?v . }

but doing so throws errors that it can't delete the server managed triples on that resource.

Comments (21)

Esmé Cowles, 2015-10-08 20:11 UTC

If you specify a particular property, you can delete it, e.g.:

DELETE WHERE

{ <hashuri> <http://example.org/foo> "bar" }

But deleting all of the userspace properties doesn't delete the resource – the server managed resources associated with it being a container stick around.

Also, trying to delete with an HTTP DELETE deletes the parent resource, e.g.:

curl -X DELETE "http://localhost:8080/rest/foo#bar"

deletes http://localhost:8080/rest/foo, not the hashuri.

Esmé Cowles, 2016-02-16 16:25 UTC

The current behavior: if all the user-managed triples about a hash URI fragment are removed, then the node remains in place, but is invisible. This could result in very large numbers of empty hash URI fragments hanging around.

Here's a PR that remove them: https://github.com/fcrepo4/fcrepo4/pull/982

Given our other choices (not including server-managed triples, not providing an explicit deletion mechanism), I think removing them when there are no user-managed/visible properties associated with them.
