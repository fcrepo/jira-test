Description

For a significant number of objects in our Fedora 4 repository, the attempt to create a version fails with the following error message (for example):

11-Jul 15:39:56.090 [http-bio-8443-exec-3] INFO o.fcrepo.http.api.FedoraVersioning - Request to add version 'version.20160711.154118' for 'prod/ff/4d/0e/44/ff4d0e44-c3a1-4dc9-bd5f-417f6517bfc3'
11-Jul 15:39:56.212 [http-bio-8443-exec-3] ERROR o.f.h.c.e.NodeNotFoundExceptionMapper - NodeNotFoundException intercepted by NodeNotFoundExceptionMapper: Cannot locate child node: 87a0a8c317f1e7e1d4fcd7-3c92-4fe3-96c2-371b8eb6f1d3 within parent: 87a0a8c317f1e7d94b13d3-bbbd-42f3-9f3d-706a10e5ffc3

This occurs both on objects which have had versions successfully created in the past and on objects that have no previous versions. Once this error occurs on an object, all subsequent attempt to create a version for that object result in the same error.

Issuing a GET on the fcr:versions node for an object with this problem returns a list of "prefix" attributes but no RDF triples and generates the following message in the fcrepo log:
11-Jul 15:53:19.348 [http-bio-8443-exec-16] WARN o.f.k.m.rdf.impl.VersionsRdfContext - An unlabeled version for https://repostore.lib.duke.edu:8443/fcrepo/rest/prod/ff/4d/0e/44/ff4d0e44-c3a1-4dc9-bd5f-417f6517bfc3 was found! Omitting from version listing!

Michael Durbin, 2016-07-12 17:33 UTC

Here's what I'd try to do to debug it:

1. Eliminate the possibility that there's a critical bug in fedora when dealing with your example data.

It wouldn't surprise me if certain version labels were invalid, or if other characteristics of the resources being versionioned might result in an exception. It's relatively easy to test this if you're doing a migration. Simply perform the migration of that problematic object against a clean repository. If it works fine, great, we can dig a little deeper.

2. Try to find a pattern in the errors.

This is trickier. Some odd possibilities that come to mind are:

a) There's a small amount of corrupted entries, but they have sha1s that match "new" content you're versioning: since modeshape doesn't actually persist new content if it already has a node with the given sha1, a corruption or problem in the database might show up in seemingly unrelated places. For example if in a fedora 3 migration a lot of versions of datastreams are identical (perhaps there's an empty template for a MODS record, or DC record or something) and for some reason the fedora 4 database has corruption on that record, whenever you try to access that content again you'd get an error.

b) I don't have any other ideas for now, but if you can get errors consistently (though unpredictably) maybe export each resource before you make the version snapshot, then if you get an error snapshotting you'll have a copy of the resource that triggered the problem. You wouldn't have to retain the exports if the version operation is successful.

Jim Coble, 2016-07-13 15:17 UTC

Andrew Woods One commonality that we have noted is that the problem seems to arise when versioning all the objects in a particular collection (and, in particular, a large collection) and, when it does arise, it seems to follow a common pattern. For example, yesterday, we queued up version creation jobs for a collection containing something over 12,000 objects. The first 4500 or so jobs proceeded with no failures. Then, the jobs began failing. Once the jobs began failing, all the subsequent queued up jobs also failed. At one point we stopped the job queue, stopped and restarted Tomcat, and resumed the job queue. The remaining queued up jobs immediately continued failing. This pattern seems to be – running a batch of version creation jobs for smaller collections (say, 6500 objects or less) seems to succeed and running a batch of version creation jobs for larger collections seems to work for some number of objects in that collection and then start failing.
Also, note that all the objects in a collection have a relationship to the collection object – don't know if that is a factor or not.
