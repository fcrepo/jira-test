Description

Reported by Nigel Thomas

Concurrent policy modifications and reads cause deadlocks with DBXML.

The current FeSL code does not manage deadlocks (or even attempt to detect them).

This can result in a corrupt policy index, or a "permanent deadlock" state where restarting the Fedora server fails to clear the DBXML deadlock - so first access to the repository never completes.

Attached are amended versions of DbXmlManager and DbXmlPolicyIndex that include wrapping operations in transactions, detection of deadlocks and transaction abortion when deadlocks occur (against release 3.4.1).

Stephen Bayliss, 2011-01-12 04:03 UTC

We can dispense with transactions altogether, so long as we have single-threaded updates.

Implemented this, it means catching errors on reads, and retrying operations (ie doing what dbxml deadlock detection would do, but a simpler version).

(there would be a more elegant way of doing this, by blocking read threads if a write is in progress and vice-versa, but allowing multi-thread reading but only single-thread writing. to be revisited as part of FCREPO-576 Closed , added a note to that issue to cover this)

Load-tested this with 10 concurrent update threads, 50 concurrent write threads, update threads each perform updates (adds, reads, deletes) to a set of 200 policy objects - no errors.
