Description

This task is to investigate and resolve the error scenario detailed below:

  • Create a container resource in the HTML UI
  • Update a property on that resource:
    PREFIX pcdm: <http://pcdm.org/models#>
    INSERT { <> a pcdm:Object }

    WHERE { }

  • Update another property on that resource:
    PREFIX pcdm: <http://garbage.com/models#>
    INSERT { <> a pcdm:Garbage }

    WHERE { }

Boom! notice error

Ideally, the solution to this issue will consist of detecting that a namespace prefix has already been defined to reference a different namespace and an exception is thrown that comes back as an HTTP response to the user as a "409 Conflict" (http://www.w3.org/Protocols/rfc2616/rfc2616-sec10.html#sec10.4.10).

A. Soroka, 2015-10-19 00:27 UTC

So you're catching the NamespaceException and rethrowing?

  • You could invent something more specific than IllegalArgumentException, e.g. UndefinedNamespaceException or the like.
  • The JCR contract is ugly and I don't think you're horribly wrong to rethrow, but you could do Arrays.asList(getNamespaceRegistry().getPrefixes()).contains(myPrefix) to avoid putting a rethrow in what seems to me to be an "unexceptional" execution path. A. Soroka, 2015-10-19 13:55 UTC

With a new independent exception type, we can use the exception-mapping system to provide some useful special behavior in the HTTP API. For example, we could offer an error screen that not only tells the user that she used an undefined namespace, but offers some way to correct that. While this is not part of your immediate ticket, you could without too much effort leave the door open by inventing a new exception. (And so doing shouldn't be very hard.)

Short answer: you don't have to, but it would be nice and it should be very little effort. If you don't know where to begin, I'm happy to help.
