Description

Allow creation of historical mementos of containers using the body and datetime in the request. Server must honor most server managed triples provided in the request body.

If the body of the request does not contain necessary server managed triples, request should return with 4xx status.

Comments (7)

Ben Pennell, 2018-03-12 13:50 UTC

Danny Bernstein Andrew Woods A few implementation questions that have come up so far:

1) When importing a historical memento, should the client be required to provide ALL of the server managed triples (fedora:created, fedora:createdBy, fedora:lastModified, fedora:lastModifiedBy, server managed rdf:type <fed:Container/fed:Resource/ldp:RDFSource/etc>).  As opposed to allowing fedora to fill in any missing ones.  While requiring all of them would ensure that the created memento will be exactly what was submitted, that could cause issues if Fedora implementations required different server managed triples.

 

2) Should fedora:writable be set to false for mementos on creation/import, regardless of what it was before?

 

3) Currently I am storing fedora:mementoDatetime and the memento mixin as properties on the memento resource.  This results in them being returned in GET response, which seems counter to the requirement of mementos being unchanged.  My intention is currently to suppress them from the body of responses, but wanted to get confirmation on this.

Andrew Woods, 2018-03-12 13:56 UTC

1) I would suggest we provide an exact list of "minimal" SMTs that must be provided by the client. I would not suggest Fedora create any additional SMTs

2) Yes, fedora:writable should be false

3) Suppressing fedora:mementoDatetime and the memento mixin seems like a good idea.

Jared Whiklo, 2018-03-12 14:01 UTC

1) I'm guessing it should be all triples, especially as we want to remove any dynamically generated triples. As which triples (if any) are server managed is an implementation decision I don't feel that should detract from this path.

 

2) Is fedora:writeable used for anything?

 

3) I would agree that these properties should not be returned as part of the body. The mementoDatetime is returned in the header and (but I could be wrong) there is a Link: <>; rel='type' for Mementos

Ben Pennell, 2018-03-12 14:45 UTC

Jared Whiklo which dynamically generated triples would you expect to be removed?  I am mainly thinking of generated membership, which I had been thinking we would want to represent in the memento since that was part of the objects state when it was captured.

Jared Whiklo, 2018-03-12 16:14 UTC

In this context I was thinking about things like created and last modified dates. I guess dynamically generated is not correct terminology. More server managed, sorry about that.
