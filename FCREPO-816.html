FCREPO-816 Allow substitution of URL path parameters when service methods reference "E" datastream

Description

A little (if at all!) documented feature of the CMA is that when a service method binds to an "E" type datastream, the parameters supplied to the method (including default parameters) are available for parameter substitution in the "E" datastream's contentLocation. (see DisseminationService lines 248 onwards)

eg, if the datastream's contentLocation is
http://server/service?param=(PARAM1)

and the service method binding to this datastream has a parameter PARAM1, this is substituted in the above URL - service method parameters can be passed through to the datastreams they are invoking.

Noting that the current CMA does not support binding of service methods as inputs to other methods, this provides a mechanism whereby a datastream can "proxy" for an object method, with any method parameters being passed through to the proxy datastream and thus to the underlying service (which could itself be a method on an object).

However, parameter substitution is currently based on matching "=(PARAM)" which means that URL path parameters are not substituted. This is inconsistent with the parameter substitution on the WSDL datastream, where any occurence of (PARAM) is substituted (ie no limitation on only substituting query string parameters).

Noting again the lack of dissemination binding, implementing this will allow an easy way to implement datastreams as proxies for methods to effectively allow method bindings as inputs to methods.

Example:

method1 runs an xslt on a datastream
method2 runs an xslt on method1 to provide an XHTML version

issue: method2 cannot bind to method1 (it is possible to supply the full method1 URL as an input to method2 in the WSDL operation location, however this input is not a datastream binding, this means that datastream mediation will not occur - so if eg the external XSLT service does not have access to object service methods the call will fail - eg if API-A authentication is enabled).

usual solution: create a datastream in the data object that references method1, then method2 binds to this object datastream. This is cumbersome as it means adding this proxy datastream to every data object, and effectively introduces a binding between the data object and the SDef (for ease of maintenance, the data object should only need to bind to the CModel)

better solution:
create a datastream called METHOD1 on the sdep with contentLocation
http://local.fedora.server/objects/(PID)/methods/sdef:pid/method1

This effectively creates METHOD1 datastream as a proxy for the METHOD1 service, on the service depoyment object.

method2 can then bind to method1 by instead binding to this datstream by:
1) declaring a default input param PID value $pid (in METHODMAP)
2) declaring a datastream binding to METHOD1, specifying the pid attribute as the sdep pid (to bind to the sdep METHOD1 datastream rather than a METHOD1 datastream on the data object)
3) in the WSDL, use (METHOD1) to effectively bind to the method1 method

Implementation:
Extend the curent parameter substitution based on a pattern "=(PARAM1)" to also include the pattern "/(PARAM1)" (possibly check for /(PARAM1)/, /(PARAM1)?, /(PARAM1)# and /(PARAM1) with nothing after - we need to avoid inadvertent substitution elsewhere in the URL, eg if (PARAM1) is used as part of a query string)

Potential issue: if there are URLs that use the pattern (PARAM1) by design in their path this would inadvertently get substituted. I can't recall seeing many URLs that use brackets in their path, and in any case appropriate choice of the binding name would get around this.

Stephen Bayliss, 2010-11-10 15:16 UTC

Agreed, the focus of this is not overall to propose how chaining of disseminators should be done. (Though in the absence of this in the short term, it does provide a mechanism)

The motivation for doing this could be expressed more simply as:

  • the current code allows parameters passed to methods to be passed to the underlying bound datastream where the datastream is of type "E"
  • however only URL query parameters are currently passed, in a REST-ful world this should be expanded to also include path parameters

Though it could be argued that the mechanism currently in place should not be there at all and should be removed? But should we be removing functionality that people may already being made use of?
