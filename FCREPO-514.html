Environment

I'm using Fedora 3.2.1 with the included tomcat and included database. (install.properties attached). This is the copy of fedora running on MediaShelf's testing disk image: fedora-3.2.1-solr-1.3.0-testing.dmg. (Info Here: http://projects.mediashelf.us/wiki/active-fedora/Blank_FedoraSolr_Disk_Image ; Download Here: http://drolma.mediashelf.us/downloads/fedora-3.2.1-solr-1.3.0-testing.dmg)

Description

After a period of usage, Fedora 3.2.1 becomes sluggish and unpredictable. Ordinary requests such as

http://127.0.0.1:8080/fedora/objects/new?label=test&ownerID=fedoraAdmin&state=A

Cause a StorageDeviceException, deriving from derby returning "ERROR 40XL1: A lock could not be obtained within the time requested". See stack trace below.

There is still storage space on the device. The errors only occur after I've used the image for a while (usually when I get to around 550 objects). I am mostly running the test suites for active-fedora and ruby-fedora against it.

Andrew Woods, 2009-07-21 14:53 UTC

There have been similar locking issues observed with the embedded-derby-db, none of which are exhibited when using the networked-derby-db. This particular issue may be linked with DERBY-JIRA-4273 (https://issues.apache.org/jira/browse/DERBY-4273). The bug mentioned in Derby's Jira may have been resolved in release 10.5.2.0 (although implementor was having a hard time reproducing the bug in the first place).
It is worth looking into whether the 10.5.2.0 release (not yet available) fixes FCREPO-514 Closed

Chris Wilper, 2009-11-22 22:33 UTC

Fedora's Derby in trunk has now been updated to 10.5.3.0 ( FCREPO-584 Closed ). It would be worth trying to reproduce this again. We haven't seen this problem in testing in Fedora, but I recall having locking issues with the older version of Derby in Akubra as well, which were resolved by updating to a newer release.
