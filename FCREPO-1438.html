Michael Durbin, 2015-04-08 15:57 UTC

I'm strongly opposed to blanket unit testing for this project for the following reasons:
1. they don't actually ensure that the code works
2. implementing and maintaining them is an onerous burden that discourages people from volunteering to make changes necessary in this project for their use
3. given the extremely low use (and the fact that it wasn't used as a base for the other fedora 4 client code in fcrepo-camel) it would seem that it may require some refactoring to be more generally adopted for use (which would result in all the work writing unit tests being wasted effort)
4. given its status in fcrepo-labs, it is not expected to have the same requirements for unit-test-based code coverage
5. most of the units of code we'd be testing are so simple that the setting up mocking to test them dramatically exceed the complexity and size of the code being tested.

In other words, I don't see how, for code that's essentially one that exercise the fedora REST API as currently specified, adding a unit test that amounts to a mocked implementation of the REST API call we're invoking adds value anywhere near proportional to the amount of work it takes. Furthermore it arguably decreases the value of the codebase because there would then be two pieces that need to be completely rewritten when the REST API changes.

That said, I'm willing to add an integration test for this.
