FCREPO-569 fedora/risearch GET query returns incorrect result when querying on literal object that contains multibyte utf-8 sequences

Environment

Windows XP client and server (same machine), Server platform encoding set to utf-8 (also occurs when set to cp1252

Description

Issuing a "GET" iTQL query to fedora/risearch, constraining the object on a string literal that is a multibyte utf-8 string returns incorrect results.

To reproduce, create an object with the following relationship in RELS-EXT:

(the byte sequence for the literal below is 0xE2, 0x80, 0x9C, 0xCE, 0x910x20, 0xC2, 0xBF, 0xE2, 0x80, 0x9D
which is: left double quotes; capital alpha; space; inverted question mark; right double quotes)

<info:fedora/some:pid> <urn:bar> '"Α ¿"'

The sample iTQL query for this is:
select $s from <#ri> where $s <urn:bar> '"Α ¿"'

Issuing this in the fedora/risearch web interface (ie via POST) works fine - the tuple is returned.

The GET version of this is as follows (url-encoded)
http://localhost:8080/fedora/risearch?query=select+%24s+from+%3C%23ri%3E+where+%24s+%3Curn%3Abar%3E+%27%E2%80%9C%CE%91+%C2%BF%E2%80%9D%27&type=tuples&lang=itql&flush=true&format=Sparql

This returns no results.

This currently impacts integration tests for example fedora.test.api.TestRelationships.testAddRelationship() when tests are added for multibyte utf-8 literals.

Stephen Bayliss, 2009-11-02 11:13 UTC

Reproduced using a simpler test case using the copyright symbol: ©
Including <dc:rights>©</dc:rights> in the DC datastream results in the correct triple in the resource index.

URL-encoding this character (for HTTP GET RI query) gives %c2%a9

Using this in the query returns no results.

However using just the ASCII equivalent, ie %a9 does return results.

So it would appear that where the query parameter is being url-decoded, this is not done wrt utf-8 correctly.

Former user, 2009-11-02 14:47 UTC

I can reproduce this on OSX.
I believe the UTF based URIs are not properly decoded by Tomcat with the current default configuration. The Tomcat Configuration Reference[1] states: "This [URIEncoding] specifies the character encoding used to decode the URI bytes, after %xx decoding the URL. If not specified, ISO-8859-1 will be used." The property is not set, so it defaults to ISO-8859-1. After setting this property in server.xml the query seems to be encoded correctly.

[1] http://tomcat.apache.org/tomcat-5.5-doc/config/http.html

Stephen Bayliss, 2009-11-02 15:51 UTC

I can confirm Kai's solution - that adding URIEncoding="UTF-8" to the connector in server.xml resolves this on Windows.

Suggest we
(1) document this; and
(2) modify fedora.utilities.install.container.TomcatServerXML to add this attribute
or
(1) standardise on ISO-8859-1 url-encoding throughout Fedora; however this may cause more issues as UTF-8 encoding is pretty much standardised on outside of URLs

W3C recommendation is to use UTF-8:
http://www.w3.org/TR/html40/appendix/notes.html#non-ascii-chars
http://java.sun.com/j2se/1.5.0/docs/api/java/net/URLEncoder.html#encode%28java.lang.String,%20java.lang.String%29

Chris Wilper, 2009-11-03 15:58 UTC

Sounds like UTF-8 is the right option, I agree with your first solution (document it and modify TomcatServerXML to add the attribute). Too bad Tomcat doesn't default to that, though. I wonder what other appservers do.
