FCREPO-775 Failing to close input stream when reading datastream content leaves file locked - can't purge

Environment

Windows

Description

Failing to close an input stream used for reading a resource, eg using the REST API getDatastreamDissemination (client) can leave the file locked on the server.

Purges of the object then throw IOException (in org.akubraproject.fs.FSBlob.delete).

This did not seem to happen with the legacy LLStore implementation.

This can happen client-side, ie read a managed content datastream, don't close the InputStream, purge datastream/object can fail with an underlying IOException.

Mostly this has only occured during testing (when we add and then purge an object in quick succession).

Is this just a case of reviewing the code for non-closed streams, or is there something else that should be done to tackle this issue? This only seems to occur on windows (so there is potential to determine the platform and do a File.deleteOnExit(), but is this the right way to tackle this?)

This occurred in FCREPO-766 Closed where IOUtils.copy() was used (which does not close streams).

Another instance ConfigC - TestPolicies failure:
org.fcrepo.test.fesl.util.HttpUtils.process() line 241-246
(This time a loop copying bytes from the InputStream, but not closing it -fix about to be committed closing the InputStream, previously this was not present).

And in org.fcrepo.server.security.xacml.pdp.decorator.PolicyIndexInvocationHandler - after adding/updating policy, it is indexed in DBXML. Again stream was not being closed, so policy could not then be deleted.

In the existing LLStore, the delete is via a File.delete() (with no check for "true" returned) - would be useful to see what Akubra does for this.

A simpler solution: http://commons.apache.org/io/api-1.4/org/apache/commons/io/input/AutoCloseInputStream.html

Wrap the rest response in that, and that will cater for the majority of cases I think (FileInputStream would get closed as soon as it has been read).

Would this cause an issue for streaming clients? (ie they want to seek back and forth, do we even support that?)

AutoCloseInputStream does not support read and reset. However probably not too difficult to come up with our own version that does. That way we maintain the same contract as we have now.
