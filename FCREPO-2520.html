Description

In testing with the Hyku repository app on top of Fedora (using a build from the master branch, May 2017), occasional errors occur when files are deposited but fail to complete the process properly. When attempting to retrieve or delete the item from Fedora, a 500 response is returned. The errors in the log are:

java.lang.IllegalArgumentException: Error parsing media type 'cannot open `/tmp/40e8273e-1ea8-48ec-916c-e78bc06ba1ea20170608-25523-m6g42x' (No such file or directory)'

followed by:

Caused by: java.text.ParseException: White space not allowed.

Requesting fcr:metadata on the item shows the following:

ebucore:hasMimeType "cannot open `/tmp/40e8273e-1ea8-48ec-916c-e78bc06ba1ea20170608-25523-m6g42x' (No such file or directory)" ;

The mimetype set here is clearly invalid. While it seems likely that the primary issue is due to the Hyku app supplying an invalid mimetype, there should be better data validation in Fedora to ensure that a mimetype which cannot be parsed is not allowed into the repository.

Alternatively, if it is desirable to allow invalid data to be stored, then the API should fail gracefully when that data is requested and allow the item or the metadata itself to be removed or updated without error.

Aaron Birkland, 2018-01-25 14:31 UTC

This issue is not fully addressed yet.  There are two aspects to this ticket:

  • Degrade gracefully if an existing repository has bad mime type values (Bethany's PR, now merged addresses this)
  • Ensuring that bad values do not get in to the repository in the first place

We can debate if (2) is necessary - is it the responsibility of the repository to ensure that mime type values are syntactically correct?  If not, then this needs to be positively asserted and/or documented and this ticket can be closed.

If validation is necessary, then there are two areas of concern:

  1. Validation of Content-Type headers in requests that create or modify an LDP-NR
  2. Validation of direct mutations ebucore:hasMimeType triple (e.g. via a PATCH or PUT to the LDP-RS that describes an LDP-NR.)

Validation concern (2) is particularly problematic.  The modeshape implementation chooses to assign particular significance to the  ebucore:hasMimeType triple.  The value of this triple is used in crafting responses to GET or HEAD requests on the associated LDP-NR.  We speculate that Hyrax (or some associated service) was causing the problem via PATCH (Bill Branan - can you confirm, please?).
