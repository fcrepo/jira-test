Osman Din, 2015-03-26 21:42 UTC

ModeShape’s Name needs a localName and URI, as the trace suggests. With the provided SPARQL update statement, localName is blank for http://example.org/. (It should’ve been http://example.org/title/“ or something, I believe). This is enforced at many different points in ModeShape, and wherever this is checked (using the utility CheckArg), an exception gets thrown, and, perhaps more problematically, returned as a String.

For example, see AbstractJcrNode . The toString() catches the generic Exception, and returns the exception message as a String (not sure why ModeShape chose to do this).This is problematic if we log the value using something like FedoraResource.toString().

Options:

Perhaps the resolution would be to try to see if some sort of logging could be done in F4 upon initial PATCH. Alternatively, the runtime exception could also be caught in PropertiesRdfContext, although this would be ModeShape dependent behavior and I wouldn’t be surprised if patches would be needed in other F4 code as well. Or, perhaps just rely on users knowing better (that is know when an update is “dodgy”).

Andrew Woods, 2015-04-10 22:24 UTC

Ideally, we could return a 4xx status code on the initial PATCH.
In the absence of that possibility, we should at least enable the deletion of the resource after the fact.

Osman Din, 2015-05-27 14:47 UTC

Just a note on the latest comment: Deletion doesn't seem to be technically possible once a "dodgy" resource has made its way in (ModeShape still wants a localName when javax.jcr.Item#remove() is invoked), so validating the initial HTTP request is likely the only approach (and the one that I'm going to try).
