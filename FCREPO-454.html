Description

In response to http://article.gmane.org/gmane.comp.cms.fedora-commons.devel/1066
Bill wrote:

> It occurs to me with this request that the states we use currently use for
> objects in Fedora are primarily for user convenience. Is there anything
> stopping us from allowing a repository admin to define the states in which
> an object can exist? This is a long way from being workflow, but I could see
> it facilitating the creation of a simple customized workflow on top of
> Fedora, especially with the ability to do access control based on state.

Comments (5)

Chris Wilper, 2009-02-26 19:28 UTC

I think this is worth some more thought/community feedback.

The way people do this kind of thing now is by 1) having a special datastream to hold state, and 2) holding such info in a custom predicate in RELS-EXT. Here are a couple advantages I can think of to having extensible states:

  • For simple cases, people don't need to define a special format just to hold this state value
  • Even when using RELS-EXT (or RELS-INT down the road) with a custom predicate, it's still relatively expensive to make a small change, because ultimately the whole datastream's content must be modified. It gets worse if versioning is enabled.

Chris Wilper, 2009-03-13 17:50 UTC

We discussed this in the special topic meeting on 3/13:

http://fedora-commons.org/confluence/x/4YSv

There was general agreement that we should have either A) extensible state values for the STATE attribute, or B) an additional attribute for tracking workflow state. A is simple and easy to do, but B might give people a better separation between "Availability/Visibility" state and "Workflow" state. The group didn't come to a strong conclusion on this. We will therefore solicit more input from workflow-savvy people.

Stephen Bayliss, 2009-08-24 12:13 UTC

I can see the following potential options:

1) leave it to a workflow engine to manage (the workflow engine would be responsible for persisting state)
2) use the existing state attribute (extend the values permitted)
3) have a new state attribute
4) have generic methods for adding and manipulating custom object and datastream properties (repository developers can then define their own state attribute(s) as required)
5) do it in RELS-EXT/RELS-INT

I would tend to favour (4) as it doesn't prescribe how state should be modeled and persisted wrt workflow, but gives developers the ability to implement whatever they need. However there does seem to be potential overlap with RELS-EXT/RELS-INT in this approach.

Also, we currently have in FOXML optional extproperty elements to store "custom" properties - but no API methods to manipulate them - perhaps adding API methods for these would suffice at this stage? (The original reporter only seems to mention tracking "state" at the object, rather than datastream, level)

Chris Wilper, 2009-09-01 17:13 UTC

Decided 9/1/09, need improved docs on relationship API, see FCREPO-528 Closed . Consensus was that workflow state management is not a central concern of the repository and we need real use cases to motivate changing Fedora's definition of STATE to go beyond (Active, Inactive, Deleted). Possible future special topic meeting if motivated by a group doing workflow who wants to see a change to Fedora to facilitate this.
